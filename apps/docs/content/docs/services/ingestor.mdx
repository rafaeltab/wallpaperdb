---
title: Ingestor Service
description: Authenticated wallpaper ingestion with durable upload recovery
---

The ingestor accepts wallpaper bytes for an authenticated Profile, validates content, stores the immutable original, and publishes an upload announcement for downstream consumers.

## Upload contract

`POST /upload` accepts one multipart file. The Profile ID comes from Clerk authentication; multipart ownership fields cannot override it. Images are buffered within a 200 MiB transport ceiling before inspection. Supported image formats are JPEG, PNG, and WebP, with a 50 MiB content limit and dimensions from 1280×720 through 7680×4320. Video uploads are not supported.

A successful response is HTTP 200 with `id`, `status`, `uploadedAt`, `fileType`, `mimeType`, `width`, `height`, and `fileSizeBytes`. The status is `processing` for accepted content or `already_uploaded` for existing content owned by that Profile. Concurrent requests for unfinished identical content receive HTTP 409.

Expected failures use RFC 9457 `application/problem+json`, with stable problem-type URIs under the repository's `docs/problems` directory. Validation is 400, missing authentication 401, oversized input 413, quota denial 429, unavailable dependencies 503, and unexpected defects 500. Internal diagnostic causes are never included in responses.

`GET /health`, `GET /ready`, and Swagger UI at `/documentation` are public. Readiness becomes true only after the application graph is acquired; health checks PostgreSQL, object storage, NATS, and configured telemetry.

## Application architecture

The ingestor is one application boundary in the Wallpaper Ingestion context. `Ingestion`, `Admission`, and `Availability` expose application-owned interfaces and namespaced Effect services. Their layers resolve dependencies at construction. PostgreSQL, S3, image inspection, NATS, and Redis remain behind driven adapters; Fastify translates multipart requests and application outcomes.

The composition root owns shared adapters, request fibers, and recovery workers. Configuration is parsed once, credentials are redacted, and secrets are unwrapped only for adapters. Telemetry initializes before dynamically loading instrumented server dependencies. Shutdown stops accepting requests, gives in-flight responses a bounded grace period, interrupts remaining work, and releases resources. Recovery loops do not overlap themselves and stop with the application's scope.

Architecture lint checks public module entry points, inward dependency direction, dependency cycles, and absence of TSyringe or global service locators.

## Durable upload and recovery

1. Inspect content and atomically reserve its Profile/content identity, complete metadata, logical asset reference, and event occurrence.
2. Store the original under the stable asset identity.
3. Atomically commit stored state and the upload announcement to an outbox.
4. Publish with the original event occurrence ID and wait for broker acknowledgement.
5. Mark the upload `processing`. Downstream completion is a separate responsibility.

A storage failure leaves enough information to check the exact original during recovery, including non-JPEG extensions. A publication failure retains the stored original and outbox occurrence. Retries preserve occurrence, correlation, causation, and persisted trace context. CloudEvents 1.0 metadata wraps the shared wallpaper payload; existing consumers can still parse retained legacy events. The shared payload still carries legacy bucket/key fields pending coordinated consumer migration.

Recovery considers records unchanged for more than ten minutes on the next scheduled cycle. Each cycle leases up to five eligible records, processes them concurrently, then repeats for at most twenty batches (100 records). Expiring leases and conditional writes prevent stale workers from overwriting newer progress. Database transactions finish before S3 or NATS operations begin. Missing originals receive three attempts; publication is quarantined after ten attempts while retaining the original and occurrence for investigation. Cleanup processes at most ten pages per cycle, resumes pagination, and deletes only ingestor-owned orphaned or failed assets.

An individual cleanup lookup or deletion failure leaves that asset for a later scan, increments the reconciliation error counter, and allows other assets and pages to proceed. If an asset's disposition cannot be checked, cleanup retains it. A listing failure stops that cycle and preserves the cursor for retry; cancellation still interrupts the work.

## Admission and telemetry

Redis atomically enforces a per-Profile fixed window; denied requests do not extend it. Defaults are 100 uploads per hour. Disabled or unavailable Redis uses bounded instance-local quota state. This fallback does not provide a fleet-wide quota; its metric drives a provisioned degradation alert.

Existing upload, storage, file-processing, and reconciliation metric names are preserved. Effect spans bridge request context into driven operations. Exporter connections and stalled telemetry responses have bounded cleanup, and telemetry failures do not alter application decisions.

## Running and upgrading

Upgrade existing deployments in this order:

1. Rebuild and restart **Media, Variant Generator, Color Extractor, and User**, including every consumer replica, with this revision of `@wallpaperdb/events`. Its upload-event schema accepts both retained legacy events and the new CloudEvents envelope, so these consumers can run alongside the old ingestor.
2. Drain and stop all old ingestor replicas before changing the database.
3. Run the migration and start the new ingestor:

```bash
make build PACKAGE=ingestor
make migrate PACKAGE=ingestor
make run PACKAGE=ingestor SCRIPT=start
```

Do not start the new ingestor until every upload-event consumer has been upgraded. Older consumer binaries reject the CloudEvents envelope and terminate those deliveries; upgrading them afterward does not trigger ordinary redelivery. Keep consumers on a version that accepts both formats while either can be retained or replayed.

`make migrate PACKAGE=ingestor` runs the standard Drizzle Kit migration command. A versioned SQL migration validates existing records, prepares legacy reservations before applying the broadened uniqueness constraint, and backfills recovery metadata and outbox entries. Drizzle records the migration in its journal so this data upgrade runs once.

The upgrade preserves committed originals and their states, resolves duplicate unfinished reservations deterministically, and marks interrupted, uncommitted records with incomplete metadata failed so clients can retry. Incomplete committed records stop migration for repair without becoming eligible for cleanup. Legacy stored uploads receive one stable outbox occurrence. The schema changes and data upgrade share a transaction: a failure rolls them back, allowing the migration to be rerun after repair. The context ADR records this deployment requirement and the event compatibility scope.

Non-test startup also requires `CLERK_SECRET_KEY` and `CLERK_PUBLISHABLE_KEY`. `HTTP_REQUEST_TIMEOUT_MS` bounds request receipt and socket inactivity (default two minutes).

Required connection settings are `DATABASE_URL`, `S3_ENDPOINT`, `S3_ACCESS_KEY_ID`, `S3_SECRET_ACCESS_KEY`, and `NATS_URL`. Bucket, region, stream, Redis, Clerk, telemetry, quota, and recovery interval settings are parsed by the composition root. `NODE_ENV=test` uses the test authentication adapter; deployed environments use Clerk.

## Verification

```bash
make check PACKAGE=ingestor
make test-integration PACKAGE=ingestor
make check-crap PACKAGE=ingestor CRAP_THRESHOLD=30
make run PACKAGE=ingestor SCRIPT=build:docker
make test-e2e PACKAGE=ingestor-e2e
```

Tests use observable conditions and controlled clocks instead of fixed sleeps. Their main guarantees are:

| Boundary | Covered behavior |
| --- | --- |
| Capabilities | Upload validation and ownership, deduplication, recovery after ambiguous storage or publication failure, finite retries, cleanup pagination, retention and isolated failures. |
| PostgreSQL | Concurrent reservations, metadata constraints, atomic stored-state/outbox writes, leases and stale workers, quarantine, legacy migration rollback, backfills and stable reruns. |
| Storage, events and Redis | Original bytes and object layout, absence versus outage, bounded stalled requests, real JetStream acknowledgements and deduplication, persisted event identity and trace context, shared quotas and bounded local fallback. |
| HTTP and lifecycle | Authentication order, multipart and response contracts, safe Problem Details, quota headers, deadlines, disconnect cancellation, graceful and forced shutdown, startup resource cleanup. |
| Workers and telemetry | Controlled scheduling, non-overlapping cycles, failure retry and scope shutdown; logs, traces and metrics reaching a local OTLP receiver, privacy and exporter cleanup. |
| Application and Docker | A representative upload through real PostgreSQL, storage and NATS; three Docker smoke tests for packaged startup, public endpoints, authentication rejection, upload/publication and duplicate identity. |

Remaining focused gaps are successful JPEG/WebP inspection and dimension boundaries, legacy intent-expiry selection, and proof that scheduled recovery starts through real application composition. Worker tests use a controlled ingestion service, so they do not detect a missing worker layer in the application. Recovery tests advance beyond the cutoff; they do not pin the change from five-minute stored-event retry eligibility before migration to the current ten minutes.

Docker tests use test authentication and disable Redis. Valid production Clerk authentication, deployed OTLP delivery, downstream consumers and multiple deployed ingestor replicas are outside that suite; real Redis and local OTLP contracts are tested separately. Atomicity, lease and replay tests cover specific failure scenarios, not process crashes at every external boundary.

Coverage reports include all ingestor source files. CRAP is a risk indicator alongside behavioral tests; the shared analyzer's missing callback/generator inventory is tracked in issue #217, so a numeric pass does not establish that every callback was assessed.
