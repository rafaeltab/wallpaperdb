# Own stable Assets and immutable Sources in Media

Accepted target direction in [#391's consolidated resolution](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6313111831), extended by [#256's generation and selection resolution](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525). Partially supersedes ADRs 0008/0009 and the Media/User/Ingestor lifecycle decisions. Final specifications and production implementation belong to #259.

The current context is the [Asset service](../../apps/asset/GLOSSARY.md). Historical Media decision names and links remain unchanged.

## Ownership and admission

Media owns the complete lifecycle of stable Assets containing immutable Source renditions. Applications retain their domain identities and references to Media-assigned Asset IDs. Changed bytes receive new Source IDs; accepted membership can change without changing the Asset ID. Configured Asset types select generic acceptance and delivery policies. No separate Publication identity or domain callback decides Source acceptance.

Applications authorize domain operations through durable commands in Media's language. Author Source operations use independent [Owner authentication](0010-authenticate-media-owners-through-configured-identity-providers.md). Media verifies mandatory admission rules before changing membership; supplementary inspection may follow without blocking unchanged delivery or weakening readiness/failure rules. Failed replacement retains prior membership. Assets may start empty, but Source management cannot empty them after first acceptance. [ADR 0011](0011-unlink-profile-pictures-before-asynchronous-media-deletion.md) defines terminal deletion and asynchronous Profile unlink.

Media owns Source storage mapping and cleanup, replacing ADR 0008's producer-issued byte identities, bucket layouts and producer-only deletion. Integration references still omit storage coordinates; Source bytes remain immutable and retired identities cannot be reused. Future layout changes require explicit treatment. No descriptor registry is introduced. The [clean rebuild](https://github.com/rafaeltab/wallpaperdb/issues/257#issuecomment-5940357833) needs no historical layout migration or compatibility implementation; #259 specifies the new layout.

The Media-local ADR's immutable wallpaper targets and read-only Source credentials describe the old implementation. Durable acceptance, replay, outbox and recovery obligations remain. Media owns per-Asset-type private-evidence retention, preserving the 30-day Profile picture default and recorded expiries under [ADR 0011](0011-unlink-profile-pictures-before-asynchronous-media-deletion.md). Temporary-input expiry and terminal replay fences remain separate obligations.

## Profile pictures

Media retains and validates the processed square crop as an immutable Source. Web selects the crop; Media processes private temporary HDR input. Output no longer returns through Web for upload to User storage. The SDR browser editor still supplies its processed crop to Media. User owns the Profile reference and workflow. Ordinary replacement retains the Asset ID and replaces the complete Source set so other format/range requests cannot select the previous picture.

Replacement checks the expected Source-set revision. A competing picture mutation preserves the winning set and requires explicit retry of the retained edit. User checks Profile concurrency for initial attachment/removal and fences stale confirmations and results against current intent. Unrelated Biography changes no longer conflict with ordinary replacement, superseding #243's broad Profile-version coupling while preserving conflict/retry behavior.

This replaces ADR 0009's output transfer, User storage/validation authority and exclusion of processed output from Media's catalog. Preserve [#270's requirements](https://github.com/rafaeltab/wallpaperdb/issues/270#issuecomment-5902621514) for crop, configured dimensions/bytes, HDR routing, motion, alpha, sanitation and canonical validation. The crop is an intake Source, not a Materialized rendition of unedited input. This ownership change qualifies no new HDR path.

## Rendition delivery

Delivery cannot enlarge an accepted Source. [Intake may enlarge a small crop](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312425664) to the configured processed picture size before acceptance under #243/#270. Dimension preservation refers to the Default Source. If no eligible Source can satisfy that size, reject the request.

[Omitted dimensions inherit](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312526402). Both inherited axes use the selected Source's native displayed dimensions; one numeric axis derives the other proportionally. Concrete dimensions must match the Source's aspect ratio unless fit is explicit. Inheritance refers to the Source, never a smaller Materialized input reused for processing.

The [#256 fit amendment](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525) replaces the old default `contain` and its no-padding meaning:

- `inside` scales proportionally within bounds without padding.
- `contain` preserves proportions within an exact canvas, with centered opaque-black padding by default. Explicit colors and transparency require qualified output support and cannot waive Source-alpha preservation.
- `cover` crops proportionally; `fill` stretches when ratios differ. Both require qualification and obey no enlargement.
- Omitted fit rejects aspect-ratio changes for both HTTP delivery and configured materialization. Only unavoidable integer-pixel rounding is allowed. #259 defines and tests the deterministic rounding rule, sizing tables, schema and bounds. The 3% Source-admission and 5% browse tolerances do not apply to delivery sizing.

[Input selection](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525) considers active accepted Sources and usable Materialized inputs with Source provenance. First require faithful satisfaction of the complete request under current qualification, lifecycle and preservation constraints. Explicit SDR prefers authored SDR Sources and qualifying descendants, then embedded authored SDR bases and descendants, then qualified conversion. Within the eligible class, choose the smallest adequate actual displayed pixel area after accounting for fit, without enlarging any input. At equal resolution, prefer an exact Source no-op, then an exact stored output, then least processing, then stable identity. A Source no-op returns exact bytes. Adequate dimensions cannot recover content, motion, range or depth discarded by prior processing.

When both dimensions inherit, use the eligible Default Source within the required precedence class, otherwise that class's largest eligible Source. Its native dimensions set the target and all inherited characteristics refer to it. Stored intermediates cannot reduce the target. If stored output is missing or unsuitable, try another faithful output, then generate from the selected Source under current limits. Arbitrary on-request results are not persisted. Existing readiness, unsupported-rendition and temporary-failure responses apply when no path succeeds; missing inventory does not withdraw discovery eligibility.

## Materialization

[Per-Asset-type configuration](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525) uses `materialization.renditions: RenditionRequest[]`, sharing HTTP request values, defaults and sizing semantics. Resolve each entry against accepted Sources using the same selection policy, rather than generating from every Source. Entries express desired outputs, not proof of stored bytes or encoded characteristics; eligibility depends on actual Source facts, qualification and limits.

Ahead-of-time outputs must preserve the supplying Source's aspect ratio and complete frame, without cropping, padding or stretching. A mismatched configured ratio is ineligible even with explicit fit. A fit that changes nothing at matching ratios remains eligible. Mismatched requests may still qualify for on-request delivery; later crops use the same qualified processing semantics as direct Source processing. #259 selects initial request arrays and measured work, retaining #263's full-resolution materialized SDR wallpaper requirement. Earlier illustrative lists are not defaults.

Generation starts directly from Sources and preserves the highest available quality for reusable intermediates without cumulative degradation. This does not require a lossless codec mode for every format. Generation and reuse must qualify against direct Source processing; maximum encoder quality alone does not prove faithful re-encoding. #259 defines settings and measured acceptance, without a new public quality selector or relaxed HDR qualification. Optional persistence of arbitrary requested results remains deferred.

Immutable output identities bind Source provenance, resolved processing settings and encoding revision. Changes to those inputs create new identities; retries reuse committed results. Do not overwrite bytes or replace actual facts with requested settings. Reuse requires durable bytes and matching facts, with replay-safe acceptance and external steps. Membership, preservation, policy and terminal deletion fence stale work and reuse independently of private retention. #259 specifies normalization, identity encoding, storage layout and revision activation.

Accepted Source/default changes and newly usable inspection facts trigger asynchronous consideration of configured targets. Configuration/support changes update eligibility and desired targets but cannot automatically start population-wide generation. Applying additions, changes or retirement to existing Assets requires an explicit manual, pausable operation with bounded load and durable progress, preventing configuration edits from exhausting capacity. Pause stops new work, lets bounded in-flight work finish and saves progress. Safe outputs remain available pending replacement; lifecycle or qualification changes exclude unsafe outputs immediately. Asynchronous cleanup cannot remove active Sources or current outputs. #259 defines controls, budgets, restart-safe pause/resume and stale-work handling while reserving public delivery capacity. This manages the new system; it is not historical migration or backfill.

## Public integration and admission defaults

The [public announcement](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6251166579) is a change-driven complete snapshot of Asset ID, revision and compact jointly faithful output capabilities, sizing constraints and valid native coverage. It excludes Owner, Default Source, Source identities/membership, storage and diagnostics. Qualified outputs count before materialization. Processing-support changes can revise the snapshot, deletion empties it, and temporary outages do not clear it. Browse size/shape uses native coverage; categorical filters describe faithful outputs.

Public requests use one Asset URL with query selectors, including format. Exact Source access remains owner-protected. Save names and extensions identify the actual encoding, including preserved/inherited formats and no-op bytes. HTTP validators must identify selected bytes, not only the stable Asset ID, so representation-changing Source/default/processing updates cannot yield an incorrect 304. No new cache policy or mechanism is selected; #259 verifies validators and browser save names.

[Wallpaper still-image defaults](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312814842) are inclusive 50 MiB encoded bytes, 100,000,000 pixels and 20,000 pixels per displayed axis, configurable by Asset type. Similar aspect ratio compares a candidate with all active Sources, including the replaced Source, after orientation: `largestRatio / smallestRatio - 1 <= 0.03`. Policy changes apply prospectively; acceptance rechecks effective policy and membership. These defaults neither broaden qualified admission classes nor settle animation/native resource budgets. Profile pictures retain 512-square, 5 MiB processed and 50 MiB temporary-HDR defaults. #259 specifies resource/payload limits and configuration activation.

Wallpaper color measurements retain the first Default Source's provenance for the Asset's lifetime, despite later default changes, replacement or withdrawal. Preserve those measurements durably; ordinary per-type Source-byte cleanup cannot authorize re-extraction from another image. This avoids repeated color changes, while accepting initial color/display divergence and substantial replacement. No similarity enforcement or permanent private-byte hold is selected, and the color algorithm is unchanged. [Visual-continuity research #414](https://github.com/rafaeltab/wallpaperdb/issues/414) does not block the initial lifecycle.
