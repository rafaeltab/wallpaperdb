# Own stable Assets and immutable Sources in Media

Status: accepted target direction in [#391's consolidated resolution](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6313111831). Partially supersedes ADRs 0008 and 0009 and the Media/User/Ingestor local lifecycle clauses. Generation/selection remains #256; final specifications and production implementation remain #259 work.

Media owns the complete lifecycle of a stable Asset containing immutable Source renditions. Applications retain their domain identities and references to Media-assigned Asset IDs. Changed bytes receive new Source IDs; accepted membership can change without changing the Asset ID. This replaces producer-owned immutable Asset identity and byte lifecycle, and keeps reusable technical acceptance and delivery policy inside Media. Configured Asset types select generic policies; no separate Publication identity or domain callback decides Source acceptance.

Applications authorize their domain operations through durable commands in Media's language. Author Source operations use the independent Owner authentication described in [ADR 0010](0010-authenticate-media-owners-through-configured-identity-providers.md). Media verifies mandatory admission rules before changing accepted membership. Supplementary inspection can continue afterward, preserving unchanged delivery and the conservative readiness/failure contract. Failed replacement retains prior membership. An Asset may start empty; after first acceptance, Source management cannot empty it. [ADR 0011](0011-unlink-profile-pictures-before-asynchronous-media-deletion.md) records terminal deletion and asynchronous Profile unlink.

Media retains the processed, cropped square Profile picture as its accepted immutable Source. Web selects the crop; Media processes temporary HDR input and validates the cropped output under the Profile picture type policy. The raw input remains private and temporary, and the accepted output no longer returns through Web for upload into User-owned storage. The existing SDR browser-editor path still produces a processed crop for admission into Media. User owns the Profile reference and its workflow. Ordinary picture replacement retains the Asset ID and switches the complete accepted Source set, preventing other format/range requests from selecting the previous picture.

Media checks the expected revision of that accepted Source set before replacing a picture. A competing picture mutation preserves the winning accepted set and requires explicit retry of the retained edit. User checks Profile concurrency for initial attachment/removal, but unrelated Biography changes no longer conflict with ordinary Source replacement. This replaces #243's broad Profile-version coupling for that operation while preserving its conflict/retry behavior. User's durable workflow fences stale confirmations and results against current attachment/removal intent.

This replaces ADR 0009's output-byte transfer, User storage/validation authority and exclusion of processed output from Media's catalog. Native processing remains in Media. Preserve the [#270 product requirements](https://github.com/rafaeltab/wallpaperdb/issues/270#issuecomment-5902621514), including crop, configured dimensions/bytes, HDR routing, motion, alpha, sanitation and canonical validation. The cropped output is a Source accepted through intake, not a Materialized rendition of the unedited input. No new HDR path is qualified by this ownership change.

ADR 0008's producer-issued byte identities, producer bucket layouts and producer-only deletion responsibilities no longer define new Media Assets. Media owns source storage mapping and cleanup. Preserve logical references without storage coordinates in integration contracts, immutable Source bytes, non-reuse of retired identities, and explicit treatment of future layout changes. This decision introduces no descriptor registry. The [clean rebuild](https://github.com/rafaeltab/wallpaperdb/issues/257#issuecomment-5940357833) requires no historical layout migration or compatibility implementation; #259 owns the new layout specification.

The Media-local ADR's immutable wallpaper targets, read-only source credentials and producer-owned deletion describe the existing implementation. In the target, immutable bytes belong to Sources while Asset membership and delivery state change under Media authority. Its durable acceptance, replay, outbox and recovery obligations remain. Media owns private-evidence retention and cleanup under per-Asset-type configuration, preserving the existing 30-day Profile picture default and recorded expiries as described in [ADR 0011](0011-unlink-profile-pictures-before-asynchronous-media-deletion.md). Temporary input expiry and terminal replay fences are separate obligations.

The [confirmed public announcement](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6251166579) is a change-driven complete snapshot of Asset ID, revision and compact jointly faithful output capabilities with sizing constraints and valid native coverage. It excludes Owner, Default Source, Source identities/membership, storage and diagnostics. Qualified outputs count before materialization; processing-support changes can revise the snapshot, deletion empties it, and temporary outages do not clear it. Native size/shape coverage remains required for browsing, while categorical filters describe faithful outputs.

Rendition delivery cannot enlarge an accepted Source. The [confirmed intake distinction](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312425664) retains #243/#270's small-crop authoring behavior, which may enlarge a crop to the configured processed picture size before acceptance. Explicit dimension preserve refers to the Default Source; if no eligible sufficiently large Source can satisfy the preserved size, the request fails rather than enlarging bytes or silently weakening preservation.

The [confirmed dimension rule](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312526402) makes omission equivalent to inherit. Both inherited axes use the selected Source's native displayed dimensions; one numeric axis derives the inherited axis proportionally. Two concrete constraints apply the requested fit under the no-enlargement rule. Inheritance refers to the Source, not a smaller Materialized input selected for reuse. Concrete sizing tables, schema and bounds remain #259; generation and safe input/source ranking remain #256.

Public requests use one Asset URL with query selectors, including format, while exact Source access remains owner-protected. Returned filenames and extensions identify the actual encoding, including preserved/inherited formats and no-op bytes. An Asset URL can change representation under the same identity, so HTTP validation must distinguish its selected bytes from immutable Source identity. A representation-changing Source/default/processing update cannot receive an incorrect 304 based only on the stable Asset ID. No new caching mechanism or cache policy is selected; #259 must verify validators and actual browser save names.

The [selected wallpaper still-image defaults](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312814842) are inclusive 50 MiB encoded bytes, 100,000,000 pixels and 20,000 pixels per displayed axis. Media makes them operator-configurable by Asset type. Similar aspect ratio compares the candidate with all active Sources, including the replaced Source, using `largestRatio / smallestRatio - 1 <= 0.03` after orientation. Policy changes apply prospectively and acceptance rechecks the effective policy with current membership. These defaults do not broaden Source admission beyond selected qualified classes or settle animation/native resource budgets. Profile pictures retain their independently selected 512-square, 5 MiB processed and 50 MiB temporary-HDR defaults; #259 sizes resource and payload limits and specifies configuration activation.

Wallpaper color measurements use the first Default Source and retain that provenance for the Asset's lifetime. Later default changes, replacements or withdrawals do not automatically change the measurements. This avoids repeated color-information changes and anticipates future visual continuity, but the user explicitly accepts initial divergence while substantial replacements remain permitted. Neither similarity enforcement nor a permanent private-byte hold is selected. Preserve the first measurements durably; ordinary Source byte retention remains per type, and purging those bytes does not authorize silently re-extracting a different image. The color algorithm is unchanged. Visual-continuity research is deferred to [#414](https://github.com/rafaeltab/wallpaperdb/issues/414), without blocking the initial lifecycle.
