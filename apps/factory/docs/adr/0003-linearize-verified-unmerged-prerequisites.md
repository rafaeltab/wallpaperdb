# Linearize verified unmerged prerequisites

Waiting for every prerequisite to merge would make the maintainer a synchronous dependency gate. Serializing an entire dependency graph would avoid joins but sacrifice the parallel work required by [spec #571](https://github.com/rafaeltab/wallpaperdb/issues/571). The factory instead admits dependents on verified unmerged prerequisite code and linearizes parallel branches when their changes must be combined.

Restacking replays issue-specific layers onto a verified containing boundary without merge commits. Original parent boundaries and review provenance remain available so landed changes are not replayed as open work. Ref updates, PR targets and stack grouping recover as separate durable steps; expected-head leases and affected-writer coordination do not make them one atomic operation. See the [prerequisite checks](../../src/adapters/github/prerequisites.ts), [landed prerequisite verification](../../src/adapters/github/landed-prerequisite.ts) and [join and maintenance adapter](../../src/adapters/github/joins.ts).

The verification trade-off is deliberate: conflict-free restacks and agent-classified simple conflict resolutions require current-tree CI; substantial conflict resolutions also require independent review. Carrying original review provenance is not a claim of direct review of the rewritten commit. Unknown classifications and incomplete publication or verification keep dependents blocked. This avoids restarting every review solely because a mechanical replay changed commit identities, while preserving review for functional conflict changes. See the [restack policy](../../src/capabilities/restack/implementation.ts) and [recovery adapter](../../src/adapters/t3/restack.ts).

The same policy maintains descendants after manual merges. User-requested changes to already ready prerequisites after downstream work has started remain a manual recovery case; this decision does not authorize overwriting those edits or automatically repairing every external divergence.
