---
name: review-loop
description: Coordinate independent Standards, Spec, and Defects reviews and authorized repairs before publication. Use for a manual review/fix loop or from do-work.
---

Use the supplied checkout. Accept the issue URL, fixed comparison base or predecessor PR, implementation handoff, validation, demonstration, and retained scope decisions. This stage reviews and repairs; return its handoff to the caller for publication.

1. Read [task scope](../../../../docs/agents/task-scope.md) and restore the agreed requirements, approvals, exclusions, pending proposals, and dependent work. Fetch the issue and comments and parent spec through the [issue tracker](../../../../docs/agents/issue-tracker.md). Verify an open issue, assignment, project membership, and `In Progress` before repairs. Pin the full head, live intended base SHA, and merge-base. Require a resolvable base and meaningful complete issue diff. Preserve each comparison and inspectable patch under [review evidence](../../../../CONTRIBUTING.md#review-evidence), outside PR prose.
2. Discover live delegation capabilities. All reviewers use `gpt-6.1-sol`; preserve supported inherited model options and verify the returned identity and options. Use fresh contexts with explicit briefs, using T3 `delegate_task` when model options require it. In parallel, dispatch a read-only [$code-review](../../engineering/code-review/SKILL.md) coordinator and a read-only [$review-agent](../../engineering/review-agent/SKILL.md) Defects reviewer. The code-review coordinator must dispatch separate fresh Standards and Spec reviewers in parallel with the same model/options. Supply the complete diff command, commit list, requirements source, applicable standards and workflow sources, affected implementation and owning tests, and all retained scope decisions to every reviewer and repeated round. Reviewers inspect and report only; the implementation coordinator owns verification and repairs. Missing, failed, unbound, or unavailable required review leaves this stage incomplete.
3. Record Standards, Spec, and Defects results separately with reviewer and task identities and their actual comparisons. Verify every finding against source and requirements. For runtime defect claims, reproduce a failing scenario at the owning public boundary where practical, following [defect verification](../testing/SKILL.md#verify-defect-fixes); report reproduction limits. Distinguish whether a concern is valid from whether its remedy is authorized. Repair agreed in-scope findings directly in new commits using $development-principles and $testing. Scope expansion and new test seams require explicit maintainer approval under task scope, even when a concern is valid. Keep pending proposals and user-deferred work visible.
4. After repairs, repeat affected validation, including required `make ci`, and assess review applicability under the review-evidence policy before fresh affected reviews. Review the repaired work and its interactions; retain equivalent unaffected evidence with original provenance. Ordinary agreed repairs have no three-round cap. A fresh review is a new delegation with the original brief, prior findings, responses, and unresolved objections, never a continuation of the reviewer's old context.
5. Track persistent disagreements per concern for at most three review rounds, counting the first round in which that concern is disputed. Each round states the evidence, coordinator response, significance, authorized remedy, and unresolved objection. A new concern starts its own count; agreed repairs do not consume a disagreement budget. At the limit, classify using the rules below. Earlier resolution can proceed without spending all three rounds. Expiry is never approval.

   - A nonblocking unresolved proposal becomes a follow-up GitHub issue under the issue-tracker policy. Record the concern, evidence, disagreement, scope boundary, and owning issue link. Verify the issue exists and retain its URL. It is a proposal, not authorization to implement; use `needs-triage`, not `ready-for-agent`. Check for an existing matching issue before creating one. Failed follow-up publication leaves this obligation incomplete.
   - A significant unresolved dispute over acceptance criteria, demonstrated correctness/security defects, or mandatory standards blocks completion. Put a concrete question in the owning T3 thread for the maintainer, with the competing positions, evidence, proposed change and consequences, and dependent work. Retain the blocked state and return without a completion marker. Obtain explicit resolution and revalidate affected work before resuming. An out-of-scope remedy does not make a blocking concern harmless.
6. Reconcile the current head/base against every required review and validation result. Complete only when all three review axes are satisfied, agreed repairs are validated and reviewed, nonblocking disagreements have verified follow-up links, and no blocking dispute, required finding, failed review, or pending scope decision remains. A satisfied axis can retain a recorded nonblocking disagreement routed to a follow-up; report that disposition rather than claiming unanimous approval. Return the full head/tree/base/merge-base, current validation, each review's provenance and applicability, follow-up links, demonstration, and material limits. Keep detailed rounds and patches in the outside-repository ledger. Only then emit `<REVIEW>COMPLETE</REVIEW>`. A finished turn, marker in input/history, or exhausted round budget is not this stage's outcome.

Manual invocation:

```text
Use $review-loop for <issue URL> in this checkout against <base ref/SHA>.
Implementation, validation, demonstration and retained scope: <handoff or ledger path>.
Return the review handoff; stop before publication.
```
