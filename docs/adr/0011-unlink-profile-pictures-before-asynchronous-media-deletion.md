# Unlink Profile pictures before asynchronous Media deletion

Status: accepted for the target architecture in [#391's removal resolution](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6195238800). Partially supersedes [ADR 0004](0004-authorize-profile-picture-delivery-at-origin.md). Implementation and final specification remain outside this planning decision.

User clears the Profile's picture reference and durably records the request to delete its Media Asset in the same local transaction. It returns success without waiting for Media. The generated avatar represents the absence of a picture and needs no Media Asset. Media owns the Asset lifecycle and executes deletion; User authorizes the Profile operation. This lets Profile removal succeed while Media is unavailable, at the cost of allowing an already-known Asset URL to work until Media processes deletion. Public Profile projections and existing views can temporarily retain the prior reference.

Media enforces delivery against its own authoritative Asset lifecycle. Once it accepts deletion into that lifecycle, it denies further delivery and source operations. Physical cleanup can finish asynchronously. This replaces ADR 0004's immediate origin-denial guarantee and synchronous User availability callback. It does not introduce a new cache policy or promise to recall cached or downloaded copies.

The [confirmed retention transfer](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6250853974) makes Media responsible for private evidence and cleanup under configuration selected by Asset type. Preserve the existing 30-day Profile picture default and recorded expiry dates. Configuration changes or replay cannot reset an existing expiry. Private retention neither permits public delivery nor makes deletion reversible, and temporary raw editor input has its own bounded lifetime. Terminal replay fences remain valid independently of image-byte expiry.

Deletion is terminal. Late or replayed uploads, inspection and processing results cannot resurrect an Asset. A new picture after removal receives a fresh Asset ID, while an ordinary accepted picture replacement retains its Asset ID and switches the complete Source set. User retains durable responsibility for the deletion request, which targets the removed Asset rather than whichever picture the Profile might hold later. No transaction spans User, Media and object storage.
