# Authenticate Media owners through configured identity providers

Status: accepted target architecture in [#391's consolidated resolution](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6313111831). The user selected direct author verification after the [real Clerk authorization proof](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6176867112); later discussion confirmed the distinct broker-authenticated application boundary. Production implementation and remaining validation belong to #259.

Media directly verifies author credentials from configured identity providers. Its authentication adapter maps the verified subject into a configured Owner namespace. Media's domain compares that namespace and opaque subject with the Asset's Owner reference for every protected author operation. This supports direct author requests without an application-issued token exchange or WallpaperDB-specific identity policy in Media. Clerk is the first adapter integration.

Application creation authority is separate from author identity. An independently authenticated application requests an allowed Asset type, supplies an opaque Owner subject and Application reference, and receives Media's assigned Asset ID with the Application reference echoed unchanged. Trusted configuration supplies the application's permitted Owner namespace and types. Author request fields cannot assign ownership, and a service credential cannot act as an author. Creation continues through durable commands; the proof's synchronous HTTP transport does not replace that requirement.

The [confirmed application trust model](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6195774406) uses durable NATS creation/deletion commands with separate application credentials and exclusive broker-enforced publish permissions. Media maps the protected ingress channel to a stable application identity, then enforces its allowed operations, types and Owner namespace. Body fields, client names and CloudEvents source cannot establish that identity. Media binds each Asset to its Creating application; only that application may request full deletion under configured permissions. Credential rotation does not change application identity. This trusts the broker and its permission configuration rather than requiring a synchronous caller check or queued author-session token.

Commands and result events use Media's language and a shared generic contract. For example, CreateAsset and DeleteAsset request operations; Media events announce their outcomes. Wallpaper and User translate their own domain actions into that contract, with opaque Application references. Per-application subject routing does not introduce application-specific Media schemas. Final spellings and schemas remain specification work.

Creation command identity is scoped to the authenticated application. Replaying the same command and payload returns its original Asset ID; conflicting reuse fails and cannot reassign ownership or type. A new command may reuse an opaque Application reference to create a fresh Asset after removal. The reference is not a global Asset uniqueness key. Terminal deletion is not undone by replay of an old creation command.

The [20-check proof and reproduction instructions](https://github.com/rafaeltab/wallpaperdb/tree/4323cf1c/packages/auth/prototypes/clerk-owner-proof) establish owner access and non-owner denial with real Clerk development accounts and signed session tokens. Neither the application nor Media needed Clerk's administrative key. The fixture runner used that key only to provision disposable accounts and sessions.

Production validation must establish the actual token profile, issuer and signature validation, expiry, applicable audience and authorized-party checks, key rotation and failure behavior. The proof's development-session tokens omitted audience and authorized-party claims. It did not qualify browser password sign-in, cross-provider mapping, live revocation or durable command transport. The final configuration schema and transport credential provisioning remain specification work, without weakening the selected trust separation or owner-only authorization.

Real-broker validation must separately prove publish isolation, application-to-Asset deletion checks, spoof rejection, replay safety and stable application identity through credential rotation. Subject permissions must cover all ingress and replay paths and prevent application access to broker administration that could bypass them. The checked-in unauthenticated Compose broker and URL/client-name connections do not implement this target trust model.

An Owner reference identifies an author, whereas ADR 0008's historical `AssetReference.owner` identifies a byte-producing application. They are different contracts. [ADR 0001](0001-use-clerk-user-ids-as-profile-ids.md) still makes Clerk user IDs WallpaperDB Profile IDs; Media treats their subject values as opaque. This authentication decision does not itself replace picture availability, storage or byte transfer. [ADR 0011](0011-unlink-profile-pictures-before-asynchronous-media-deletion.md) and [ADR 0012](0012-own-stable-assets-and-immutable-sources-in-media.md) explicitly reconcile those clauses.
