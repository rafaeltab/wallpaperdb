# Factory host operations

## Host prerequisites

The host's user manager must remain available after logout. Verify that lingering is enabled before activation; changes to host policy belong to the supervising operator.

Retain the active release's pinned Node installation, private configuration and dedicated user unit until recovery has been verified. The [installer](scripts/install.ts) records the executable path; moving or removing that installation can break an otherwise intact release.

Completion verification requires the structured T3 MCP connection configured in the [composition root](src/composition/implementation.ts). CLI transcript output alone cannot establish descendant inactivity or registered waits. Missing connection or activity evidence leaves completion unverified.

## Background T3 observation

The [composition configuration](src/composition/implementation.ts) derives the WebSocket origin from `FACTORY_T3_MCP_ENDPOINT`. Set `FACTORY_T3_OBSERVER_ORIGIN` when it differs. `FACTORY_T3_AUTH_BASE_DIR` selects the configured CLI's authentication directory when its default is unsuitable. Keep the MCP-only credential separate from the normal read-only bearer session used by WebSocket observation.

The [credential adapter](src/adapters/t3/observer-credential.ts) issues a dedicated `orchestration:read` session through the supported T3 CLI. It stores the session privately at `observer/session` below `FACTORY_STATE`, reuses it after restart, replaces it before expiration or after authentication rejection, and reconnects subscriptions on replacement. The directory is mode 0700 and the session is mode 0600. Preserve these permissions and include the private session in stopped-state backups. Do not publish it in logs or issue evidence. Provisioning failures retain observations and claims and retry in the background.

The [observer](src/adapters/t3/observations.ts) maintains shared thread metadata and detailed managed-thread activity. The installed runtime must support authenticated protocol-v2 shell/thread subscriptions, cursor replay, synchronization markers, archived shell snapshots and thread-family metadata. Bounded-history recovery uses the supported full managed-thread HTTP snapshot endpoint through the [snapshot adapter](src/adapters/t3/complete-snapshot.ts), then resumes from its cursor and waits for synchronization. When unchanged shell updates are suppressed, background family confirmation must cover the current detail cursors and match retained membership and safety facts before proving inactivity. Initial synchronization and recovery may read full managed snapshots. Routine decisions use retained local facts; disconnects do not release occupied capacity, and unavailable completion evidence remains unverified. The separate [inventory worker](src/composition/refresh.ts) refreshes lightweight link metadata immediately and every 15 minutes, independently of planning.

## Execution settings

Use the Project canvas Settings panel to save the factory-wide model, reasoning effort, Standard/Fast mode and permission level without restarting. Choices come from the configured T3/Codex installation; Fast requests Codex priority service independently of effort. Permission choices respect the MCP client's ceiling and provider restrictions. Supervised permission modes can leave unattended work waiting for a human. Inherited/default values preserve T3 defaults, whose effective values may be unknown. See the [Settings controls](frontend/src/canvas/execution-controls.tsx) and [T3 translation](src/adapters/t3/execution-settings.ts).

The scheduler captures execution settings at admission. Planner attempts and recovery operations capture them before claiming a launch. Later stages, uncertain-launch reconciliation, continuations and implementation retries retain the captured settings, including permissions. A new admission or new planner/recovery operation uses the latest saved settings; changing settings never restarts an existing worker or consumes another admission. Changing an existing execution's permissions requires a separate execution context, not a factory configuration edit. Job and planner details distinguish captured settings from observed T3 selections, inherited defaults and unknown values. See the [scheduler](src/capabilities/plan/scheduler.ts), [planner](src/adapters/t3/planner.ts) and [recovery adapter](src/adapters/t3/restack.ts).

Existing records without execution settings retain the legacy model and inherited options and permissions. Saving unrelated scheduling controls preserves the current execution settings. Configured launches require the authenticated MCP connection described above and use structured launch controls; unavailable combinations fail without substitution. Model validation searches for an exact requested model when T3 omits it from the default list. Capability preflight completes before durable launch claims for planners, workers, fresh implementation retries and recovery. A discovery failure without a launch request leaves preparation retryable; uncertain outcomes after sending retain their claims for reconciliation. See the [job launch ordering](src/capabilities/job/implementation.ts). Settings persist in the existing revisioned [JSON records](src/platform/record-schemas.ts) in SQLite, so rollback needs a reader compatible with those additional fields.

## Upgrade and recovery

Stop all writers and back up the entire state directory, including database journals, before migration or restoration. Retain the previous release, unit and private configuration. Verify copied production state through the [migration-only entry point](src/main.ts). Starting a full factory against that copy can contact retained external workers even while admissions are paused. Development and demonstrations need isolated state and controlled external endpoints.

The state-response protocol preserves existing stage records, claims and provider observations. An idle old-format agent receives one migration instruction to verify current state using the versioned contract. The factory never accepts legacy success. A failed migration requires maintainer intervention. Reconciliation claims retain attempts and the pending instruction atomically in the existing SQLite journal. These additive [record fields](src/platform/record-schemas.ts) require a compatible release for rollback. Never remove records or restore stale JSON to make an older release start.

Configure the per-job Agent reconciliation attempt limit with `FACTORY_AGENT_RECONCILIATION_LIMIT`, default three, in the [composition configuration](src/composition/implementation.ts). Changing stages or restarting the service preserves consumed attempts. A lost send response retains its claim and is not resent. Exhausted budgets, failed migrations and dependency-cycle decisions appear as durable manual recovery. Dependency recovery survives restart and invalidates older handback authority; explicit reset revalidates corrected current state. An operator can explicitly reset through the [job resume endpoint](src/http/implementation.ts) using the exact job, stage index, owning run and control revision with `resetReconciliation: true`. This preserves claims and history and rechecks current state; it cannot resume a cancelled job. Deployment and live operator recovery remain supervisor actions.

After the factory performs external work newer than a backup, restoring that backup can discard claims for work that still exists. Preserve the current state and use a compatible release. Restore an older backup only after the supervising operator reconciles every subsequent external effect. After JSON-to-SQLite migration, legacy JSON files are historical originals, not a current backup. Do not delete records or fields to make an older release accept newer state.

The [planner journal reader](src/adapters/t3/planner-state.ts) validates appended immutable revisions once per reader lifetime and retains their revision indexes. Each lookup rereads and validates its selected record; it retains no historical context payloads in memory. Restart validates the history again. Replacing or editing existing journal revisions while a writer is running violates the immutable journal contract; stop writers before recovery.

The installed service's lock does not protect against direct development launches. Keep those launches away from the service's state directory.

An authorized live branch trial against retained execution state must stop the main writer completely and acquire its exact service lock. Preserve the pinned installation, unit and private configuration, back up the entire stopped state, and first verify the exact returning release against isolated copies using migration-only and read validation. Do not run a full factory on a copied production journal. At handback, stop the branch writer and resume the unchanged pinned service against the newest authoritative state. Verify retained claims and launches; never restore a pre-trial backup over external work created during the trial.

## Stage reconciliation

A supported state response can report incomplete work. False required checks keep implementation pending; they do not mean the response format is obsolete or that review or publication has happened. The [receipt adapter](src/adapters/t3/stages.ts) distinguishes incomplete checks, unsupported or mismatched responses, checkout/comparison failures and missing review/publication evidence. The [reconciliation policy](src/capabilities/job/reconciliation.ts) retains that reason with the bounded same-stage instruction across restart.

Implementation reconciliation continues the existing $implement workflow and local validation. No PR or independent-review completion is expected at that stage. Accepted implementation advances to $review-loop, and accepted reviewed state advances to $publish-pr. Review workflows may use their required independent read-only reviewers; the prohibition on replacement implementation workers and worktrees does not prohibit those reviewers. Publication reuses an intended PR when present and may create the first PR when publication prerequisites are satisfied. A genuine unrelated validation or scope blocker requires an accurate maintainer question, not a fabricated successful state or an invented PR requirement.

The existing cancellation, parked-question, uncertainty and reconciliation-budget guards still apply. Reconciliation does not resume cancelled work, change admission controls, release admission, or merge work. New instructions carry an optional reason in the existing journal records; rollback requires a compatible reader as described above.

## Operator-attested recovery

A missing thread search result cannot prove that a launch failed. Retiring an uncertain planner claim requires explicit server evidence of non-launch. For the supported T3 `-32602` rejection recovery, the supervising operator must stop the service, retain a complete backup and supply the evidence reference and timestamp to the [reconciliation command](src/main.ts). Deployment and this attestation remain supervisor actions.

## Monitoring

Provision the [factory alert rules](../../infra/grafana/provisioning/alerting/factory.yaml) in the actual monitoring installation and verify its notification routing. Repository configuration alone does not prove deployment or delivery. Use controlled checks without real notifications unless authorized, and preserve unrelated monitoring services.

An intentionally unmonitored factory needs its missing-signal alert disabled in that installation. Missing data cannot distinguish that choice from process loss.

## GitHub project membership

The WallpaperDB project's auto-add workflow must continue adding every repository issue and PR. This external workflow is a prerequisite for [project-based metadata discovery](src/adapters/github/project-sync.ts).

Dependency responses use the shared versioned agent protocol. The [job handback transition](src/capabilities/job/handback.ts) validates prerequisites before instructing the existing idle agent to record GitHub blockers, close its abandoned PR and restore the open issue to Planned. Invalid identities use the reconciliation budget; cycles require manual recovery. Missing authoritative verification retains ownership rather than assuming an uncertain write failed. The [scheduler](src/capabilities/plan/scheduler.ts) releases admission and allowance together only after verified handback, retaining abandoned admission evidence. The [guarded persistence operation](src/adapters/store/handback.ts) checks the exact owning job identity and the uncancelled revision that verified handback in the same SQLite transaction as release. The transaction also marks the old journal terminal, so cancellation or supersession invalidates stale observations and old in-flight work cannot authorize another instruction after refund. Informational status rereads cannot replace the verified revision. Future ordinary pickup obeys dependencies and capacity and uses a fresh job and journal generation. Cancellation alone does not refund allowance. Preserve all generations and their threads, worktrees and branches during recovery.

## Rebase comparisons

A reported newer main SHA is not authority. The [comparison verifier](src/adapters/t3/comparison.ts) checks GitHub's authenticated main containment, the original allowed boundary and the actual issue-only comparison. Unexpected feature bases and omitted prepared prerequisites require manual recovery. Preserve the original owning worktree, PR identities, immutable stage records and review evidence when investigating; do not change the retained base to make a response pass.

The [join adapter](src/adapters/github/joins.ts) first attempts Git replay at the selected boundary, retaining each original issue comparison. Different authenticated main roots can normalize onto newer main when their required parents are covered by that boundary or the factory-selected layers. Missing parent coverage blocks reconstruction. Each rewritten head requires current local checks and fresh independent review before guarded publication, then independent hosted CI. The [recovery adapter](src/adapters/t3/restack.ts) uses the shared response contract and checks the exact target and complete descendant inactivity. Unknown publication outcomes retain their claims for reconciliation; dependents remain withheld until metadata, heads and verification agree. An unchanged PR head and target do not need CI reruns merely because main advances.

Idle inconsistent restack responses enter durable reconciliation in the same owning recovery worker. The [recovery journal](src/adapters/t3/restack-reconciliation.ts) reserves attempts before delivery, using the existing agent reconciliation limit from the [composition configuration](src/composition/implementation.ts). The budget spans resolution and independent review; old-format responses receive one separate migration. Exhaustion or failed migration requires manual intervention. Recursive inactivity and the actual instruction boundary gate every acceptance and continuation. Unknown sends retain their claims across restart, and cancelled workers cannot resume automatically. This correction does not relax base, clean-head, checks or independent-review evidence requirements.

The owning worker identity is retained across restart and recovered from existing journal evidence during upgrade. A replacement worker requires manual recovery. An accepted classification remains visible while independent review descendants are busy, but it does not satisfy review evidence or grant readiness.
