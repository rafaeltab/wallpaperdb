---
title: Service upgrades and retained work
description: Deployment ordering, legacy recovery, and replay procedures for existing installations.
---

For fresh local setup, use [CONTRIBUTING.md](https://github.com/rafaeltab/wallpaperdb/blob/main/CONTRIBUTING.md). This guide covers existing data and retained work.

Apply generated database migrations before starting the corresponding new service. Deploy each service's complete `dist` directory: native image workers and deferred application chunks are required at runtime.

## Immutable asset references

Storage adapters derive addresses from logical references and the image metadata in events. Keep `S3_BUCKET` consistent across Ingestor, Variant Generator, Color Extractor, and Asset. Keep `PROFILE_PICTURE_BUCKET` consistent between User and Asset. Consumers need read access to their producers' objects; only owners may delete bytes. [ADR 0008](https://github.com/rafaeltab/wallpaperdb/blob/main/docs/adr/0008-resolve-assets-through-stable-object-layouts.md) records why these layouts are stable contracts.

When upgrading a development installation from the descriptor-registry revision, stop producers while upgrading all applications together. Before switching, compare its descriptors against the deterministic layouts and configured buckets. Preserve any mismatching object and its descriptor, and migrate it deliberately before replaying its logical reference. Matching original, variant, and Profile-picture paths need no copy or reset. The old `asset-references` bucket is no longer a runtime dependency; retain its descriptors until audit and replay checks finish. Rolling back to descriptor-based binaries also requires descriptors for assets created after the switch; the old descriptor records alone are insufficient.

Do not rename buckets or change layouts through configuration alone. A migration must preserve object bytes and identities and account for producer records, Asset's stored locations, and retained messages. Historical coordinate-based events continue to use their recorded locations. Back up the object buckets with their owning databases and configuration, and verify restore and replay together. The production release procedure and Grafana alerts that reach a human are tracked in [issue 236](https://github.com/rafaeltab/wallpaperdb/issues/236).

## Quarantine replay

Asset, Color Extractor, and Variant Generator share a replay decoder in [`@wallpaperdb/core/quarantine`](https://github.com/rafaeltab/wallpaperdb/blob/main/packages/core/src/quarantine/index.ts). Ordinary single records and raw chunk manifests retain their formats and identities. Header-heavy inputs use a manifest with `encoding: "original-message-v1"` to archive their complete original headers and bytes inside bounded chunks. Upgrade replay tooling to read this format before processing those records.

Read a manifest's chunk sequences in order and pass their data with the manifest to `decodeQuarantineReplay`; pass a single record without chunks. The decoder validates bounded metadata, lengths, and SHA-256 before restoring original bytes and CloudEvent/trace headers, including repeated values. Do not silently normalize invalid metadata: repair it deliberately before replay. Archived broker publication controls are excluded from replay. Publish to the recorded original subject with a fresh broker publication ID, preserving the original CloudEvent occurrence instead of the quarantine envelope's identity.

Acknowledge the source only after every chunk and the completion manifest receives durable acknowledgement. Partial chunks do not establish handoff. Failed writes leave the original pending until capacity or broker availability returns. Restrict access to quarantined original events.

## Ingestor

The CloudEvents upload migration requires consumer-first deployment:

1. Upgrade every Asset, Variant Generator, Color Extractor, and User replica to a revision whose `@wallpaperdb/events` accepts both legacy uploads and CloudEvents. Upgrade Gateway's event intake too if it predates CloudEvents support.
2. Drain and stop all old Ingestor replicas.
3. Apply the Ingestor migrations with `make migrate PACKAGE=ingestor`, then start the new Ingestor.

Older consumers can terminate new-envelope deliveries; upgrading afterward does not trigger redelivery. Keep both formats supported while either remains retained or replayable.

The migration prepares legacy reservations and outbox recovery metadata in one transaction. Incomplete committed records stop migration for repair; investigate those records and rerun the migration rather than making their originals eligible for cleanup. Keep committed originals and their metadata intact. The [Ingestion context decisions](https://github.com/rafaeltab/wallpaperdb/tree/main/apps/ingestor/docs/adr) explain the compatibility limits.

## Asset

### Rename from Media

The workspace, Compose service, telemetry service name and public delivery prefix are now `asset`. Gateway uses `ASSET_SERVICE_URL`, `ASSET_PUBLIC_BASE_URL` and `ASSET_PUBLIC_PATH`; Web uses `VITE_ASSET_URL`. Existing `/media` URLs have no redirect. Regenerate worktree configuration with `make install`; update custom deployments and saved client URLs to `/asset`.

Upgrade an existing development stack in the same worktree and Compose project:

1. In the previous checkout, run `make apps-stop` without a `SERVICE` selector. This removes all application containers while preserving infrastructure, its network, and volumes.
2. Switch to the renamed revision and run `make install` to regenerate application environments. Keep the existing `.worktree` project identity and infrastructure volumes.
3. Run `make apps-start` without a `SERVICE` selector to rebuild all applications and reload their configuration, including Caddy routing `/asset` to `asset:3003`.
4. Check `/asset/ready`, request an existing wallpaper through `/asset/wallpapers/<id>`, and request a resized rendition. Verify Gateway returns `/asset` delivery URLs and Web loads them. Compare catalog state and consumer acknowledgement floors with the values recorded before stopping the applications.

Starting only `SERVICE=asset` leaves callers and Caddy unchanged. Do not reset infrastructure, purge streams, or recreate consumers for the rename. Use consumer recovery below only if startup reports an exhausted legacy delivery limit.

Persistent identities deliberately retain their earlier names:

- `wallpaperdb_media` remains the Asset database. Its tables, Drizzle migration history, catalog, occurrence ledgers and pending outbox rows are unchanged. `make psql DB=asset` selects this database.
- All Compose infrastructure volume keys and the project name remain unchanged, preserving PostgreSQL, JetStream, object storage and Grafana state. Asset has no dedicated data volume. Object bucket names and keys remain unchanged.
- The three `media-*` consumer names listed below retain their acknowledgement floors and pending deliveries. `MEDIA_QUARANTINE`, its `media.quarantine` subject and `media.upload.*` record types retain quarantined records and replay compatibility.
- `https://wallpaperdb/media` remains the CloudEvent source and part of the NATS publication deduplication key. Changing it could make an interrupted outbox publication appear to be a new occurrence. Gateway also retains `wallpaperdb/media` for legacy event decoding. These are event identities, not delivery routes.
- `USER_MEDIA_SERVICE_TOKEN` remains the shared User/Asset credential setting, so setup reuses the existing secret instead of rotating it. It is unrelated to Gateway's renamed URL configuration.
- The dashboard file and display name use Asset, but its `wallpaperdb-media-overview` UID remains stable to preserve saved Grafana links. Queries use the renamed `asset_*` metrics; new telemetry identifies the service as `asset`. Historical `media_*` telemetry remains under its original name.

No delivery-URL rewrite or event replay is required. The catalog stores bucket/key references and asset identities; Gateway and Web construct public URLs. User's picture-import `source_url` remains the external identity provider's input URL. Back up the existing databases, object storage and JetStream state as a unit before an upgrade, and verify delivery and consumer progress afterward.

### Catalog and consumer recovery

Apply migrations without resetting the delivery catalog. Legacy reconciliation preserves stored metadata and can emit one new availability announcement because older releases had no publication ledger.

Startup rejects a legacy consumer with a finite `MaxDeliver` and recorded redeliveries. Increasing that limit cannot revive already exhausted messages. Recover it with every Asset replica stopped:

1. Save `manager.consumers.info(stream, durable)` to an operator-owned file. Verify that source history still contains the required messages. Do not purge it.
2. Record `saved.ack_floor.stream_seq + 1` as the restart sequence. Previously acknowledged legacy omissions need a separately chosen earlier replay point.
3. Delete only the affected durable and recreate it with the same filter, explicit acknowledgements, unlimited broker delivery, and the recorded sequence:

```ts
await manager.consumers.delete(stream, durable);
await manager.consumers.add(stream, {
  durable_name: durable,
  ack_policy: AckPolicy.Explicit,
  max_deliver: -1,
  filter_subject: saved.config.filter_subject,
  deliver_policy: DeliverPolicy.StartSequence,
  opt_start_seq: saved.ack_floor.stream_seq + 1,
});
```

4. Restart Asset and monitor dependency and consumer health, pending outbox work, and quarantine.

The durables are `media-wallpaper-uploaded-consumer` and `media-wallpaper-variant-uploaded-consumer` on the configured wallpaper stream, and `media-profile-picture-snapshots` on `PROFILE`. New consumers bound application processing attempts while broker redelivery remains unlimited when quarantine is unavailable.

`MEDIA_QUARANTINE` has a thirty-day repair horizon, one-GiB capacity, and discard-new overflow. Startup rejects incompatible policies. Export or repair failures before expiry. Failed quarantine writes leave originals pending; restore NATS or capacity so they can retry.

Use the [shared quarantine replay procedure](#quarantine-replay), including its framed-record decoder. See the [Asset decision](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/asset/docs/adr/0001-replay-safe-delivery-catalog.md).

## Gateway

### Wallpaper index compatibility

The color-utility catalogue requires a fresh mapping. Startup rejects a histogram-based index with `IncompatibleWallpaperMapping`, identifying the index and remediation. Container restarts and `make infra-start` preserve the incompatible mapping.

The color-query replacement assumes a [fresh installation](https://github.com/rafaeltab/wallpaperdb/blob/main/docs/research/color-querying/PRODUCTION-QUESTIONS.md#fresh-installation-and-picker-scope). For disposable local data, stop the applications with `make apps-stop`, run `make infra-reset`, then `make infra-start` and `make dev`. The reset deletes the checkout's databases, object storage, and retained NATS events as well as OpenSearch.

If data must be retained, preserve the old index and original assets before planning recovery into a new `OPENSEARCH_INDEX` with the [required mapping](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/gateway/src/adapters/opensearch/mappings.ts). Legacy histograms cannot supply current measurements; copying supported catalogue metadata restores ordinary browsing but leaves those wallpapers out of color-ranked results until their originals are measured again. Already acknowledged Gateway consumers do not repopulate a new index merely because its name changed.

Utilities are excluded from stored `_source`, so source-only reindexing of a current catalogue also loses its utility bank. Stop Gateway writers during the copy. Remove `utilities`, `colorReady`, `colorOrder`, and `colorSnapshot` from every copied document before writing it to the new index; do not transfer legacy histogram fields either. Copied readiness admits unmeasured documents to color searches; a copied watermark can suppress their measurement replay. Keep the original snapshots and events in the preserved source, then replay retained compatible measurements through [Gateway's projection path](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/gateway/src/adapters/opensearch/wallpaper-projection.ts). That path writes the snapshot, occurrence order, complete utility bank, and readiness marker together. Verify ordinary and color-ranked browsing before reopening catalogue traffic; never set `colorReady` independently to mark an incomplete restore as ready.

Audit copied `variants` and `variantOrder` together. Every copied rendition needs the matching occurrence watermark for its width, height, and format; otherwise an older pending event can replace it. If the source predates occurrence metadata or has incomplete watermarks, remove both the copied variants and their order map from the destination, then initialize `variants` as an empty array. Replay the complete retained variant history through Gateway's projection path in occurrence order while catalogue traffic and new producers remain stopped. This rebuilds each rendition and its watermark together. Verify that every recovered rendition matches the latest retained occurrence before reopening traffic. If the available history cannot establish those latest occurrences, keep recovery incomplete and reconstruct them from verified evidence; do not invent watermarks from document timestamps.

### Retained events and message budgets

Upgrading projections does not recover information older versions discarded. Existing color projections lack occurrence ordering metadata, so the first stale result after upgrade can replace their colors. Replay the complete retained color history before reopening catalogue traffic if historical ordering must be preserved. The same applies to timestamp precision lost by older millisecond-only projections.

Wallpaper and Profile source messages are bounded to 64 KiB including headers. Quarantine and broker `max_payload` must each allow at least 256 KiB for the envelope. Gateway rejects incompatible limits before subscribing.

Gateway quarantine stores the original payload in `data.original` and complete NATS headers in `data.originalHeaders`, both base64 encoded. Decode both fields for replay, preserving the original occurrence and trace metadata while excluding archived broker publication controls. Choose a fresh broker publication ID. Oversized duplicate diagnostic fields may be omitted; the replay evidence remains intact. This format is separate from the three services' [chunked quarantine protocol](#quarantine-replay).

Lowering a stream limit does not rewrite retained messages. Gateway audits retained payload and header bytes before first consumption. Its `wallpaperdb.gateway.quarantine-budget` stream metadata records the stream creation time, configured limit, policy version, and audited sequence. Version 2 replaces the earlier payload-only audit. Matching certificates avoid repeated history scans; the initial scan takes time proportional to retained history.

An oversized historical message stops startup and reports its stream, sequence, and byte count. The original remains stored. Export the identified record, for example with `nats stream get WALLPAPER <sequence> --json`, determine its retention and replay requirements, and explicitly resolve that record before restarting. Do not purge the source stream to bypass the failure.

Remove the audit certificate before loosening a source limit, even temporarily. Stream recreation or a changed limit requires another audit. Change the event-size contract, quarantine capacity, and audit policy together. See the [Gateway projection decision](https://github.com/rafaeltab/wallpaperdb/tree/main/apps/gateway/docs/adr).

Deployments retaining `GRAPHQL_MAX_COMPLEXITY=1000` must raise it to admit the web browse query under descendant-aware costing; the current default is 2000. Clients inspecting failed health probes must read the health classification from `healthStatus`; `status` is now the numeric Problem Details HTTP status.

## User

Drain old User replicas before applying `0010_dark_terrax.sql` and `0011_faithful_skrulls.sql`, then start the new image. These migrations add picture upload/deletion recovery states and outbox trace context. Do not run older picture cleanup workers alongside the new state machine.

User's private Biography ownership feed accepts both legacy uploads and new Wallpaper publications. The [ownership consumer](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/user/src/adapters/events/consumer.ts) keeps the existing `user-wallpaper-ownership` durable and creates a separate `user-wallpaper-publication-ownership` durable for `wallpaper.published`. Its independent cursor reads retained publications that the legacy filter may already have skipped. Preserve both consumers and the ownership projection on restart; changing the old filter alone cannot recover those skipped facts. Replay is limited to history still retained in the configured Wallpaper stream. The [cross-context contract](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/user/test/wallpaper-publication.integration.test.ts) covers this upgrade path and Biography authorization.

If startup rejects the legacy `WALLPAPER/user-wallpaper-ownership` consumer for a finite delivery limit and recorded redeliveries:

1. Stop every User replica. Save the consumer configuration and acknowledgement floor, and verify retained history.
2. Recreate only that durable with explicit acknowledgements, the `wallpaper.uploaded` filter, unlimited broker delivery attempts, and a starting sequence one greater than the saved acknowledgement floor. Startup diagnostics include that sequence. Use the same NATS recovery pattern described for [Asset](#asset).
3. Restart User and monitor consumer health. Duplicate projection is safe because the first accepted owner remains authoritative. Application processing still stops after three attempts and requires durable quarantine before acknowledging failed input.

`USER_QUARANTINE` uses discard-new storage with a 64-MiB bound and thirty-day retention. A full or unavailable quarantine leaves delivery unacknowledged. Restore capacity or repair the failure before replaying affected input.

### Private pictures and evidence

Provision the Profile picture bucket without anonymous access, including any custom `PROFILE_PICTURE_BUCKET`. Do not put Profile pictures in a public wallpaper bucket. Set the same `USER_MEDIA_SERVICE_TOKEN` in User and Asset, with Asset's `USER_SERVICE_URL` pointing to User's internal origin. Worktree setup generates these settings for Docker development. For host-based development, use the reachable host User URL and the same token in both services. Never expose this token in browser configuration. A missing or mismatched token makes picture delivery fail closed.

Removing a picture stops future origin delivery; it cannot recall immutable copies already cached by browsers or a CDN. Replaced and removed originals remain private until their recorded expiry. Changing the configured retention duration does not rewrite existing asset deadlines.

Local evidence cleanup removes only published event rows and expired private picture candidates. It preserves current Profiles, active assets, Handle claims, and undelivered events. Delayed publication does not extend Handle reactivation eligibility. It does not erase downstream projections or retained NATS history; the temporary event-retention policy is tracked in [issue #162](https://github.com/rafaeltab/wallpaperdb/issues/162).

If telemetry is intentionally disabled, also disable the missing-signal alert. Otherwise operators will receive an alert for the absence they configured. See the [User workflow decision](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/user/docs/adr/0001-effect-profile-workflows.md).

## Enrichment workers

Deploy a Gateway that accepts CloudEvents color results before upgrading Color Extractor. Stop legacy worker replicas before relying on durable quarantine, because they retain their earlier termination behavior. Broker-exhausted legacy messages require operator replay; changing the consumer configuration does not recover them automatically.

Variant Generator and Color Extractor quarantine have a thirty-day repair horizon and one-GiB capacity with file-backed storage and discard-new overflow. Startup rejects incompatible policies. Explicitly migrate existing Color stream settings while preserving retained evidence.

Restarts and infrastructure setup preserve quarantine configuration. If startup rejects `COLOR_EXTRACTOR_QUARANTINE`, inspect the stream before restarting. Export retained evidence before tightening its age or capacity limit, or confirm the stream is empty. Compare every field checked by the [startup validation](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/color-extractor/src/adapters/events/quarantine.ts), including subjects, storage, retention, discard policy, byte and age limits, and per-subject eviction settings. Correct mutable incompatible values in place. The required byte limit is at most 1 GiB and greater than zero; the age is exactly thirty days.

Startup validation does not audit every routing or access setting. Remove quarantine `republish` rules before restarting publishers: [NATS republishes bodies and publisher headers to live subjects](https://docs.nats.io/learn/jetstream/subject-mapping#republish-to-live-subjects), where ordinary subscribers can receive the evidence. Also audit subject transforms, mirrors and sources, account exports, and subscriber permissions for access to original events. Apply the same access restrictions to evidence archives; a passing startup check does not establish confidentiality.

Storage and retention policy are not mutable [stream-update fields](https://nats-io.github.io/nats.js/jetstream/types/StreamUpdateConfig.html). A memory-backed stream therefore needs deliberate replacement, not an in-place storage change:

1. Stop every Color Extractor replica and every quarantine consumer or replay process. Keep the broker running because restarting it loses memory-backed evidence. Save the stream configuration and state; prevent expiry and administrative deletion during the export, temporarily disabling mutable age expiry if needed.
2. Export every retained record through the stream message-read API into a durable, access-restricted archive. Preserve the original stream name, sequence, subject, timestamp, raw header bytes, and payload bytes. Include partial chunks and manifests, not just successfully decoded events. Record sequence gaps, record counts, and checksums.
3. Read the archive back and compare its records with the stable stream state. Verify complete manifests using their original sequence references and the [shared replay decoder](#quarantine-replay). Resolve missing chunks or an incomplete export before proceeding. Keep the archive independently of the broker and verify it remains readable there.
4. Only after that verification, delete the incompatible stream and create a fresh file-backed `COLOR_EXTRACTOR_QUARANTINE` using the configuration in `ensureQuarantine` at the linked startup-validation source. Confirm every required setting before restarting workers. An empty stream can take this step after its empty state is verified.
5. Replay repaired work from the archive using the shared procedure. Resolve manifest chunk sequences against the archive, not the recreated stream: its new records can reuse old sequence numbers. Preserve original occurrence identities, use fresh broker publication IDs, and retain the archive until replay and recovery are verified.

Do not republish raw chunks into the replacement stream with new sequence numbers while leaving old manifest references unchanged. Do not delete retained evidence or reset the NATS volume merely to bypass startup validation.

Both workers use the [shared quarantine replay procedure](#quarantine-replay). Inputs exceeding the complete message budget or JetStream's 64 KiB header limit use bounded chunks and, when needed, the versioned original-message frame. Monitor pending inputs, quarantine capacity, and publication failures.

Existing variant object keys are immutable. Changing encoding settings affects new targets; replay does not regenerate an existing rendition with new settings. Deliberate regeneration needs a separately designed versioned target identity. See the [Variant Generator decision](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/variant-generator/docs/adr/0001-replay-safe-variant-generation.md).

New variant announcements report their actual encoded dimensions. Existing variants retain the dimensions previously announced for their immutable targets, including historical nominal preset dimensions; replay does not rewrite those facts.
