# Contributing to WallpaperDB

Start with the [coding guidelines](CODING_STANDARDS.md) for the work you are changing. Run repository tasks through Make; `make help` lists commands and prints this worktree's ingress address.

## Set up a checkout

The authoritative tool inventory, exact versions, and host boundaries are in [mise.toml](mise.toml). [mise.lock](mise.lock) locks download checksums and Conda dependencies. The validated host is Linux x86-64 with glibc, Docker Engine access, procfs and `flock`. Full local validation requires Linux because the shared Docker queue reads procfs. Other platforms are not locked or validated; do not infer support from a backend's download availability.

Bootstrap [mise](https://mise.jdx.dev/getting-started.html) at the configuration's minimum version, with host Git, Make, a POSIX shell, CA certificates and download/archive utilities available. Review the configuration before trusting it. The managed toolchain includes Git and Make after bootstrap; Docker's daemon, permissions, credential helpers and native compiler/OS dependencies remain host responsibilities. Mise does not install credentials or change the daemon.

```sh
git clone https://github.com/rafaeltab/wallpaperdb.git
cd wallpaperdb
mise trust
make install
make toolchain
```

Make recipes enter `mise exec` automatically, including non-interactive agent commands. For direct CLI work, use `mise exec -- <command>` from the checkout or [activate mise in your shell](https://mise.jdx.dev/cli/activate.html). Shell activation alone is not required for Make. Run `make toolchain` to print and check the executables and versions actually selected. Missing tools fail before workspace tasks start; rerun `make install` after a toolchain change. A new linked worktree needs its own trust decision and installation.

Keep exact tool requests and the generated lockfile together. To upgrade, edit [mise.toml](mise.toml), run `mise lock --platform linux-x64`, then validate `make install`, `make toolchain`, and the affected tasks. Installation uses `--locked`; it rejects missing platform entries instead of silently resolving them. Local mise overrides are unsupported for the shared toolchain. The default Node pin matches the application images. The broader runtime compatibility contract remains [package.json's engines](package.json); a development pin does not narrow it. The pnpm `packageManager` declaration must match mise and is checked before Make recipes; pnpm's automatic manager switching is disabled in [.npmrc](.npmrc).

Package-owned CLIs and Chromium remain installed through pnpm and the workspaces' Playwright versions. Use the browser installation commands below; Playwright's `--with-deps` may need host package-manager privileges to install shared libraries and fonts. Playwright 1.59.1 rejects the `ubuntu26.04-x64` target on Ubuntu 26.04, so browser installation there needs a Playwright-supported runner/OS; mise cannot correct the package's browser/platform support. Agent-browser's own browser download is separate: `mise exec -- agent-browser install` uses its pinned CLI.

Docker and Compose discover the managed plugins through a private derived configuration under ignored `.mise/`. It retains the source Docker configuration, credentials and contexts; login, logout and context changes still use the source configuration. This avoids changing host plugin installations. Container runtime images and Alpine build dependencies remain declared in Dockerfiles and Compose. Container pnpm bootstraps read the root manifest rather than maintaining another version pin.

Installation assigns an isolated worktree slot and generates `.worktree`, `infra/.env`, and application `.env` files. It also creates `~/.config/wallpaperdb/secrets.env`, or uses `$XDG_CONFIG_HOME/wallpaperdb/secrets.env` when set. The legacy `secret.env` filename is still accepted.

Fill in the Clerk credentials in that secrets file before running authenticated services. Browser tests also need the seeded test user's email and password. Keep those values outside Git. Run `make install` again after changing them. Installation regenerates application `.env` files, so edits made directly to those files will be lost. Environment variables supplied to installation take precedence over the secrets file.

```sh
make infra-start
make dev
```

Open the ingress address printed by `make help`, followed by `/web`. The same ingress exposes `/grafana` and the service routes; see [Caddy's routing configuration](infra/caddy/Caddyfile) for the full list. Port assignments vary by worktree, so use the generated values rather than assuming service default ports.

Installation also generates private Asset authority in `apps/asset/.authority.json`, its broker configuration in `infra/nats/.generated.conf`, and a token-only operator inbox projection in `infra/.operator-inbox.json`. These files contain credentials and remain outside Git and image build contexts. [Asset setup](apps/asset/scripts/development-authority.ts) preserves configured identities and credentials across installation. Edit the trusted authority file to change application permissions, identity-provider settings or the operator destination, then rerun its `dev:configure` script through Make to regenerate broker configuration and the inbox projection. Existing checkouts need this regeneration before starting the inbox with the projected mount. Broker changes require a controlled broker restart. Existing active configuration requires an explicit `activate` operation through the [operator CLI](apps/asset/scripts/operator.ts); ordinary startup never replaces it. Initial development startup provisions accounts and initializes an empty installation after database migration.

The local operator destination is `/operator-inbox/` through ingress. Its HTTP Basic username is `operator`; its password is the generated authority file's `operatorNotification.token`. It displays persisted delivery receipts and offers no Asset or broker control. Use the operator CLI for deliberate quarantine or result recovery. For a result quarantine, pass the notice's `resultId` to `recover-result --id`; the notice's `id` identifies that exhaustion notification. For a Source confirmation quarantine, pass the notice's `sourceConfirmationId` to `recover-source-confirmation --id`. A deployed installation should select its trusted operator webhook and credentials in file configuration.

`make infra-start` and browser E2E omit the optional database and search admin UIs. Run `make infra-start-admin` to include both, then access `/pgadmin/` and `/opensearch-dashboards/` through the application stack's existing Caddy ingress. Infrastructure stop, reset, logs, and worktree teardown include the admin profile. LGTM stays enabled because the applications export telemetry to its collector. Headless runs preserve that behavior while omitting the admin UIs.

PostgreSQL runs its [database initialization](infra/postgres/init/01-init.sql) only for an empty volume. An existing development volume needs the new `wallpaperdb_wallpaper` database before Wallpaper can report readiness. Use `make psql` to create that database and apply its grant from the initialization file; restarting PostgreSQL does not rerun initialization.

`make dev` runs the applications in Docker with source watching. `make dev PACKAGE=<workspace>` runs that workspace's development script; the script determines whether it runs on the host or in Docker. Host-run services need host-accessible dependency endpoints. Use [service upgrade instructions](apps/docs/content/docs/guides/service-upgrades.mdx) and the [storage migration procedure](apps/docs/content/docs/infrastructure/seaweedfs.mdx) when upgrading existing data.

## Check a change

```sh
make check PACKAGE=<workspace>
make test-focused PACKAGE=<workspace> ARGS='<test path>'
make ci
```

Choose tests using the [testing guidelines](docs/coding-standards/project-organization.md#shared-testing-principles). The focused command builds workspace dependencies and runs selected tests serially. Local `make ci` runs build, lint, type checks, unit tests, integration tests, and non-E2E coverage merging. It reports that browser and container E2E are excluded. Integration tests retain their own containers and browser adapter contracts; install their Chromium dependency with `make run PACKAGE=web SCRIPT=test:browser:install` when needed. Ordinary validation needs only the prerequisites of those checks, without application-stack or E2E credentials.

Local CI's [task concurrency](Makefile) defaults to four to balance turnaround and resource headroom. Override it with `make ci CI_CONCURRENCY=1` on smaller hosts. The shared Docker queue still admits one validation run at a time.

GitHub Actions is the default place for complete browser and container E2E. Both jobs in the [E2E workflow](.github/workflows/e2e.yml) enforce failures on pull requests and main. Use explicit local E2E for diagnosis or deliberate validation:

```sh
make test-e2e PACKAGE=web-e2e ARGS='specs/upload.spec.ts'
make test-e2e PACKAGE=test-utils ARGS='tests/postgres.test.ts'
make test-e2e
```

The [Make command](Makefile) preserves `PACKAGE`, test-runner `ARGS`, and `FORCE=1`. E2E results remain uncached. Container-only selections use their test containers without Compose. Browser selections require generated configuration, development Clerk credentials, a seeded test user, and Chromium. Install Chromium with `make run PACKAGE=web-e2e SCRIPT=test:browser:install`. Run `make install` after updating secrets.

The [local runner](scripts/local-e2e.mjs) checks Docker, configuration, worktree ports, and container access to the public PostgreSQL initialization files before building current-checkout application images. If initialization permissions are rejected, apply only `chmod a+rx infra/postgres/init` and `chmod a+r infra/postgres/init/*.sql`. Docker bind-mount restrictions may need a separate host configuration fix; permission changes alone cannot resolve them.

Browser runs create a unique Compose project with fresh volumes on this worktree's ports. Existing stacks and data remain intact. Occupied ports fail before building; use a free worktree slot or deliberately stop your own development stack. The runner uses non-watching startup, waits for the [browser readiness contract](apps/web-e2e/src/environment-contract.ts), and removes only its own containers, network, and volumes on success, failure, or interruption. A complete run releases the browser stack before container suites start. No manual application startup is needed.

`make ci`, `make test-integration`, and explicit local E2E automatically join one Docker validation queue shared across worktrees. `make docker-status` shows its owner and waiting work. Use `make docker-run ARGS='command arguments'` for other Docker-heavy experiments, in an owned environment. Queued work runs in admission order and reports queue wait separately from execution. Remove manual `flock` wrappers around these updated commands, which now acquire their own lock. When validating an older checkout, inspect its Makefile first: commands that predate automatic coordination still need an explicit `flock` wrapper on the shared lock. Older `flock` users still coordinate through the same lock file but have no queue metadata.

The [shared queue](scripts/lib/docker-queue.mjs) requires Linux procfs and `flock`, and identifies processes across PID reuse and reboots. Cancelled or dead waiters release their place; child processes inherit the host lock so terminating a coordinator cannot admit another run while its command still executes. Nested coordinated commands reuse that inherited lock. Lock wait defaults to 900 seconds; `DOCKER_VALIDATION_TIMEOUT` overrides it in seconds. `DOCKER_VALIDATION_LOCK_FILE` selects an isolated queue for testing. Existing `E2E_LOCK_FILE` and `E2E_LOCK_TIMEOUT` remain fallbacks. The E2E runner's image build and startup/readiness deadlines remain controlled by `E2E_BUILD_TIMEOUT` and `E2E_READY_TIMEOUT`; see the [runner](scripts/local-e2e.mjs). Cleanup operations have separate bounded deadlines.

Lock targets must be empty regular files owned by the current user, without symbolic links, hard links, or group/other write access. Unsafe targets are rejected without truncating existing data.

Nested coordinated commands require every intermediate launcher to forward the file descriptor identified by `WALLPAPERDB_DOCKER_LEASE_FD`. Forwarding the environment variables alone is insufficient. Node or pnpm launchers that drop extra descriptors cause nested validation to fail before its workload starts. Prefer running coordinated Make targets directly; custom launchers must preserve the descriptor explicitly.

Browser credentials and owned artifact paths are passed only to the browser suite process.

The runner prints the failing phase and original status, reports cleanup failures separately, and retains service logs, command output, and browser failure artifacts in the private temporary directory it prints. Oversized command-output lines are omitted with a marker to keep streamed diagnostics bounded. Captures of configuration or service logs are capped at 1 MiB across stdout and stderr. Exceeding that limit fails the phase, stops its child process, and still attempts owned teardown; incomplete output is discarded. Browser artifacts and authentication state are written directly into that run's diagnostics directory; earlier workspace reports and authentication state remain untouched. It removes the run's temporary diagnostics before reporting success, once all requested tests and cleanup succeed. Use its focused rerun command; inspect retained logs before retrying or manually cleaning a failed owned project. Treat browser reports and traces as private and sanitize excerpts before sharing.

For other scripts use `make run PACKAGE=<workspace> SCRIPT=<script>`. `PACKAGE` selects a workspace, `SERVICE` selects an application container, and `DB` selects a database. Read `make help` instead of maintaining a second command list here.

## Pull request history

This repository uses rebase merging. Check each PR layer against its actual base with `make run PACKAGE=scripts SCRIPT=check:pr-history ARGS='<base> <head>'` before publishing. The [history check](scripts/check-pr-history.mjs) rejects merge commits in the PR and branches that would add no contents to the current base. A patch reverted on the base can be reapplied. The [PR history workflow](.github/workflows/pr-history.yml) runs the default branch's trusted validator for all PRs, including documentation changes. It fetches comparison commits as Git data and never executes the submitted tree. A base advance alone does not require rewriting an existing PR.

Preserve published commits while making review fixes, and keep additional commits linear. Resolve base conflicts by preparing a linear rebase, rather than merging the base into the PR. Invoking [babysit-pr](.agents/skills/wallpaperdb/babysit-pr/SKILL.md) authorizes necessary history rewrites and force pushes to the selected PR within the user's scope and limits. Outside that workflow, rewriting published history needs explicit user authorization; prepare and validate the proposed resolution before requesting it. After an authorized rewrite, use an explicit expected-head lease, rerun required validation, and assess review applicability under [review evidence](#review-evidence). A PR with pre-existing merge commits remains incomplete until its history is resolved.

Before reporting work complete or ready to merge, confirm GitHub's authenticated `mergeable` result is true for each PR against its current base. Refresh an unknown result; unresolved conflicts or an unknown result block handoff. The accepted integration guarantee is conflict freedom. With the PR head and base branch unchanged, an independent base advance preserves passing validation and reviews. Keep the published work as it is; no rebase, synthetic integration checkout, repeated CI, or repeated review is required solely because the base advanced. Stronger integration guarantees require the user's approval under [task scope](docs/agents/task-scope.md). When the branch's contents already landed, verify the landing and report that outcome. Native stack readiness remains required for every stacked layer.

The history workflow reconciles all open PRs through default-branch `pull_request_target`, `workflow_run`, and scheduled events. CI activity triggers reconciliation promptly; the schedule covers base pushes without CI, including documentation changes and branches without an open PR. GitHub can delay scheduled runs, so a base push does not guarantee immediate revalidation. All events share one non-cancelling concurrency group. Each admitted run reads live comparisons, finishes its writes before the next publisher starts, and reconciles every open PR even if an intermediate pending run was replaced. Run the status publisher only through this serialized workflow; use the read-only history checker for local validation. Each submitted head receives `PR history #<number>`, with the compared base SHA in its description.

These Actions-authored history statuses are advisory diagnostics, excluded from the CI gate. A collaborator with repository write access can reproduce the status context, so its result cannot establish trusted execution. Resolve the base branch through GitHub's authenticated Git reference API; a PR response can retain an older base SHA. Immediately before a ready-to-merge handoff, fetch the current head and live base and rerun the history checker from the trusted default-branch policy snapshot. This fresh check determines history readiness regardless of the advisory status. Other applicable CI checks and review requirements remain mandatory.

### Incremental mutation-testing pilot

Mutation checks are advisory and separate from `make ci`. The [workflow](.github/workflows/mutation.yml) checks changed code automatically on PR updates and builds a cumulative baseline nightly on the default branch. Manual dispatch supports a representative scope and explicit checkpoint import for acceptance exercises. A failed or incomplete mutation pilot does not block delivery, and agents report its available outcome without waiting or retrying merely to turn it green. Ordinary CI requirements still apply. No mutation-score threshold is enforced during the pilot.

The [inventory](mutation.inventory.json) classifies every maintained workspace. Its exclusions include concrete reasons and [follow-up work](https://github.com/rafaeltab/wallpaperdb/issues/445). Enabled unit/capability suites use native Vitest coverage selection. Gateway Redis also has an integration stage. Other fixture families need cancellation-safe resource ownership before opt-in. Deployed bundles and subprocess execution remain unvalidated; ordinary coverage does not establish mutation activation in those processes. Generated code is outside the eligible source scope.

Web's normal [mutation configuration](apps/web/vitest.mutation.config.ts) retains the exact pre-existing Node project and all 183 eligible production sources. Web jsdom and page-owned Chromium are excluded from normal mutation execution under [#519's support decision](https://github.com/rafaeltab/wallpaperdb/issues/519); their remaining qualification work is tracked in [#600](https://github.com/rafaeltab/wallpaperdb/issues/600). This preserves all ordinary Node, DOM and browser suites and does not newly qualify Node mutation support from an unmutated test baseline.

The [bounded jsdom question](https://github.com/rafaeltab/wallpaperdb/actions/runs/40977483399) passed its 1,048-test combined baseline, including five App cases and 40 browser cases, but both predefined production guard candidates remained Pending and whole capture was incomplete. The [first Chromium question](https://github.com/rafaeltab/wallpaperdb/actions/runs/40980512909) also passed that baseline. Its predefined production distance-function empty-body mutation was reported Killed with the expected zoom '1' versus '2' assertion and sole real browser pinch killer. That target was not unreached, but raw target filter, mode, positive native hit and result, plus complete timing/worker/footer/disposal evidence, were missing. A separate injected keyboard-guard mutant produced an outside-test RuntimeError; it remains an error, not a kill or a baseline failure. PID-change, open-error, child-signal and earlier transport causes remain unknown. These are precise support exclusions, not claims that the mechanisms are impossible or that the failed runs passed.

React Muuri retains its existing jsdom [workspace opt-in](packages/react-muuri/mutation.config.json). The [accepted event-bridge witness](https://github.com/rafaeltab/wallpaperdb/actions/runs/40944953596) established native activation, per-test selection, positive hits, assertions, killers and healthy capture for one of 15 eligible source files. It does not establish a full package baseline, real layout/browser behavior, fault paths or an independent residual-resource census. Later writer/framing source applicability is separate from that historical witness and is not a new whole-package or current-head runtime qualification.

The mutation workflow retains Ubuntu 24.04 and every other existing input, cache, permission, budget and timeout. Normal Node/jsdom stages do not install Chromium. Future page qualification needs a fresh supported runner/install assessment and explicit reviewed configuration changes; the coordinator has no runtime project/config-switch input. Both declared PNG inputs and the bounded stage-owned projection remain because the normal Node [picture-processing suite](apps/web/test/features/picture-processing.test.ts) reads the small PNG through the same external peer topology. The P3 declaration conservatively preserves the reviewed two-file projection contract and does not enable browser execution.

Page-owned execution does not establish activation inside image Worker globals. [Worker and deployed-bundle transport remain unqualified under #560](https://github.com/rafaeltab/wallpaperdb/issues/560). [Deployed Playwright journeys](apps/web-e2e/src/playwright-config.ts) use separately served bundles without native Vitest activation or per-test coverage/result transport. Supporting them requires owned instrumented serving, browser or Worker activation, native selected-test/result transport and bounded resource ownership. The E2E workspace's Node configuration tests do not qualify those journeys.

Local mutation runs are exceptional. Use them only to answer a concrete implementation or diagnostic question, with at most five minutes overall including setup and shutdown. Build full repository baselines in CI. The local runner requires a workspace and rejects budgets above 300 seconds. It prepares dependency builds inside that invocation deadline, reserves shutdown time, and reports incomplete analysis if preparation exhausts the allowance. Inventory inspection skips the build. Start with a small source selection if setup cannot fit. Use the same exact Node runtime as CI when sharing checkpoints; runtime, OS distribution, libc and architecture are compatibility inputs.

```sh
# Inspect supported workspaces and exclusions without executing mutations.
make test-mutation PACKAGE=profile-markdown ARGS='--inventory --offline'

# Exceptional local diagnostic, bounded to one minute including shutdown.
make test-mutation PACKAGE=gateway ARGS='--scope all --files src/adapters/redis/usage.ts --budget 60 --offline'

# Explicit portable repository checkpoint import into a bounded diagnostic.
make test-mutation PACKAGE=profile-markdown ARGS='--budget 30 --baseline /tmp/checkpoint.json --offline'
```

CI diagnostics may pass comma-separated workspace basenames to `--package`; local diagnostics remain limited to one workspace. `--files` takes comma-separated exact workspace-relative source paths. Representative completion never establishes full-repository completion. `--suite` selects a stage for diagnosis; manual CI dispatch exposes the same selector. Integration-only reports retain compatible unit results and unit-kill deferrals within the selected files. Ordinary runs coordinate all applicable stages. The maintained repository uses the [coordinator](scripts/lib/mutation-coordinator.mjs); standalone workspace configurations retain the original single-suite runner for compatibility verification.

PR mutation execution shares a 15-minute budget across all workspaces and stages. Nightly execution shares 60 minutes. One worker runs at a time, below the two-worker limit. Startup, unmutated coverage collection and mutation execution consume this aggregate budget. Shutdown time is reserved inside it. The coordinator also reserves 20% of the invocation allowance, capped at 15 seconds, for final checkpoint publication and reports that cost separately. It reuses restored stage state for summaries and publishes one cumulative repository checkpoint after the bounded pass; completed stage results remain in immutable snapshots between visits. CI installation/build, artifact transfer and upload have separate finite deadlines. Local artifact transfer and lock waiting count toward the local invocation limit. Local integration analysis acquires the same Docker host lock as other validation only after the unit gate leaves runnable integration work, and releases it after each integration visit and its owned fixture cleanup; avoid holding that lock around `make test-mutation` itself.

A stage receives a bounded slice. `--quantum` sets its maximum execution and shutdown allowance in seconds, defaulting to 120. The runner reserves shutdown time inside the smaller of that slice and the remaining aggregate budget. The saved scheduling cursor rotates across workspaces and stages on subsequent runs, so an expensive early workspace cannot starve later services. Unit/capability results come first. Only surviving or unit-uncovered mutations reach integration. Unit kills skip integration; pending unit work remains pending. Native per-test coverage selects tests within each stage. Zero covering tests remain uncovered. Mutation identities include source content, location, operator and replacement; numeric IDs cannot join stages. Combined survivors require every applicable stage to finish. Timeouts, invalid mutations, errors and pending work retain separate outcomes and never increase the kill rate.

The runner checkpoints before shutdown, then terminates its owned worker process group after a finite grace. Gateway Redis containers belong to the stage and survive repeated Vitest module lifetimes. Each mutation receives fresh application modules/clients and starts after a verified empty-data reset. Leaked clients or failed resets stop execution as infrastructure errors. The stage removes only its own named container, including on cancellation and failure. Fixture startup, reset and teardown timings appear separately in reports. `MUTATION_REDIS_ISOLATED=1` selects owned per-mutation containers for a bounded outcome comparison; `MUTATION_REDIS_RESET_FAILURE=1` exercises the failure path. These inputs invalidate the integration checkpoint.

Immutable stage snapshots live under the shared Git directory, so linked worktrees reuse compatible progress. Each execution uses private sandboxes and report files. Restoration unions independent snapshots for identical inputs and rebinds test IDs and checkout paths. File-level provenance retains older unselected results for later native reassessment without counting them as current evidence. Partial writers cannot erase completed compatible results. Different terminal outcomes for the same mutation and inputs remain an explicit `RuntimeError` with all conflicting statuses, independent of publication order. They count as execution errors and pending work, and cannot be reused as native outcomes. Diagnose the differing results and change the affected inputs before expecting a clean baseline. Repository checkpoints retain unvisited stages and the scheduling cursor. A failed publication leaves earlier valid snapshots intact. Concurrent executions keep their own immutable outputs; stable report paths are only presentation outputs.

A checkpoint may be partial. A complete baseline requires mutation discovery across every eligible source file and terminal results for that input state. Reports keep eligible-source discovery, processed mutation counts, score and execution health separate. Before all source files are discovered, the full eligible mutation count is unknown. A 100% processed baseline may still contain survivors, uncovered mutations, invalid mutations and timeouts. Relevant changes can reduce current completeness. Repeated no-progress stage visits identify the blocked stage; increase its CI slice or diagnose startup/reset costs instead of assuming eventual completion.

Source-only edits select changed mutation files. Relevant tests, helpers, fixtures, dependencies, runner/configuration or declared environment changes widen the selected scope conservatively. Source/test changes conservatively invalidate prior execution results for that workspace and stage. A helper change can alter a mutant without changing its text, so native reuse receives only results matching the current complete suite-input identity. Older unselected files retain their provenance for reporting; other compatible workspaces keep their progress. Stryker performs native incremental analysis on that validated input. Compatibility checks invalidate unsafe reuse for runtime, OS/architecture, installed toolchain, dependency graph and fixture/configuration changes. Declare files outside the workspace in the suite's repository-relative `externalInputs`; their bytes participate in compatibility and their changes widen source selection. Declare external environment names in each suite's `environmentKeys`; checkpoints store hashes, never their values. After checkpoint imports, a stage with declared environment inputs widens to all its eligible sources when no compatible stage checkpoint exists, even if Git paths did not change. An existing compatible environment checkpoint retains normal changed-file selection. External services and undeclared inputs remain the suite owner's responsibility. Unselected results retain their original input identity. See [Stryker's incremental limitations](https://stryker-mutator.io/docs/stryker-js/incremental/).

Pull-request CI runs use `--offline` and do not receive a GitHub API token or persisted checkout credentials. Nightly and manual runs retain authenticated checkpoint downloads.

Automatic remote import considers the five newest successful same-repository mutation workflow runs on the authenticated default branch, with a 45-second aggregate transfer limit. It imports compatible stage snapshots across those artifacts, so a newer artifact with another fixture variant cannot hide older compatible progress. Scheduling comes from the newest compatible artifact. Local transfers also respect the invocation deadline. PR artifacts cannot replace the shared baseline. Missing, expired, inaccessible or incompatible artifacts produce a visible bounded cold fallback. Artifacts expire after 90 days. `--offline` uses shared local state; `--baseline` explicitly imports a downloaded repository `checkpoint.json`. Manual CI dispatch's `import_run` imports a deliberately selected same-repository artifact for acceptance continuation, independently of automatic default-branch trust. A subsequent nightly run imports cumulative progress and preserves compatible results and unvisited workspaces.

Repository outputs are `reports/mutation/summary.json` and portable `checkpoint.json`. Stage reports live under `<workspace>/reports/mutation/<stage>/`; completed native runs also emit `mutation.html` and `mutation.json`. Private `run-*` directories preserve diagnostics and per-mutant pending work. Generated artifacts stay outside Git. The runner exits 0 for completed/no-change analysis, 2 for incomplete analysis, 1 for baseline-test/runner/infrastructure/publication failure, and 130 for cancellation. Make maps nonzero recipes to its own status, so automation reads the summary. Budget expiry produces an advisory warning and uploads progress; the outer platform timeout is a failure and may prevent upload. Failed runner execution remains visible in the mutation check without making ordinary CI ignore errors.

Stage summaries separate `checkpointReuseSeconds` (checkpoint restoration and incremental-file preparation), `coverageCollectionSeconds` (native dry-run calls), and `mutationExecutionSeconds` (native mutant-run calls). `incrementalAnalysisAndSelectionSeconds` measures native planning after coverage, including incremental matching and coverage-based selection. These are wall-clock measurements, not CPU time or estimates of saved runtime. Fixture reset time can overlap runner calls. If a runner is interrupted mid-call, `runnerTimingsComplete` is false and recorded runner durations are lower bounds.

When upgrading Stryker or Vitest, retain the existing [compatibility regression](scripts/mutation-runner.test.mjs) and recheck native test selection, collection failures, static initialization, zero covering tests and mutation-time hangs with a bounded real-runner exercise. The [pinned Vitest patch](patches/stryker-vitest-10.0.0.patch) fixes nested selection, module isolation, and the empty-coverage fallback that otherwise reports entirely uncovered scopes as survivors. The staged reporter also relies on Stryker 10's plan event being consumed by its executor; revalidate unit-kill gating and stage provenance before upgrading. Investigate upstream fixes before removing the patch. Acceptance evidence belongs in the implementation PR, without another tooling regression suite or committed investigation notes.

## Review evidence

Use this policy for local independent reviews, hosted code and security reviews, automated workers, and final handoff or landing checks. For an independent base advance with unchanged PR head and base branch, preserve reviews under the [PR history policy](#pull-request-history). Changes to the reviewed work or base branch prompt an applicability assessment before requesting another review.

### Record the reviewed comparison

Keep the review ledger in session state or outside the repository. For each review kind or axis, retain the reviewer's identity, task or authenticated result URL, outcome and findings, scope and requirements, full reviewed head SHA, base repository/ref and live base SHA, merge-base SHA, and the diff command used. Preserve the Git objects or an inspectable patch and base context so the original comparison can be reconstructed after refs move. For hosted reviews, establish the actual comparison from authenticated metadata or a captured round recording its head, base branch, and starting base SHA. An unbound result is incomplete evidence.

### Assess applicability after changes

1. Capture the new head, live base ref/SHA, and merge-base. Compare the original and current patch series, for example with [`git range-diff`](https://git-scm.com/docs/git-range-diff) using `git range-diff <old-merge-base>..<old-head> <new-merge-base>..<new-head>`. Inspect the aggregate diffs too when commits were split, squashed, or reordered. Preserve the command, compared OIDs, output or artifact location, and assessment.
2. Inspect every changed patch and conflict-resolution hunk in context. Compare base changes with `git diff <old-base> <new-base>` and inspect changes relevant to the reviewed behavior, requirements, dependencies, configuration, or security assumptions, including changes outside the patch's files. Equal patches alone do not establish applicability when upstream behavior changed. Range-diff is comparison evidence, not proof of arbitrary semantic equivalence.
3. Carry forward a clean review when the reviewed work remains equivalent and relevant assumptions still hold. Document why each patch difference or conflict resolution is inconsequential. Material behavior, requirement, or security changes need fresh review of the affected work and its interactions by the applicable review kinds or axes. Retain unaffected evidence with its scope. An ambiguous comparison, unavailable original context, or unexplained difference leaves applicability incomplete until inspection resolves it or fresh review covers it. An unresolved finding or a newer pending or adverse review cannot be bypassed by selecting an older clean result.
4. Record the decision separately from the original review. Identify the assessor, current comparison, retained result and actual reviewed SHA, evidence inspected, rationale, scope retained, and any fresh review needed. Repeat this assessment when the reviewed work or base branch changes again. Preserve the original provenance through successive carry-forwards, comparing against the actual reviewed work rather than treating an assessment as a new reviewer approval.

In handoffs, say that evidence from the original reviewed SHA was carried forward to the current comparison. Link the assessment and original result when linkable artifacts exist. For session-only or local records without URLs, identify the assessor and original reviewer/result, actual reviewed and current comparisons, retained scope, evidence inspected, and applicability rationale inline. Claim direct review only for the commit the reviewer inspected. A carry-forward does not waive required validation of changed implementation, history, branch-protection, and landing checks. Keep tested commits and trees separate from review evidence.

## Stop or remove a worktree

`make apps-stop` and `make infra-stop` stop this worktree's containers and preserve its data. `make infra-reset` deletes infrastructure data after confirmation.

For another checkout, run `git worktree add -b <branch> <path>` and `make install` in that directory. Each worktree gets separate ports, containers, and volumes.

Linked-worktree Compose project names come from Git's administrative worktree directory name. For example, `.git` pointing to `.git/worktrees/t3-3e761aad` produces `wallpaperdb-t3-3e761aad`. Branch switches, branch renames, and detached HEAD checkouts keep the same project name and persistent slot when installation reruns. The main checkout uses `wallpaperdb`, slot 0. See [setup](scripts/setup-worktree.mjs) and the [shared naming rule](scripts/lib/worktree-project.mjs) for normalization and the length limit.

Existing linked worktrees adopt this naming rule on their next installation. Stop any running stack under its previous project name before regenerating configuration. Setup does not migrate or delete previous containers or volumes.

Before removing a checkout, run `make worktree-remove` there. It releases the slot and deletes non-main worktree containers and volumes. Then use `git worktree remove <path>` from another checkout. If a directory was already removed, follow the stale-slot cleanup instructions printed by the next installation.

Normal [teardown](scripts/teardown-worktree.mjs) uses the project name saved in `.worktree` and preserves main-checkout volumes. Stale cleanup derives the project name from the administrative directory containing the supplied `worktree-slot` file, so it also works when that directory's HEAD file is missing.
