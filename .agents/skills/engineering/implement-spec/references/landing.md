# Land an explicitly requested stack

For both native stacks and ordinary PRs, immediately before landing or enqueueing, verify the main-targeting PR's base remains `main` with [gh pr view](https://cli.github.com/manual/gh_pr_view), then read the selected remote's current trunk SHA with [git ls-remote](https://git-scm.com/docs/git-ls-remote): `git ls-remote --exit-code --heads "<remote>" "refs/heads/main"`. Require exactly one result whose full OID matches the reviewed `main` SHA recorded by the final $implement-spec review. A failed lookup or missing comparison evidence blocks landing. Use this fresh remote-tip check even when PR metadata reports the recorded base OID. On a mismatch, fetch current `main`, rebase affected branches, apply the layer review and validation rules, and repeat the complete-spec review and validation before another attempt. Unchanged PR heads and base names alone do not establish that the reviewed comparison is current. Apply this gate again before each subsequent landing or queue submission after a partial landing.

When landing is explicitly requested, inspect the target branch's effective merge rules first. Without a merge queue, use GitHub's rebase method, or squash when the repository permits it. Invoke stack landing non-interactively with an explicit target and method: `gh stack merge "<stack-or-pr-number>" --yes --rebase`, or substitute `--squash`. Verify that the target resolves to the requested ready prefix before executing it. Immediately before landing or enqueueing, read every selected PR's authenticated head SHA and base branch, compare them with its recorded validated and reviewed commit and expected parent, and recheck native readiness. Stop on any mismatch, preserve external work, and repeat the affected review and validation before another attempt. The extension's [merge command](https://github.com/github/gh-stack/blob/v0.2.1/skills/gh-stack/references/commands.md#merge) has no equivalent to an atomic expected-head flag, so this preflight cannot guarantee protection against a subsequent concurrent push. If an atomic head match is required, report that limitation before landing. For an ordinary PR without a native stack, use [gh pr merge](https://cli.github.com/manual/gh_pr_merge) with `gh pr merge "<pr-url>" --match-head-commit "<validated-head-sha>" --rebase`, or substitute `--squash`. The matched SHA must be the full recorded validated and reviewed head; on a mismatch, refresh review and validation before another landing attempt. Land prerequisites before their dependents, or use the native atomic stack operation for a ready prefix when no merge queue applies.

If a merge queue applies, follow the extension's [queue behavior](https://github.com/github/gh-stack/blob/v0.2.1/skills/gh-stack/references/commands.md#merge). The queue overrides method flags and may land the requested PRs in separate groups. Before enqueueing a native stack, read `delete_branch_on_merge` from the selected repository with `gh api --hostname "<host>" "repos/<owner>/<repo>"`. Require it to be false; if it is true or cannot be established, report a blocker before queue submission. Branch deletion can close the first remaining PR at a group boundary, as shown in [the upstream reproduction](https://github.com/github/gh-stack/issues/444). Changing that repository policy requires a separate maintainer decision. Verify that the queue's configured method is rebase or an allowed squash before submitting; if it would introduce merge commits or its method cannot be established, report the blocker before enqueueing. Report queued PRs as queued until each reaches `main`. Verify each landing individually and apply the partial-landing rules below whenever only part of the prefix has landed.

After a partial landing, fetch `main` from the selected remote, rebase the remaining layers onto their new parents, and update the stack.

After any partial landing, record which PRs landed and the remaining layers' old parent boundaries. Follow [restacking and evidence refresh](stack-recovery.md#restacking), then [publish and preserve complete native membership](stack-recovery.md#publishing).

Follow the [issue landing policy](../../../../../docs/agents/issue-tracker.md#relationships): verify closing links when retargeting a layer to `main`, then issue closure and project status after verified landing. Report failed automation.
