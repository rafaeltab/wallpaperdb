title: Local CRAP scores
description: Use complexity and coverage to identify functions worth investigating.
---

CRAP combines cyclomatic complexity with test coverage. Use it to find functions that may need tests or refactoring. It does not measure developer performance or prove that behavior is correct.

```sh
make crap
make check-crap CRAP_THRESHOLD=30
```

Both commands run unit and integration coverage, including dependency builds. Docker is required. They analyze the repository by default; add `PACKAGE=<workspace>` to select one workspace. Run one CRAP command at a time, without another test run writing the same coverage directories.

`make crap` lists functions from highest to lowest score. `make check-crap` prints only functions above the supplied threshold and fails when any exceed it. Equality passes. The example threshold of 30 is a calibration value, not repository policy or a CI gate. A failed test or invalid coverage report fails the command rather than reusing stale coverage.

## Interpret the report

```text
CRAP = complexity² × (1 − coverage)³ + complexity
```

Coverage is a fraction from zero to one. The report uses the lower applicable statement or branch coverage; a branchless function uses statement coverage. Missing coverage counts as zero. A function with complexity 4 and 50% effective coverage scores 6; with no coverage it scores 20.

Only unit and integration coverage contributes. Libraries tested exclusively through E2E can therefore receive high scores despite having tests. Inspect the behavior and its tests before deciding what to change.

The inventory includes ordinary, async, and generator callbacks, including nested callbacks and curried wrappers such as `Effect.fn`. Each body receives its own score; nested decisions belong to the nested function. Source positions distinguish anonymous callbacks on the same line. Calling a wrapper or constructing an Effect does not establish coverage of its callback body.

The shared Vitest configuration enables AST-aware coverage remapping for Vitest 3; Vitest 5 already uses it. This preserves callback locations and source branches. Older V8 reports can omit anonymous function metadata or contain only function-entry branch counters. When those records cannot establish a function's own statement or source-branch coverage, the analyzer treats the measurement as missing and uses zero. A passing threshold does not prove that the tests establish correct behavior.

V8 can mark a generator's first yield covered when only its iterator has been created, before `.next()` runs. This provider limitation can overstate coverage for short generators. The [provider regression fixture](https://github.com/rafaeltab/wallpaperdb/blob/main/scripts/fixtures/crap/callbacks.test.ts) checks iterator creation separately from resumed execution.

The analyzer is maintained as the private `@wallpaperdb/crap-typescript-core` workspace. Its [upstream provenance and Apache-2.0 license](https://github.com/rafaeltab/wallpaperdb/blob/main/packages/crap-typescript-core/UPSTREAM.md) record the vendored baseline. [Issue #239](https://github.com/rafaeltab/wallpaperdb/issues/239) tracks evaluating an upstream contribution after sustained repository use.

The analyzer's tests and type checks run through the standard Turbo workspace tasks in CI. Use `make test-unit PACKAGE=crap-typescript-core` for its tests and coverage, and `make check-types PACKAGE=crap-typescript-core` for type checking. Root `make test-crap` runs the separate provider compatibility tests. The analyzer workspace participates in repository-wide CRAP reports like other packages.

For scope and exclusions, read [crap.config.mts](https://github.com/rafaeltab/wallpaperdb/blob/main/crap.config.mts). For orchestration and coverage handling, read [scripts/crap.mts](https://github.com/rafaeltab/wallpaperdb/blob/main/scripts/crap.mts). If a killed process leaves `coverage/.crap-lock`, confirm it is no longer running before removing the lock.
