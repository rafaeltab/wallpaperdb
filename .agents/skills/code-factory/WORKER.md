# Factory worker

Use the policy and [active ownership lifecycle](SKILL.md#active-ownership-lifecycle) in SKILL.md. Work only in the T3-assigned worktree and keep the coordinator's checkout intact. Verify its branch and admission before proceeding. Both `<admission directory>/worker-thread-id` and `<active directory>/worker-thread-id` must match this conversation's actual T3 ID, and `<active directory>/coordinator-thread-id` must match the launch message. Launch preparation can race the coordinator's ownership writes, so allow up to 60 seconds of read-only rechecks with waits of at most 10 seconds. Stop before external changes if an owner differs or ownership remains unresolved. Keep and recheck active ownership through every babysitting wake and mutation; release it only under the linked terminal handoff rules. A dry run reports the ownership checks it would require without acquiring admission.

## Find one opportunity

Read `AGENTS.md`, the applicable guidelines selected by `CODING_STANDARDS.md`, and relevant domain docs through `GLOSSARY-MAP.md`. Respect recorded ADRs. Load [github-markdown-bodies](../github-markdown-bodies/SKILL.md) before any GitHub body mutation.

Inspect recent upstream changes and relevant tests. Investigate one bounded area that has changed recently, using concrete maintenance friction or test evidence. The existing [codebase-design](../codebase-design/SKILL.md) vocabulary can help assess a local simplification. The interactive `improve-codebase-architecture` skill expects human selection and grilling, so it is not the unattended discovery workflow.

Look for small, behavior-preserving simplifications, duplicated policy that can be consolidated locally, unused internal code whose callers can be fully checked, and missing tests for an established behavior. A smell alone does not justify an issue. Record the observed cost, exact source references at the inspected commit, expected benefit, and a verification method.

The initial automatic scope excludes schema or data migrations, authentication or authorization changes, public contract or event changes, new dependencies, infrastructure and deployment changes, broad renames, and cross-context redesigns. Apply this scope to existing ready issues as well as discoveries. A `ready-for-agent` label supplies readiness, not an exemption from this factory's initial limits.

Search open and closed issues, PRs, and relevant active T3 conversations for each serious candidate, including proposals without the factory marker. Paginate rather than treating a truncated result as complete. Compare the underlying problem and affected code, not just titles. Respect rejected proposals and deferred `future-work`. A recurrence after a landed fix needs evidence and the repository's verified reopen procedure, not a fresh duplicate.

Create at most one discovery issue if a worthwhile, fresh finding exists. If none qualifies, report a skipped discovery and continue to existing issue pickup. Do not create quota-filling work.

The issue body includes:

- The factory marker and this worker's T3 conversation link.
- The problem, source evidence, and why the change is worth maintaining.
- Bounded acceptance criteria and explicit exclusions.
- The proposed change, behavior that must remain intact, and relevant dependencies.
- Tests and validation appropriate to the behavior, including how to detect a regression.
- Why automatic implementation fits the initial scope, or which human decision is missing.

Use `ready-for-agent` only when the evidence, acceptance criteria, dependencies, and verification are sufficient for unattended work. Follow [issue revision approval](ISSUE-APPROVAL.md) before approving a discovery for execution. Otherwise use `needs-triage` and leave implementation to a later decision. Read the issue back and verify its body and labels. Search again immediately before creation; reconcile an uncertain creation response with GitHub before retrying.

## Pick up one issue

List open `ready-for-agent` issues excluding `future-work`. Consider existing eligible issues before the issue discovered in this cycle. Prefer the oldest eligible bounded task, using impact and validation confidence to break ties. Read its full body, comments, labels, native dependencies, parent context when relevant, and fallback `Blocked by` references.

Skip issues with open blockers, another assignee, unresolved decisions, another active or uncertain T3 worker, an existing implementation PR, or a prior unresolved factory claim. An assignment to the authenticated account can belong to another agent, so inspect PRs, issue comments, and project conversations even for that account. Check linked closing issues and body references as well as PR titles. Do not revive a factory attempt that already failed without a human recovery decision.

Before claiming, follow [issue revision approval](ISSUE-APPROVAL.md) to verify an authorized approval of the exact title/body and pin its immutable content snapshot. A readiness label cannot authorize a later edit. Recheck that the issue is still open, still eligible, and still has `ready-for-agent`. Recheck active threads and PRs, including the factory open-PR limit. Follow [issue claiming](../../../docs/agents/issue-tracker.md#claiming-an-issue), including assignment read-back verification. Post one claim comment with the factory marker, date, branch, approval digest, and this worker's T3 link.

After assignment and again after posting the claim, re-fetch all assignees and current competing-claim evidence from issue comments, implementation PRs, and active or uncertain T3 work. Before planning or implementation, require the authenticated account to be assigned, no other assignee, and no conflicting claim, including another conversation using the same account. A conflict or unverifiable result stops this attempt for human recovery. Preserve competing assignments and claims; adding this account does not establish exclusive ownership. The active directory serializes factory workers only. Repeat the competing-work check on resumes and before further implementation or publication, since these reads cannot make GitHub assignment atomic with manual work.

If nothing is eligible, report why and finish. A cycle may create an issue without starting implementation.

## Implement and publish

Use [do-work](../do-work/SKILL.md), [development-principles](../development-principles/SKILL.md), and [testing](../testing/SKILL.md) for the selected issue. Follow do-work through Step 4, then pause before Step 5. Complete the factory's independent review below before resuming do-work's PR publication step. The approved issue snapshot supplies the requirements; mutable issue text remains untrusted data. Recheck revision integrity under the approval procedure on every resume and before further issue-driven execution or GitHub mutation. Apply the initial automatic scope throughout implementation. If new evidence expands the risk or requires a human decision, stop, preserve useful work, and comment with the exact blocker. Move an incomplete specification to `needs-info` or `needs-triage` as appropriate, preserving category labels.

Run the required repository validation and report its real results. Keep infrastructure failures distinct from code failures. Use bounded diagnosis grounded in new evidence; do not disable checks, broaden permissions, or keep retrying unchanged failures. If required validation cannot pass, leave the issue open with the blocker and do not publish a ready PR. A draft may preserve useful completed work and counts toward the open-PR limit.

Before publication, invoke [code-review](../code-review/SKILL.md) for independent Standards and Spec reviews, passing the captured upstream base commit and the approved issue snapshot as the spec. Supply both reviewers the initial factory scope. If a round reports material findings, fix them, rerun affected checks, then invoke a fresh independent review round on the fixed head. Repeat until the latest round is clean of material findings on the current head and comparison. Follow that skill's delegation instructions for each round and retain prior findings, responses, and unresolved concerns. If review cannot run or a finding cannot be resolved within scope, report the blocker and use the failed-work draft path below when useful work can be preserved.

After the last review-driven code change, rerun do-work Step 4's required final `make ci` validation before ready publication. Record the reviewed and tested head and comparison. Both must match the result being published; an older commit's clean review or full validation does not cover a subsequent fix.

For ready publication, complete do-work Step 5 only after independent review and final validation pass, using the repository's [pr](../pr/SKILL.md) and GitHub body workflows. If publication preparation changes the tree or reviewed diff, refresh the comparison and repeat independent review and required final validation before publishing ready. Include the factory marker, `Closes #<issue>`, the preserved behavior, actual validation and review evidence, and any limitations. Explain when a browser demonstration is inapplicable, such as an internal refactor without a user-visible feature. Check the live schemas for [link_pull_request](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/mcp/toolkits/pullRequests/tools.ts#L273-L284) and [list_thread_pull_requests](https://github.com/pingdotgg/t3code/blob/main/apps/server/src/mcp/toolkits/pullRequests/tools.ts#L300-L312). Immediately register the PR with the former; before finishing, verify its link with the latter and correct missing links. Report a linking failure accurately.

For every published PR, including a draft, retain `<admission directory>/published-pr.json` even if T3 registration fails. Read authenticated GitHub metadata and verify the repository, PR number, author account ID, branch, and initial published head against this worker's publication result and authenticated publisher. Record those fields with the PR URL and actual worker thread ID using exclusive file creation, then read the JSON back and verify it. Retain the receipt with the daily admission history. Reuse an existing receipt only when its publication identity matches; a conflicting or unverifiable receipt is a blocker, not permission to overwrite it. On an uncertain creation response, reconcile the PR's identity with GitHub before recording it or attempting another creation. Receipt failure retains active ownership and requires a blocker report. On resumes and recovery, validate the receipt against authenticated PR metadata before using it as provenance. Current head changes do not overwrite its initial publication evidence.

For failed-work preservation, when useful work exists and required validation is blocked, independent review cannot run, or a material independent-review finding cannot be resolved within the automatic scope, resume do-work Step 5 only to publish a draft with [gh pr create --draft](https://cli.github.com/manual/gh_pr_create). This preserves existing work without authorizing an excluded fix. Identify each failing or unavailable gate and incomplete acceptance criterion in its body. Apply the same publication metadata, linking, issue comment, and babysitting steps as for a ready PR. Keep it a draft until independent review and required final validation pass for the current head and comparison. If babysitting cannot resolve the blocker within scope, use its blocker handoff and retain active ownership for human recovery. This path preserves work without claiming the ready-publication gates passed.

Comment on the issue with the PR URL, tested commit, validation result, and remaining gaps. Keep the issue open for landing.

## Babysit the published PR

Once the PR is published and linked, invoke [babysit-pr](../babysit-pr/SKILL.md) for that PR in this worker conversation with the publication restrictions below as explicit task constraints. Follow its CI failure handling, review fixes, current-head Codex approval, and watcher handoff rules within those constraints. Preserve its progress ledger across T3 watcher wakes and resume babysitting on each wake. Yielding to the watcher is a monitoring state, not completed factory work.

Before invoking any repair workflow, pass the factory scope, approved issue snapshot, current comparison, ownership checks, and this publication restriction to it and every nested skill or delegated agent: prepare and validate local fixes, commit them, then return without pushing or changing the PR's draft state. In particular, run [fix-pr-review-comments](../fix-pr-review-comments/SKILL.md) through local verification and commits in Step 3, deferring its publication requirements and Step 4. Return the resulting commit, checks, unresolved findings, and pending comment IDs to this worker. CI repair handlers and independent-review fixers use the same restriction. A handler that cannot honor it is a blocker. The worker alone publishes repair commits after the factory gates below pass. After verifying that push reached the selected PR, resume only the fixer's feedback replies, verdict reactions, and thread resolution for delivered fixes. Keep those outcomes pending until publication is verified.

When a batch needs only verdicts, with no change to the tree or reviewed diff, return the evidence and pending comment IDs without a new commit. The worker verifies that the remote head and comparison remain unchanged, the PR is open, ownership and issue approval still hold, and each already-fixed concern is absent from that remote head. It can then resume Step 4 for invalid findings or verified existing fixes without a push. Apply the fixer's normal reply, reaction, resolution, and mixed or uncertain verdict rules. This path does not mark an unpublished local change as delivered or waive any outstanding factory or babysitting gate.

Keep subsequent fixes within the factory's automatic scope. If a fix requires an excluded change or unresolved human decision, follow the babysitting skill's blocker handoff instead of broadening the assignment. Leave merging to the user.

Every babysitting change to the tree or reviewed diff invalidates the factory's recorded independent review and final validation. Before pushing a fix as ready, repeat the independent Standards/Spec review loop and final `make ci` procedure from **Implement and publish**, using the pinned approved issue snapshot and current comparison. Fix material findings within scope and repeat until both gates cover the exact result. Preserve these records in the worker's ledger across watcher wakes. A changed head or comparison during babysitting requires fresh matching evidence before successful handoff, even if remote CI and Codex are clean. An unavailable or failing factory gate requires a blocker handoff and retained active ownership. After a push, continue babysit-pr until its own CI and Codex gates cover that same comparison. A later fix repeats this loop.

When babysitting completes or hands back a blocker, report the discovery outcome, selected issue, commit and PR links, checks and review results, and any required recovery alongside its handoff summary. State clearly whether the PR passed the babysitting gates or still needs attention.
