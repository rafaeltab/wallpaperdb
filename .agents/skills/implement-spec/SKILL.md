You have been provided a spec and its implementation tickets. Read them through the repository's [issue tracker](../../../docs/agents/issue-tracker.md).

For a spec with multiple tickets, the goal is one linear GitHub PR stack, with one branch and PR per ticket. The bottom PR targets `main`; each subsequent PR targets the previous ticket's branch. The top branch contains the complete spec.

For a single-ticket spec, create an ordinary branch from current `main` and a draft PR targeting `main`. Apply the implementation, review, validation, and issue-closure steps below. Pushing the validated branch and opening its draft PR through [do-work](../do-work/SKILL.md) and the publication rules below remain mandatory. Skip extension setup and all `gh stack` commands; use the ordinary-PR path for explicitly requested landing. A [native remote stack requires at least two PRs](https://github.com/github/gh-stack/issues/467); the single ticket still implements the complete spec.

Tickets form a dependency graph. Implement them one at a time in an order that puts every prerequisite before its dependents. Independent tickets also become successive stack layers. Apply the issue tracker's readiness rule to every prerequisite, including tickets with multiple blockers.

Use rebase to incorporate changes from `main` or an earlier layer. Do not use `git merge` or introduce merge commits.

Communication with subagents should use context pointers to the spec, tickets, research notes, parent branch, and commits. Keep temporary exploration notes outside the repository, accessible to later subagents.

Use one implementer subagent at a time in a single worktree for the stack. Each ticket gets its own branch in that worktree. Review and validate its work before starting the next ticket; its PR can remain open while later tickets are implemented.

## Prerequisites

Before installing or invoking the extension, check `gh --version` and `git --version`. Require GitHub CLI 2.13 or newer for [matched-head ordinary PR merges introduced in 2.13](https://github.com/cli/cli/releases/tag/v2.13.0) and pinned extension installation, and Git 2.36 or newer per the extension's [installation requirements](https://github.com/github/gh-stack/tree/v0.2.1#installation). Compare numeric version components. Stop on an unsupported or unparseable version before changing repository configuration or creating branches.

The `gh stack` commands require the [GitHub CLI extension](https://github.com/github/gh-stack) at [v0.2.1](https://github.com/github/gh-stack/releases/tag/v0.2.1), the release used to verify this workflow's command behavior. If the extension is missing, use the CLI's [pinned installation](https://cli.github.com/manual/gh_extension_install): `gh extension install github/gh-stack --pin v0.2.1`. Check `gh stack --version` for `0.2.1` before executing workflow commands, then check `gh stack --help`. Stop on a different installed version; review its provenance and behavior before changing the pin. Use the release's [command documentation](https://github.com/github/gh-stack/blob/v0.2.1/skills/gh-stack/SKILL.md) and local command help for supported options.

Require generated and adopted ticket branch names to match `^[A-Za-z0-9][A-Za-z0-9/_-]*$` and pass Git's [branch-name validation](https://git-scm.com/docs/git-check-ref-format) with `git check-ref-format --branch "<ticket-branch>"`. Require remote names to match `^[A-Za-z0-9][A-Za-z0-9._-]*$`. Reject incompatible names before command construction. Pass dynamic values as separate process arguments; when using a shell, quote them as literal data rather than pasting ticket text into command source or evaluating it.

## Steps

1. Read the spec, full tickets, comments, and blocking relationships. Choose an order that respects the dependency graph. Resolve missing prerequisites or cycles before starting affected tickets.

2. Select and record the remote whose fetch and push URLs resolve to the authenticated target repository. For all CLI operations in this workflow, export [GH_REPO](https://cli.github.com/manual/gh_help_environment) to that repository's `HOST/OWNER/REPO` and verify `gh repo view "<host>/<owner>/<repo>" --json nameWithOwner,url` resolves to it. This also binds stack API calls to the publishing repository, addressing the extension's [multi-remote repository-resolution limitation](https://github.com/github/gh-stack/issues/381). Apply the [temporary Git configuration rules](#temporary-git-configuration) before setting the selected push-default remote. Pass `--remote "<remote>"` to stack commands that support it, following the extension's [non-interactive guidance](https://github.com/github/gh-stack/blob/v0.2.1/skills/gh-stack/SKILL.md#non-interactive-use).

   For multiple tickets, check repository capability before initializing branches or starting an implementer. Require write access from `gh repo view "<host>/<owner>/<repo>" --json viewerPermission`. Use `gh api --hostname "<host>" --paginate "repos/<owner>/<repo>/stacks"` with the selected repository and current credential. This is the read-only availability check used by [the extension's submit implementation](https://github.com/github/gh-stack/blob/v0.2.1/cmd/submit.go) and [stack-list API client](https://github.com/github/gh-stack/blob/v0.2.1/internal/github/github.go). A successful empty list is valid. If permissions are insufficient or the API fails, report the error and stop before implementing tickets; native stacks remain the requested output. Investigate authentication or API failures instead of interpreting every error as a disabled feature.

   Before switching branches, updating the trunk, or initializing, require `git status --porcelain` to be empty, including staged, unstaged, and untracked files. Preserve unrelated work in a separate worktree or an explicitly recorded stash; commit ticket work in its owning layer and repeat validation. The extension's [add behavior](https://github.com/github/gh-stack/blob/v0.2.1/skills/gh-stack/references/commands.md#add) carries uncommitted changes onto the new branch.

   Fetch `main` from that remote and record the fetched commit. If `refs/heads/main` is missing, inspect [worktree ownership](https://git-scm.com/docs/git-worktree) with `git worktree list --porcelain`; if no worktree owns that branch, create it with [git branch](https://git-scm.com/docs/git-branch): `git branch main "<fetched-main-sha>"`. Stop if ownership prevents creation or a concurrent ref appears. For an existing local trunk, fast-forward only when it is an ancestor of the fetched commit. Require `git rev-parse "refs/heads/main"` to equal the full fetched SHA before creating or adopting ticket branches. An already-up-to-date result does not prove equality when local `main` is ahead. If local `main` is ahead or diverged, preserve its commits and report a blocker before initialization; do not reset it or include those commits in ticket work. Follow Git's [fetch](https://git-scm.com/docs/git-fetch) and [ref-update](https://git-scm.com/docs/git-update-ref) rules, including worktree ownership when updating the trunk.

   Choose and record a branch name for every ticket. For a new run, require each name to be absent locally and on the selected remote. Check the remote with [git ls-remote](https://git-scm.com/docs/git-ls-remote): `git ls-remote --exit-code --heads "<remote>" "refs/heads/<ticket-branch>"`. Exit code 2 establishes absence; exit code 0 is a collision, and any other failure blocks creation. Choose a different unused name on collision. Repeat the check immediately before each branch creation, including later `gh stack add` calls. The extension's [init behavior](https://github.com/github/gh-stack/blob/v0.2.1/skills/gh-stack/references/commands.md#init) decides adoption from local refs, so a remote-only branch is unsafe to initialize as new.

   Exact absence is insufficient for hierarchical refs. Before implementing any ticket, enumerate local heads with [git for-each-ref](https://git-scm.com/docs/git-for-each-ref): `git for-each-ref --format="%(refname)" refs/heads/`, and remote heads with `git ls-remote --heads "<remote>"`. For each new branch, compare its full ref with those heads and every other planned ticket ref. Reject equality or a slash-boundary prefix in either direction, such as `refs/heads/ticket` and `refs/heads/ticket/2`. Choose another name and repeat the checks on collision; listing errors block creation. Repeat this namespace check immediately before each new branch creation. For continuation, permit the exact ref being verified and adopted, while rejecting conflicting other refs.

   For requested continuation, follow [continuation checks](references/continuation.md) before adopting branches or resuming ticket work. They align fetched and local refs and reuse or rebuild existing tracking.

   For a new multi-ticket run, temporarily enable rerere under the configuration rules below to avoid the extension's [first-run confirmation](https://github.com/github/gh-stack/blob/v0.2.1/skills/gh-stack/references/commands.md#init), then initialize with `gh stack init --base main "<first-ticket-branch>"`. For a new single ticket, create its ordinary branch instead. Consult `gh stack "<command>" --help` for command options. Branch targets alone do not register a native GitHub stack.

3. Select the next ready ticket. Use the branch prepared in step 2 for the first ticket. For each later ticket, repeat step 2's clean-worktree check before adding a branch on the validated stack tip with `gh stack add "<ticket-branch>"`. Check out the ticket branch in the stack worktree. Give the implementer pointers to the ticket, spec, worktree, and exact parent commit. The implementer:
   - confirms the ticket branch is based on that parent before starting;
   - uses [tdd](../tdd/SKILL.md) and follows the repository's [development principles](../development-principles/SKILL.md);
   - validates the ticket and reports its commits and results before another implementer starts.

4. Use [code-review](../code-review/SKILL.md) on the ticket's changes against its parent branch. Fix findings in the ticket branch and rerun affected checks, then repeat the parent-relative review on the resulting head. Continue until both review axes pass for the current parent and layer commits, with no unresolved findings. Record only that passing commit pair with the ticket's evidence. Any further change invalidates that record until the rebase rules establish an identical diff or a fresh review passes. The ticket is implemented for stack readiness only once its acceptance criteria, validation, and review pass.

5. Follow [do-work](../do-work/SKILL.md) for validation and the publishing rules below. Write a ticket-specific title and body using [pr](../pr/SKILL.md) and [github-markdown-bodies](../github-markdown-bodies/SKILL.md), then publish a draft PR. Include the ticket's closing reference and link to the spec. The first publication creates an ordinary PR; register the native stack once the second PR joins it. Record the PR URL and validated commit in the ticket so later implementers can verify prerequisite readiness.

6. Repeat steps 3 through 5 for each remaining ticket. When `main` or an earlier layer changes, restack before continuing or publishing. Follow the rebase rules below for every affected layer's recorded commit and validation evidence.

7. Once all tickets are implemented, repeat step 2's clean-worktree and fetched-trunk checks using the selected remote before each complete-spec review iteration. Align local `main` with that freshly fetched SHA under those preservation rules, then restack affected layers and apply the rebase evidence rules below. Use [code-review](../code-review/SKILL.md) on the top branch against `main` to review the complete spec. Put each fix in the ticket layer that owns it, then rebase descendants and apply the layer review and validation rules above. Validate the combined result on the top branch and repeat the complete-spec review after any fixes or rewrites. Continue until both review axes pass for the current top SHA against the current `main` SHA, and record that passing pair before step 8. A later top or trunk change requires another complete-spec review before readiness.

8. Immediately before marking PRs ready and handing off, read the selected remote's actual `main` tip with [git ls-remote](https://git-scm.com/docs/git-ls-remote): `git ls-remote --exit-code --heads "<remote>" "refs/heads/main"`. Require exactly one result matching step 7's recorded reviewed trunk SHA. On a mismatch, return to step 7 to refresh the trunk, restack, review, and validate before readiness. A failed lookup blocks handoff. Read every PR's authenticated head SHA and base branch with [gh pr view](https://cli.github.com/manual/gh_pr_view), verify its repository identity, and compare its head with the recorded passing layer commit and its base with the expected parent. Apply this check to ordinary PRs too. On a mismatch, preserve and inspect remote work, restore the intended parent relationship, and repeat affected layer review and validation and step 7 before readiness. Mark the PRs ready for review and report the stack's PR URLs, validation results, and native GitHub stack status. Apply the issue tracker's [landing and issue-closure policy](../../../docs/agents/issue-tracker.md#relationships). Opening PRs or completing implementation does not authorize landing the stack.

9. If a temporary stack worktree was created, clean it up after all commits are published, preserving the stack branches and PRs.

## Temporary Git configuration

Before changing either [remote.pushDefault](https://git-scm.com/docs/git-config#Documentation/git-config.txt-remotepushDefault) or [rerere.enabled](https://git-scm.com/docs/git-rerere), record each key's local presence and all values with `git config --local --get-all "<key>"`. Install cleanup before the first mutation. Use `git config --local --replace-all remote.pushDefault "<remote>"` for the selected publishing remote. For multi-ticket work, use `git config --local --replace-all rerere.enabled true` before any stack initialization, including continuation and catalog recovery.

On every exit, including success, failure, interruption, or handoff, restore each changed key's recorded local values. Remove the temporary entry when no local entry existed, allowing inherited configuration to apply again; leave inherited settings intact. Preserve multiple values in their original order. Verify restoration and report any cleanup failure. Retain the original records outside the repository across resumed work; do not overwrite them with temporary values. Git's [configuration documentation](https://git-scm.com/docs/git-config) defines the local scope and replacement/removal operations.

## Publishing

Apply the ancestry, merge-commit, and validation checks in [do-work](../do-work/SKILL.md#5-open-a-pr). Keep each branch's last verified published tip separate from remote-tracking refs; a new branch expects absence. Before every publication, compare all active stack branches' actual remote heads with those recorded expectations. Stop on any difference, including a newly appeared branch. Fetch and preserve external work, then restack, review, and validate it before recording a new expectation.

Push each validated branch using Git's [explicit expected-value lease](https://git-scm.com/docs/git-push#Documentation/git-push.txt---force-with-leaseltrefnamegtltexpectgt): `git push --force-with-lease="refs/heads/<ticket-branch>:<recorded-remote-tip>" "<remote>" "refs/heads/<ticket-branch>:refs/heads/<ticket-branch>"`. Use an empty expected tip for a new branch. On rejection, reassess and validate the new remote state before retrying. Read back the remote head and update the published-tip record only after it matches the tested commit. Publish changed layers from the bottom upward, retaining verified tips after a partial publication failure.

Create the draft PR using [gh pr create](https://cli.github.com/manual/gh_pr_create) with an explicit repository, parent base, head branch, title, and body file. For an existing PR, use [gh pr edit](https://cli.github.com/manual/gh_pr_edit) to update its parent target and body after verifying the PR identity. For initial native registration with at least two PRs, call `gh stack link --base main "<bottom-pr-url>" ... "<top-pr-url>"` in stack order. Pass only verified PR URLs; the extension's [link implementation](https://github.com/github/gh-stack/blob/v0.2.1/cmd/link.go) skips Git pushes for PR URL arguments. Verify native stack membership and readiness after linking. Use the explicit-lease publication path for restacks too, because the extension's [fetch-then-lease behavior](https://github.com/github/gh-stack/issues/380) makes `gh stack submit` and `push` unsuitable for preserving recorded remote expectations.

For restacks, partial landings, or additions to an existing native stack, follow [membership preservation](references/stack-recovery.md#preserve-native-membership) before updating it. Verify the full remote membership, including merged PRs.

## Rebasing and landing

Use `gh stack rebase --remote "<remote>"` to rebase the stack onto the updated trunk and cascade changes through descendants. Preserve the old parent tips before rewriting history. For manual rewrites or stale local tracking, follow [stack recovery](references/stack-recovery.md) before further stack operations.

Refresh every rewritten layer's recorded commit in its ticket issue, even when its file tree is unchanged. Reuse successful validation for an identical tree and record that comparison; rerun required checks for changed trees. Apply this rule after every history rewrite, including restacks and partial landings.

Compare each layer's diff against its new parent with the diff between its recorded reviewed commits. If that diff changes, invalidate the old layer review and repeat step 4 before treating the ticket as ready or publishing it. If the diff is identical, record the comparison and refresh the reviewed commit pair. A tree comparison alone does not establish that the parent-relative diff is unchanged.

Publish rewritten branches and update their PR targets and native membership using the publishing rules above. PR mergeability alone does not establish native stack readiness.

When the user explicitly requests landing, follow [landing rules](references/landing.md) to verify reviewed heads, select rebase or an allowed squash, and handle merge queues and partial landings.
