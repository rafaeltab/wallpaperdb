---
title: Diagnose a running service
description: Follow a failure through application logs, Grafana, and background delivery.
---

Run `make help` to find this worktree's ingress address, then open its `/grafana/` path. Local defaults are `admin` / `admin` unless overridden. Fixed ports from other worktrees will show the wrong stack.

## Follow a failing operation

1. Capture the failing request, time, service, and any trace ID. Use `make apps-logs SERVICE=<service>` for application logs, or `make infra-logs` when a dependency will not start.
2. Open Grafana's **WallpaperDB** dashboard folder. Choose the relevant service and time range to check failures, latency, and background processing.
3. In **Explore**, select **Tempo** and search by trace ID or the configured service name. Follow the request and downstream event processing to the failed boundary.
4. Select **Loki** to inspect nearby logs. Use the service label shown in the data, then filter by trace ID where available. Startup failures remain visible in container logs even when telemetry cannot reach the collector.

Dashboard queries and alert conditions live in [infra/grafana](https://github.com/rafaeltab/wallpaperdb/tree/main/infra/grafana). Consult those definitions for metric names instead of maintaining a separate metric catalog. Save dashboard changes back to the provisioned JSON; edits made only in Grafana are not the repository's configuration.

## An upload succeeded but is missing from search

Acceptance and downstream projection happen separately. Check the producing service's outbox, consumer health, pending JetStream deliveries, and quarantine before retrying or replaying input. A working wallpaper URL does not prove that event ingestion or search projection is healthy.

A full or unavailable quarantine leaves the original delivery pending. Repair the cause or restore capacity; preserve the source event's identity during replay. The [recovery guide](/docs/guides/service-upgrades) covers exhausted legacy consumers, historical message-size failures, and quarantine reconstruction.

## Quotas stopped being enforced

Gateway admits requests without quota enforcement when Redis is disabled, unavailable, failing commands, or locally saturated. The `admission.quota.unenforced` metric's `reason` attribute distinguishes these cases. Ingestor instead falls back to bounded instance-local quotas, which do not enforce a fleet-wide limit. Check the provisioned degradation alerts and Redis health before treating either fallback as normal operation.

## Telemetry is missing

- Check the service's configured `OTEL_EXPORTER_OTLP_ENDPOINT` and collector health. Docker applications need an endpoint reachable from their network; a host's localhost endpoint does not refer to the collector inside an application container.
- Check the selected time range and actual service labels. An idle service may have no new request spans; check worker and dependency signals separately.
- Inspect application startup logs and Grafana data-source health before changing instrumentation. Telemetry exporter failures should not require deleting application data or restarting the whole stack.

When adding instrumentation, follow [composition and operations guidelines](https://github.com/rafaeltab/wallpaperdb/blob/main/docs/coding-standards/composition-and-operations.md). Keep private values out of telemetry and use spans, rather than metric labels, for per-request identifiers.
