# CI failure handling

Inspect failed-job logs and artifacts before retrying. For an untrusted head, follow [artifact isolation](untrusted-heads.md#pr-produced-artifacts) before retrieving, extracting, or inspecting files from CI. Use [diagnosing-bugs](../../../engineering/diagnosing-bugs/SKILL.md) for reproducible defects that need a code fix, and [development-principles](../../development-principles/SKILL.md) and [testing](../../testing/SKILL.md) for changes and focused Make checks. For CI-only intermittent failures, logs, artifacts, and matching historical CI runs may establish the flake classification below. Document why a local reproduction is unavailable; it is not a prerequisite for the issue-and-retry path. Publish tested fixes to the PR's actual head branch under the [existing-PR publication rule](../SKILL.md#1-establish-the-target-and-retain-progress).

Apply [diagnosing-bugs' redaction rule](../../../engineering/diagnosing-bugs/SKILL.md#redact) to every CI path, including classification without a local loop. Before displaying or publishing evidence in comments or issues, replace secrets with `<REDACTED>` and quote only the lines needed to establish the failure. Sanitize captured artifacts before sharing them; [Playwright traces](https://playwright.dev/docs/trace-viewer#network) can include network headers and bodies. Keep unsanitized artifacts private, and return a blocker if safe evidence is insufficient.

Fix failures caused by this PR, including failures in tests that existed before it. Classify a failure as a pre-existing flaky test only with evidence of intermittent behavior and evidence that the PR did not cause it. Compare the diff and use base-branch reproduction or matching historical failures where practical. An unchanged test, a single successful rerun, or inability to reproduce does not establish that classification. Escalate uncertain causes with the evidence gathered.

For a proven pre-existing flaky test, search open and closed GitHub issues for the same failure. Reuse an open matching issue and append the current recurrence evidence. If only a closed match exists, inspect its closure rationale; reopen it when the recurrence disproves a claimed fix, or create a linked successor when the prior disposition should remain intact. Require an open tracking issue before retrying. Include the test name, failure signature, failing run and job links, affected commit, intermittent-failure evidence, and evidence that the PR did not introduce it in the new issue or recurrence comment. Follow [issue-tracker](../../../../../docs/agents/issue-tracker.md), use `needs-triage` for a new issue, and apply [github-markdown-bodies](../../github-markdown-bodies/SKILL.md) when publishing bodies. Retain the open issue URL in the ledger.

For a proven transient infrastructure failure, such as a hosted runner, action download, or external service outage, record the failing run and job, failure signature, and evidence distinguishing the outage from a PR regression or persistent configuration problem. Rerun failed jobs within the budget below. For a cancelled run with no failed jobs eligible for that operation, rerun the entire selected workflow using [gh run rerun](https://cli.github.com/manual/gh_run_rerun) with its run ID and without `--failed`. Require the same proven-outage classification, current-comparison validation, and retry budget; a full rerun consumes one retry. This path does not require a flaky-test issue; retain the infrastructure evidence in the ledger. Uncertain causes, permission failures, and persistent setup defects require diagnosis or a blocker rather than an automatic retry.

For proven pre-existing flaky tests, rerun only failed jobs after recording the open issue. Immediately before any rerun, refresh the authenticated PR head, base ref, and base SHA and require them to match the recorded failure comparison. Verify the selected run belongs to that head and comparison; if either changed or the comparison cannot be established, reassess current runs instead of rerunning the stale failure. For failed-job reruns, use [gh run rerun](https://cli.github.com/manual/gh_run_rerun) with the selected run ID and `--failed`. Both the flake and transient infrastructure paths allow at most two reruns for the same failure on the same commit by default; the user may specify a different limit. Repeated occurrences across jobs, classifications, or monitoring wakes share that budget. A new CI failure needs diagnosis rather than automatic classification as the same cause. If the budget is exhausted and CI remains red, return a blocker. Filing an issue does not satisfy the CI gate, and passing on retry does not remove the issue from the final report.

Permission failures and infrastructure failures require a concrete blocker report when the agent cannot remedy them within the authorized scope.
