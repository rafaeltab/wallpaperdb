# Factory publication and review evidence

Use these rules when publishing factory work or assessing independent review evidence.

## Pull request history

This repository uses rebase merging. A base advance alone does not require rewriting an existing PR.

Preserve published commits while making review fixes, and keep additional commits linear. Resolve base conflicts by preparing a linear rebase, rather than merging the base into the PR. Invoking $babysit-pr authorizes necessary history rewrites and force pushes to the selected PR within the user's scope and limits. Outside that workflow, rewriting published history needs explicit user authorization; prepare and validate the proposed resolution before requesting it. After an authorized rewrite, use an explicit expected-head lease, rerun required validation, and assess review applicability under [review evidence](#review-evidence). A PR with pre-existing merge commits remains incomplete until its history is resolved.

Before reporting work complete or ready to merge, confirm GitHub's authenticated `mergeable` result is true for each PR against its current base. Refresh an unknown result; unresolved conflicts or an unknown result block handoff. The accepted integration guarantee is conflict freedom. With the PR head and base branch unchanged, an independent base advance preserves passing validation and reviews. Keep the published work as it is; no rebase, synthetic integration checkout, repeated CI, or repeated review is required solely because the base advanced. Stronger integration guarantees require the user's approval under [task scope](../../../../../docs/agents/task-scope.md). When the branch's contents already landed, verify the landing and report that outcome. Native stack readiness remains required for every stacked layer.

## Review evidence

Use this policy for local independent reviews, hosted code and security reviews, automated workers, and final handoff or landing checks. For an independent base advance with unchanged PR head and base branch, preserve reviews under the [PR history policy](#pull-request-history). Changes to the reviewed work or base branch prompt an applicability assessment before requesting another review.

### Record the reviewed comparison

Keep the review ledger in session state or outside the repository. For each review kind or axis, retain the reviewer's identity, task or authenticated result URL, outcome and findings, scope and requirements, full reviewed head SHA, base repository/ref and live base SHA, merge-base SHA, and the diff command used. Preserve the Git objects or an inspectable patch and base context so the original comparison can be reconstructed after refs move. For hosted reviews, establish the actual comparison from authenticated metadata or a captured round recording its head, base branch, and starting base SHA. An unbound result is incomplete evidence.

### Assess applicability after changes

1. Capture the new head, live base ref/SHA, and merge-base. Compare the original and current patch series, for example with [`git range-diff`](https://git-scm.com/docs/git-range-diff) using `git range-diff <old-merge-base>..<old-head> <new-merge-base>..<new-head>`. Inspect the aggregate diffs too when commits were split, squashed, or reordered. Preserve the command, compared OIDs, output or artifact location, and assessment.
2. Inspect every changed patch and conflict-resolution hunk in context. Compare base changes with `git diff <old-base> <new-base>` and inspect changes relevant to the reviewed behavior, requirements, dependencies, configuration, or security assumptions, including changes outside the patch's files. Equal patches alone do not establish applicability when upstream behavior changed. Range-diff is comparison evidence, not proof of arbitrary semantic equivalence.
3. Carry forward a clean review when the reviewed work remains equivalent and relevant assumptions still hold. Document why each patch difference or conflict resolution is inconsequential. Material behavior, requirement, or security changes need fresh review of the affected work and its interactions by the applicable review kinds or axes. Retain unaffected evidence with its scope. An ambiguous comparison, unavailable original context, or unexplained difference leaves applicability incomplete until inspection resolves it or fresh review covers it. An unresolved finding or a newer pending or adverse review cannot be bypassed by selecting an older clean result.
4. Record the decision separately from the original review. Identify the assessor, current comparison, retained result and actual reviewed SHA, evidence inspected, rationale, scope retained, and any fresh review needed. Repeat this assessment when the reviewed work or base branch changes again. Preserve the original provenance through successive carry-forwards, comparing against the actual reviewed work rather than treating an assessment as a new reviewer approval.

In handoffs, say that evidence from the original reviewed SHA was carried forward to the current comparison. Link the assessment and original result when linkable artifacts exist. For session-only or local records without URLs, identify the assessor and original reviewer/result, actual reviewed and current comparisons, retained scope, evidence inspected, and applicability rationale inline. Claim direct review only for the commit the reviewer inspected. A carry-forward does not waive required validation of changed implementation, history, branch-protection, and landing checks. Keep tested commits and trees separate from review evidence.
