# Factory host operations

Use the existing Linux host and authenticated headless T3 installation. The service uses the host user manager, not the desktop or a product container. Read the [configuration template](.env.example) and [Make interface](../../Makefile). Keep credentials private and restrict the listener to loopback or the existing tailnet IP. No public ingress is supported.

## Install and activate

Run `make install` and `make toolchain` in a clean, committed source checkout. Run `make run PACKAGE=factory SCRIPT=service:install ARGS='/absolute/releases'`. The [installer](scripts/install.ts) builds that commit, copies the built application and resolved dependencies into a separate commit-named directory and records commit, tree, lock digest and Node executable in `installation.json`. Keep that pinned Node installation available. Never edit an installed release. An existing release is retained rather than overwritten.

Create private configuration and state directories outside the releases. Copy the environment template to a private `factory.env`, fill the project path, pinned comparison and target branch, exact installed T3 binary, and host tailnet IP with an unused port. Set exactly one unquoted `FACTORY_STATE=/absolute/state` assignment. Duplicate or overriding assignments are rejected before the active unit changes. Preserve the installed T3 host and unrelated listeners. Verify its headless CLI supports worktree/model selection before admitting work. MCP question observation and cancellation also require a dedicated authenticated MCP client as described in the [workspace guide](README.md).

Verify `systemctl --user is-system-running` and `loginctl show-user "$USER" -p Linger`. Lingering must already be enabled for operation after logout. Do not change global host policy as part of activation.

Run `make run PACKAGE=factory SCRIPT=service:activate ARGS='/absolute/releases/COMMIT /absolute/config/factory.env /absolute/state wallpaperdb-factory-NAME'`. The [activation command](scripts/activate.ts) checks state compatibility before replacing its dedicated user unit and explicitly restarting it. It enables only the named unit. Check `systemctl --user status wallpaperdb-factory-NAME`, its journal, and `http://zerotwo:PORT/health`. A running manager alone does not prove application health. Inspect startup errors and correct configuration or dependency availability before resuming admission.

## Upgrade and recovery

Install the desired committed version alongside the old release. Run the same activation command with its new commit path and the same configuration, state and service identity. The operation restarts the factory without waiting for every external worker to finish. It does not cancel T3 workers. The service lock excludes overlapping service processes using that state directory. Direct development launches do not take this lock; do not mix them with the installed service on the same state.

The SQLite release uses format 2 internally and imports format-1 JSON records in a single transaction. Original files, including an existing `format.json`, remain untouched. After import, all production readers use SQLite exclusively. New claims and revisions are never written back to legacy files. The [generated migrations](drizzle/) and [migration entry point](src/main.ts) ship with the [installer](scripts/install.ts). SQLite connections close after each operation, including failures. Configured startup and migration-only paths require an explicit database root and resolve directory aliases to physical paths. Standalone directory aliases are supported; symlinked database files and declared durable namespace entries are rejected. Nested adapter namespaces share that root; an existing ancestor database or a nested database in a declared state namespace makes explicit initialization fail before reconciliation. Resolve that layout with the supervising operator while all writers remain stopped.

For the JSON-to-SQLite upgrade, the supervising operator must stop the old service and take a consistent backup of the entire state directory immediately before migration. Keep the old release, unit, and private configuration. Do not delete claims or start a second writer. With the old service stopped, run `make run PACKAGE=factory SCRIPT=db:migrate ARGS='/absolute/state'`. The installed equivalent is `PINNED_NODE /absolute/release/main.js --migrate-only /absolute/state`. It takes the same nonblocking `service.lock` as the installed service, applies generated migrations, validates/imports legacy records, prints only format and record count, and exits without contacting GitHub or T3. Repeating it is idempotent. Failed imports commit no records and can be retried after investigation without changing originals.

Verify a copied backup using migration-only, never a second full factory against real retained job records. Pausing admissions does not prevent reconciliation from sending to existing external workers. Use controlled external protocols for full startup verification. After independent acceptance, activate the new release against the migrated state, then inspect health, retained jobs and controls. Activation accepts legacy format 1 for automatic import and rejects a JSON release against a directory containing SQLite. Direct old binaries cannot recognize SQLite, so never bypass that check.

Rollback before the new factory has performed any external effects can restore the complete pre-upgrade backup with the old release while stopped. Once SQLite has advanced claims, reverting to the original JSON files is unsafe because they are stale. Retain the complete current SQLite directory and use a compatible SQLite release, or reconcile every post-upgrade external effect before considering a backup restore. Back up only while stopped, including the database and any journal files. Never copy only legacy JSON files as a current-state backup.

After restart inspect the dashboard's existing jobs and controls. The service reconciles external observations against durable records before advancing work. Unknown non-idempotent launch or send outcomes remain visibly pending for operator investigation. Availability of GitHub, T3 and the local filesystem remains necessary for reconciliation. Neither restart nor the native stack tool provides cross-resource atomicity, external cancellation completion, or universal exactly-once execution.

## Controlled rollout and daily use

Start with concurrency one and one distinct admission. Preview the semantic plan or deliberately select an eligible issue with retained scope context. Observe the issue, stage, elapsed time and issue/T3/PR links. Pause admissions while current work continues, adjust limits with the current revision, and explicitly resume parked work only after answering in its T3 thread. Removing readiness does not cancel active work. Cancellation is a distinct explicit control.

Use controlled external protocol endpoints and isolated Git/state when demonstrating this workflow without authorized real implementation/model/PR side effects. Label synthetic issue/PR identities and operator-asserted acceptance/reviews. Such a demonstration proves the installed production service and UI integration; it does not establish live model correctness or default-branch landing.

Implementation, independent Standards/Spec/Defects review, publication and current-tree CI remain separate stages. SIMPLE restacks require current-tree CI; COMPLEX changes require independent review-loop and CI. Required acceptance/review/CI must bind the actual current comparison before dependents proceed. Factory-ready PRs are handed back for manual merge; issues remain open until verified default-branch landing. Mutation and hosted model/security feedback are advisory. Preserve `$do-work` for manual single-issue work and `$babysit-pr` for repairs. Complete-spec acceptance remains a separate coordinator responsibility.

The [v2 command worker](src/composition/v2.ts) retains accepted responsibility through temporary SQLite failures and retries with backoff capped at thirty seconds. A computed result is retried only for persistence, without repeating its command. If a failed claim is later found committed, the receipt becomes uncertain and requires reconciliation; it never authorizes repeating external work. Restart retains the existing uncertain-command policy. See [command processing](src/capabilities/board/implementation.ts).

## Retention and retirement

Keep the active release, configuration, complete durable state and its owned unit for acceptance and recovery. Inspect logs with `journalctl --user -u wallpaperdb-factory-NAME`. Stop and disable only that unit with `systemctl --user disable --now wallpaperdb-factory-NAME` when retiring it. Remove only its unit after retaining its release identity and state backup, then reload the user manager. Stop the service before a filesystem backup. Retain old releases until compatibility and recovery have been checked; never silently delete useful demonstration state or unrelated services.

## Availability monitoring

For a monitored installation, set `FACTORY_OTEL_ENDPOINT` to the existing LGTM collector's OTLP HTTP endpoint. The [availability observations](src/composition/availability.ts) export `factory_scheduler_healthy` and `factory_scheduler_observed_at_seconds` through the [scoped metrics transport](src/composition/metrics.ts) to `/v1/metrics` every ten seconds, using a runtime-owned metric registry. A completed scheduler observation reports healthy or failed and its timestamp. Idle, paused and question-waiting observations can be healthy. A technical failure or a returned absent/ambiguous binding for retained work reports unhealthy even while `/health` remains live and the scheduler tick returns successfully. An observable failed run awaiting an explicit operator action remains available; the signal does not classify known work outcomes as dependency outages. A stuck observation stops advancing the timestamp. Export requests and shutdown are bounded; telemetry remains optional and does not control admission outcomes.

The [factory Grafana rules](../../infra/grafana/provisioning/alerting/factory.yaml) use the existing Prometheus data source. OTLP's dimensionless health unit becomes the Prometheus name `factory_scheduler_healthy_ratio`; the timestamp declares seconds and remains `factory_scheduler_observed_at_seconds`. The [infrastructure Compose service](../../infra/docker-compose.yml) mounts the alerting provisioning directory into LGTM. One rule detects failed reconciliation; the other detects observations older than two minutes or absent for five minutes, with a further two-minute pending period. A stale observation can mean a long-running reconciliation; inspect the owning operation before intervention. These are monitoring thresholds, not workflow deadlines or retry authorization.

When deploying the combined source, provision the rules in the existing monitoring installation, configure the factory's collector endpoint, and verify samples and alert state through that installation's established notification routing. Confirm healthy observations, then inspect failure and missing-signal conditions without sending real notifications during a controlled check. A source file or controlled collector test alone does not establish a running alert or notification delivery. Do not restart or modify an unrelated monitoring installation to apply a ticket repair.

With `FACTORY_OTEL_ENDPOINT` absent, the factory exports neither traces nor metrics, including when a generic OTLP environment variable is present. Intentionally unmonitored operation must disable the factory missing-signal rule in the monitoring configuration; absent data cannot distinguish that choice from process loss. Leave the rule enabled for deployments expected to be monitored. Keep collector credentials and filesystem paths out of metric labels.

## Local persistence durability

The [SQLite connection setup](src/platform/durable.ts) requires DELETE rollback journaling with `synchronous=EXTRA`. SQLite [documents EXTRA](https://www.sqlite.org/pragma.html#pragma_synchronous) as synchronizing the journal directory after commit, preserving the last committed claim across power loss when the local filesystem and storage honor synchronization. Initialization also fsyncs the database directory and its ancestors before returning responsibility. This retains the local Linux filesystem assumption of the original publisher. Process-kill and reopen tests verify transaction/restart behavior; they do not simulate a power failure or establish storage-device guarantees.

## Planner attempts and confirmed rejection recovery

[Planner attempts](src/capabilities/plan/attempts.ts) are advisory operations. `POST /api/plan` accepts an empty JSON object and returns HTTP 202 with an attempt `id` and `Location`. Observe `GET /api/plan/<id>` for progress, elapsed time, bounded failure details and the validated result. New attempts have a 600000 ms overall deadline covering gathering issues, handoff, model work including on-demand retrieval, and freshness validation. [Automatic planning](src/capabilities/plan/scheduler.ts) starts the same deadline before its preliminary discovery. Historical attempts retain their recorded identities and deadlines across upgrades and restarts. HTTP disconnect does not cancel the service-owned attempt. A busy response advertises `attemptId` only for an existing attempt resource. Legacy or automatic planner ownership instead exposes `requestId` and an outstanding or reconciliation-required reason. Handoff progress does not establish launch ownership.

The [initial message](src/adapters/t3/planner-message.ts) is a flat Candidate/Context metadata index with compact active or parked issue numbers. It omits issue bodies, comments and full job objects. The prompt requires full issue bodies and trusted maintainer comments before selection, with parent and dependency requirements retrieved as needed. Internal full inputs remain available for freshness and eligibility validation.

A bound run that completes after timeout can be reconciled before the next submission. An unbound uncertain launch remains protected. The [T3 adapter](src/adapters/t3/planner.ts) privately captures the complete message at `<FACTORY_STATE>/planner/planner-message-<encoded-requestId>.txt`, then sends that same string over UTF-8 stdin. Its 120000-character transport guard counts JavaScript UTF-16 code units before launch intent; JSON escaping is not part of that count. No normal numeric message budget has been chosen. The adapter never truncates context; the existing transport guard remains the only message-size ceiling.

Only an explicit server non-launch rejection authorizes retiring an unbound claim. An empty thread search does not establish rejection. For a legacy claim with confirmed T3 `-32602` validation rejection, the supervisor must stop the service, retain a consistent complete SQLite backup, and run the pinned compatible release's supported command:

```sh
"$NODE" "$RELEASE/main.js" --reconcile-planner-rejection \
  "$STATE" "$REQUEST_ID" "$EXPECTED_REVISION" "$OPERATOR" \
  'Explicit server -32602 validation rejection; retained log reference and timestamp'
```

`STATE` is the absolute factory state root. `RELEASE` is the installed release directory and `NODE` its pinned Node executable. The [command](src/main.ts) takes the service lock and requires an exact outstanding unbound request and revision. It appends the operator, evidence reference, rejection code and timestamp to a new planner revision. Original input, request, deadline and earlier revisions remain intact. Stale commands and bound claims fail without retiring them. The command neither starts the service nor launches workers. Review its bounded JSON receipt, then restart the compatible release and verify health and observation. Never run the old JSON release against current SQLite state. Deployment and this recovery are supervisor actions.

## T3 metadata and links

The independent background metadata refresh uses the configured MCP endpoint and authorization file with `t3_environment_read` and paginated `t3_thread_list`. It does not call thread read/show or cache conversations. Missing MCP access is reported as a failed observation and preserves last-known metadata. `/api/threads` and the scheduler's `threads` field read local SQLite snapshots only. See the [metadata adapter](src/adapters/t3/metadata.ts), [observation contract](src/capabilities/observe/index.ts) and [generated migrations](drizzle/).

T3 observations supplement durable factory bindings. Titles never establish issue ownership. Explicit T3 PR links can be joined to GitHub closing references; absent and conflicting associations remain explicit. The metadata list does not expose branch/worktree bindings, so those fields use existing factory execution evidence where available and otherwise remain null. These observations never authorize dispatch, admission, or planner freshness.

`FACTORY_T3_CONNECT_ORIGIN=https://app.t3.codes` enables the browser action for environments with Connect access. Omit it when Connect is unavailable. Only an HTTPS origin without credentials or a path is accepted. The browser still requires the user's T3 authentication. Desktop actions use `t3code://threads/<environmentId>/<threadId>`, with each identity segment encoded separately. Unknown environment identity disables links. The desktop OS handler must already be installed; automated checks never invoke it.

The supported routes and protocol registration were verified in T3 source at `680152e27b2a961686389ca69a1557cbb2c55f08`, including `packages/shared/src/promptLinks.ts`, `apps/desktop/src/electron/ElectronProtocol.ts`, `apps/desktop/src/app/DesktopLinuxUrlHandler.ts` and `apps/web/src/components/desktop/DesktopWebLinkCoordinator.tsx`, and installed nightly `0.1.7-nightly.20261103.4119`. `t3-thread://v1` and `v2` are T3 Markdown references, not external OS/browser URLs. Source support and encoded link checks do not establish a user-device launch.
