title: User Service

The User Service owns WallpaperDB's public Profiles. It verifies Clerk-authenticated Users, persists authoritative Profile state and Handle claims in PostgreSQL, and records typed Profile events for downstream consumers.

**Status:** 🚧 In Development

## Quick Start

```bash
# Start infrastructure
make infra-start

# Run user service in development mode
make dev PACKAGE=user

# The service starts on http://localhost:3009
```

## Features

### Core Functionality
- **Authenticated Profile creation** through an idempotent ensure command
- **Optimistic Profile editing** with authoritative command responses and conflict detection
- **Handle changes** with a seven-day cooldown and atomic alias retention for existing Profile links
- **Unique Handle allocation** with normalization, reserved-name protection, collision retries, and monotonic claim generations
- **Transactional Profile events** recorded in an outbox with the authoritative Profile snapshot
- **Health checks** for database and message queue connectivity

### Observability
- **OpenTelemetry** traces and metrics
- **Structured logging** with Pino
- **Health checks** for all dependencies

## Architecture

### Event Flow

```
Web + Clerk JWT → User Service → PostgreSQL (Profile + Handle claim)
                                      ↓ same transaction
                                Profile event outbox
```

### Database Schema

```typescript
profiles {
  id: text                    // Clerk user ID and primary key
  displayName: text
  handle: text                // Case-insensitively unique
  biographyMarkdown: text
  pictureAssetId: text | null
  version: integer
  lastHandleChangedAt: timestamp | null
  createdAt: timestamp
  updatedAt: timestamp
}

handleClaims {
  handle: text                // Case-insensitively unique claim
  profileId: text
  kind: text
  claimGeneration: bigserial // Monotonic projection conflict tiebreaker
  createdAt: timestamp
  expiresAt: timestamp | null // Scheduled aliases keep their claim during the grace period
}
```

## API Reference

### POST /profile/me/ensure

Verifies the Clerk bearer token and idempotently creates or returns the signed-in User's authoritative Profile. A failed Clerk identity lookup returns `503 Service Unavailable` and persists nothing.

### PATCH /profile/me

Updates the signed-in User's Display name. The request supplies `displayName` and the last-seen `expectedVersion`. Display names preserve casing and Unicode while trimming and collapsing whitespace, and default to an 80-Unicode-character limit. Stale versions return `409 Conflict` without changing Profile state or recording an event. A successful command returns the authoritative updated Profile immediately and records a versioned `profile.updated` event in the same transaction.

### PUT /profile/me/handle

Changes the signed-in User's Handle using `{ "handle": "new-name", "expectedVersion": 2 }`. Normalization produces lowercase ASCII letters, digits, and single hyphens; configured length bounds apply afterward and technical names are reserved. A successful transaction claims the new Handle, retains the former Handle as an alias, increments the Profile version, and records the complete public snapshot. Owners may promote their own retained aliases back to the current Handle after cooldown.

The command returns `400` for invalid Handles, `409` for collisions or stale versions, and `429` with `nextHandleChangeAt` during the seven-day cooldown. Repeating the unchanged normalized Handle at the current version returns unchanged state. Authenticated Profile responses include `aliases`, `retainedAliasLimit`, and `lastHandleChangedAt`; GraphQL resolves aliases without enumerating them publicly. Each alias includes its Handle, claim generation, retention start (`createdAt`), and nullable `expiresAt`. Former addresses redirect to the current canonical Handle after projection catches up.

`PROFILE_RETAINED_ALIAS_LIMIT` defaults to three and accepts non-negative integers. A Handle change that exceeds this limit schedules the oldest retained aliases for expiry 24 hours later, ordered by `createdAt` and then Handle. Scheduled aliases immediately stop counting toward the limit. Promoting an owned alias back to the current Handle clears its expiry and frees that alias slot before capacity is checked. The Handle change, scheduling, version increment, and complete event snapshot are atomic.

### DELETE /profile/me/aliases/:handle

Schedules an owned alias for expiry using `{ "expectedVersion": 2 }`. The response includes the complete updated owner Profile and the exact alias `expiresAt`, 24 hours after acceptance. This records a versioned `alias-expiry-scheduled` change with the Handle and before/after expiry values. Repeating the command for an already scheduled alias at the current version returns unchanged state.

Stale versions return `409`, malformed commands return `400`, and a Handle that is not an owned alias returns `404`. Scheduling keeps the alias claim reserved and its redirect available. The later expiry worker releases the claim; scheduling alone does not release it when its timestamp passes. Settings confirms the 24-hour redirect grace before scheduling and displays the authoritative expiry afterward.

## Configuration

Environment variables (Zod-validated):

```bash
# Server
PORT=3009
NODE_ENV=development

# Database
DATABASE_URL=postgresql://wallpaperdb:wallpaperdb@localhost:5432/wallpaperdb_user

# NATS
NATS_URL=nats://localhost:4222
NATS_STREAM=WALLPAPER

# OpenTelemetry
OTEL_EXPORTER_OTLP_ENDPOINT=http://localhost:4318
OTEL_SERVICE_NAME=user

# Clerk
CLERK_SECRET_KEY=sk_test_...
CLERK_PUBLISHABLE_KEY=pk_test_...

# Profile Handles
PROFILE_HANDLE_MIN_LENGTH=1
PROFILE_HANDLE_MAX_LENGTH=30
PROFILE_DISPLAY_NAME_MAX_LENGTH=80
PROFILE_RETAINED_ALIAS_LIMIT=3
```
