# Saved performance results in the prototype lab

The lab’s `/performance.html` page reads a published file snapshot. It does not
query OpenSearch, run evaluations, poll indexing, or start benchmarks.

The page separates:

- The 545-image correctness corpus (523 real images plus 22 synthetic fixtures):
  saved human preference feedback, case support, and the known duplicate-target
  arithmetic caveat.
- One million records with a narrow workload projection: only the fields used
  by the fixed screening queries are present.
- 100,000 records with each method’s full schema.
- One million records with a full schema: incomplete indexing remains separate
  from query measurements.
- Other and earlier scopes, including the 100,000-record projection.

Every campaign keeps its method, query, filter, concurrency or arrival rate,
p95, timed strict failures, warmup failures, request count, and completion state.
Closed-loop p95 includes successful requests only; arrival p95 includes scheduled
delay and failures. A fast successful p95 never hides timed errors or warmup
failures. Missing measurements do not become passes. Index names, utility counts,
controls and artifact hashes remain available in each campaign’s details.

Interrupted closed-loop campaigns can contain requests that never reached a
completed profile. The inventory now reconciles a matching independent audit
with the raw request log and shows those observations separately. Campaign-wide
failure totals and unfinished request counts remain visible even when filters
hide every completed profile. They do not create a final profile, p95 or
viability result. With no valid audit, pending totals are explicitly unavailable;
zero completed-profile errors never implies zero campaign errors.

The independent audit must match the campaign directory and the parsed
benchmark, plan and archived-source object hashes. The inventory additionally
streams and hashes the current raw log and reconciles its counts/error union.
Older audits did not hash their raw log: the displayed raw SHA identifies bytes
at inventory time, not a historical signature from the audit. Original evidence
and older public checkpoints remain untouched.

## Publication contract

The only served summary is:

`/home/rafaeltab/.local/share/wallpaperdb/color-evaluation/exploration/favorite-optimization/2026-09-23/favorite-performance-public-summary.json`

Use a completed checkpoint generated by `favorite-optimization-results.mjs` and
reviewed against its raw evidence. Retain its complete schema, then add:

```json
{
  "publication": {
    "sourceCheckpoint": "results-checkpoint-20260923-v5.json",
    "publishedAt": "2026-09-23T16:00:00.000Z",
    "sourceSha256": "SHA-256 of the exact original checkpoint bytes"
  }
}
```

Write a new temporary regular file in the same directory, flush it, then replace
the fixed public file atomically. Preserve the original checkpoint. This allows
future audited checkpoints to appear without code changes or server restarts.
The page displays both snapshot and publication times. An incomplete build’s
count is explicitly **at the snapshot**, not live progress.

The reader uses a constant file path, rejects symlinks and nonfiles, limits the
file to 8 MiB, and verifies the schema’s fixed experiment root. The HTTP endpoint
does not accept query parameters or arbitrary file paths. Failed reads return an
unavailable message instead of exposing filesystem errors. Dynamic page text is
inserted through DOM text nodes.

## Published snapshots and limits

The initial publication uses checkpoint v5, generated at
2026-09-23T16:01:29.385Z. It records completed C1 screens, six feedback runs, and
an incomplete full-million build. C4, C16 and scheduled arrivals remain
unmeasured in that snapshot. No performance estimate is extrapolated to a full
million or 100 million wallpapers.

Checkpoint v7 was published at 2026-09-23 16:26:35 UTC after independent review;
v6 remains preserved and unpublished. It adds duplicate-weight correctness and
accuracy-only feedback, plus three-primary-shard correctness on one physical
node. The eight performance campaigns are unchanged from v5. Its full-million
build is still incomplete at 257,922 acknowledged records with no verified final
count. This is historical progress at that snapshot, not a current live count.
The page reads future audited publications without a restart.

Scale records are synthetic mixtures; feedback comes from one observer’s
development judgments. The measured scale environment is one shared host/node,
8 CPU limit, 4 GiB heap, 12 GiB memory limit, one primary and zero replicas. Warm
queries and changing sets of open indexes limit cross-campaign comparisons.
The page displays these caveats directly.

## Verification

`make color-favorite-performance-test` tests scope separation, strict failures,
missing measurements, feedback support, partial build progress, fixed-file
access, and safe failures. Lab route tests cover the HTTP integration separately.
An offline DOM test executes the page script and confirms that interrupted errors
remain visible after filters hide all completed profiles, without adding a fake
measurement row or making extra network requests.
The UI is a read-only view of the existing result aggregator; scorers, indexers
and benchmark sources are unchanged.
