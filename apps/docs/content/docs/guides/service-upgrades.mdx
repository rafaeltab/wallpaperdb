---
title: Service upgrades and retained work
description: Deployment ordering, legacy recovery, and replay procedures for existing installations.
---

Use this guide when upgrading an existing installation. Fresh local setup is in [CONTRIBUTING.md](https://github.com/rafaeltab/wallpaperdb/blob/main/CONTRIBUTING.md). These procedures preserve historical data and work that ordinary restarts cannot recover.

Apply generated database migrations before starting the corresponding new service. Deploy each service's complete `dist` directory: native image workers and deferred application chunks are required at runtime.

## Immutable asset references

Storage adapters derive addresses from logical references and the image metadata in events. Keep `S3_BUCKET` consistent across Ingestor, Variant Generator, Color Extractor, and Media. Keep `PROFILE_PICTURE_BUCKET` consistent between User and Media. Consumers need read access to their producers' objects; only owners may delete bytes. [ADR 0008](https://github.com/rafaeltab/wallpaperdb/blob/main/docs/adr/0008-resolve-assets-through-stable-object-layouts.md) records why these layouts are stable contracts.

When upgrading a development installation from the descriptor-registry revision, stop producers while upgrading all applications together. Before switching, compare its descriptors against the deterministic layouts and configured buckets. Preserve any mismatching object and its descriptor, and migrate it deliberately before replaying its logical reference. The current layout preserves the original, variant, and Profile-picture paths; matching assets need no copy or reset. The old `asset-references` bucket is no longer a runtime dependency. Leave retained descriptors intact until the audit and replay checks are complete. Rolling back to descriptor-based binaries also requires descriptors for assets created after the switch; the old descriptor records alone are insufficient.

Do not rename buckets or change layouts through configuration alone. A migration must preserve object bytes and identities and account for producer records, Media's stored locations, and retained messages. Historical coordinate-based events continue to use their recorded locations. Back up the object buckets with their owning databases and configuration, and verify restore and replay together. The production release procedure and Grafana alerts that reach a human are tracked in [issue 236](https://github.com/rafaeltab/wallpaperdb/issues/236).

## Quarantine replay

Media, Color Extractor, and Variant Generator share a replay decoder in [`@wallpaperdb/core/quarantine`](https://github.com/rafaeltab/wallpaperdb/blob/main/packages/core/src/quarantine/index.ts). Ordinary single records and raw chunk manifests retain their formats and identities. Header-heavy inputs use a manifest with `encoding: "original-message-v1"` to archive their complete original headers and bytes inside bounded chunks. Upgrade replay tooling to read this format before processing those records.

Read a manifest's chunk sequences in order and pass their data with the manifest to `decodeQuarantineReplay`; pass a single record without chunks. The decoder validates bounded metadata, lengths, and SHA-256 before restoring original bytes and CloudEvent/trace headers, including repeated values. Do not silently normalize invalid metadata: repair it deliberately before replay. Archived broker publication controls are excluded from replay. Publish to the recorded original subject with a fresh broker publication ID, preserving the original CloudEvent occurrence instead of the quarantine envelope's identity.

Partial chunks without a completed manifest do not establish durable handoff. Failed writes leave the original pending; restore capacity or broker availability so the application can retry. Restrict quarantine access because it contains original events.

## Ingestor

The CloudEvents upload migration requires consumer-first deployment:

1. Upgrade every Media, Variant Generator, Color Extractor, and User replica to a revision whose `@wallpaperdb/events` accepts both legacy uploads and CloudEvents. Upgrade Gateway's event intake too if it predates CloudEvents support.
2. Drain and stop all old Ingestor replicas.
3. Apply the Ingestor migrations with `make migrate PACKAGE=ingestor`, then start the new Ingestor.

Older upload consumers reject the new envelope and can terminate deliveries. Upgrading them afterward does not trigger ordinary redelivery. Keep support for both formats while either can be retained or replayed.

The migration prepares legacy reservations and outbox recovery metadata in one transaction. Incomplete committed records stop migration for repair; investigate those records and rerun the migration rather than making their originals eligible for cleanup. Keep committed originals and their metadata intact. The [Ingestion context decisions](https://github.com/rafaeltab/wallpaperdb/tree/main/apps/ingestor/docs/adr) explain the compatibility limits.

## Media

Apply migrations without resetting the delivery catalog. Legacy reconciliation preserves stored metadata and can emit one new availability announcement because older releases had no publication ledger.

Startup rejects a legacy consumer with a finite `MaxDeliver` and recorded redeliveries. Increasing that limit cannot revive already exhausted messages. Recover it with every Media replica stopped:

1. Save `manager.consumers.info(stream, durable)` to an operator-owned file. Verify that source history still contains the required messages. Do not purge it.
2. Record `saved.ack_floor.stream_seq + 1` as the restart sequence. Previously acknowledged legacy omissions need a separately chosen earlier replay point.
3. Delete only the affected durable and recreate it with the same filter, explicit acknowledgements, unlimited broker delivery, and the recorded sequence:

```ts
await manager.consumers.delete(stream, durable);
await manager.consumers.add(stream, {
  durable_name: durable,
  ack_policy: AckPolicy.Explicit,
  max_deliver: -1,
  filter_subject: saved.config.filter_subject,
  deliver_policy: DeliverPolicy.StartSequence,
  opt_start_seq: saved.ack_floor.stream_seq + 1,
});
```

4. Restart Media and monitor dependency and consumer health, pending outbox work, and quarantine.

The durables are `media-wallpaper-uploaded-consumer` and `media-wallpaper-variant-uploaded-consumer` on the configured wallpaper stream, and `media-profile-picture-snapshots` on `PROFILE`. New consumers bound application processing attempts while broker redelivery remains unlimited when quarantine is unavailable.

`MEDIA_QUARANTINE` has a thirty-day repair horizon, one-GiB capacity, and discard-new overflow. Startup rejects incompatible policies. Export or repair failures before expiry. Failed quarantine writes leave originals pending; restore NATS or capacity so they can retry.

Use the [shared quarantine replay procedure](#quarantine-replay), including its framed-record decoder. See the [Media decision](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/media/docs/adr/0001-replay-safe-delivery-catalog.md).

## Gateway

Upgrading projections does not recover information older versions discarded. Existing color projections lack occurrence ordering metadata, so the first stale result after upgrade can replace their colors. Replay the complete retained color history before reopening catalogue traffic if historical ordering must be preserved. The same applies to timestamp precision lost by older millisecond-only projections.

The wallpaper and Profile source streams admit messages up to 64 KiB including headers. Quarantine and the broker's `max_payload` must each allow at least 256 KiB for the quarantine envelope. Gateway startup fails before subscribing when these limits are incompatible.

Gateway quarantine stores the original payload in `data.original` and complete NATS headers in `data.originalHeaders`, both base64 encoded. Decode both fields for replay, preserving the original occurrence and trace metadata while excluding archived broker publication controls. Choose a fresh broker publication ID. Oversized duplicate diagnostic fields may be omitted; the replay evidence remains intact. This format is separate from the three services' [chunked quarantine protocol](#quarantine-replay).

Lowering a stream limit does not rewrite retained messages. Gateway audits retained payload and header bytes before first consumption. Its `wallpaperdb.gateway.quarantine-budget` stream metadata records the stream creation time, configured limit, policy version, and audited sequence. Version 2 replaces the earlier payload-only audit. Matching certificates avoid repeated history scans; the initial scan takes time proportional to retained history.

An oversized historical message stops startup and reports its stream, sequence, and byte count. The original remains stored. Export the identified record, for example with `nats stream get WALLPAPER <sequence> --json`, determine its retention and replay requirements, and explicitly resolve that record before restarting. Do not purge the source stream to bypass the failure.

An administrative change that loosens a source limit must remove its audit certificate before larger publications are accepted, even if the old limit will later be restored. Stream recreation or a changed limit also requires another audit. Change the event-size contract, quarantine capacity, and audit policy together. See the [Gateway projection decision](https://github.com/rafaeltab/wallpaperdb/tree/main/apps/gateway/docs/adr).

Deployments retaining `GRAPHQL_MAX_COMPLEXITY=1000` must raise it to admit the web browse query under descendant-aware costing; the current default is 2000. Clients inspecting failed health probes must read the health classification from `healthStatus`; `status` is now the numeric Problem Details HTTP status.

## User

Drain old User replicas before applying `0010_dark_terrax.sql` and `0011_faithful_skrulls.sql`, then start the new image. These migrations add picture upload/deletion recovery states and outbox trace context. Do not run older picture cleanup workers alongside the new state machine.

If startup rejects the legacy `WALLPAPER/user-wallpaper-ownership` consumer for a finite delivery limit and recorded redeliveries:

1. Stop every User replica. Save the consumer configuration and acknowledgement floor, and verify retained history.
2. Recreate only that durable with explicit acknowledgements, the `wallpaper.uploaded` filter, unlimited broker delivery attempts, and a starting sequence one greater than the saved acknowledgement floor. Startup diagnostics include that sequence. Use the same NATS recovery pattern described for [Media](#media).
3. Restart User and monitor consumer health. Duplicate projection is safe because the first accepted owner remains authoritative. Application processing still stops after three attempts and requires durable quarantine before acknowledging failed input.

`USER_QUARANTINE` uses discard-new storage with a 64-MiB bound and thirty-day retention. A full or unavailable quarantine leaves delivery unacknowledged. Restore capacity or repair the failure before replaying affected input.

### Private pictures and evidence

Provision the Profile picture bucket without anonymous access, including any custom `PROFILE_PICTURE_BUCKET`. Do not put Profile pictures in a public wallpaper bucket. Set the same `USER_MEDIA_SERVICE_TOKEN` in User and Media, with Media's `USER_SERVICE_URL` pointing to User's internal origin. Worktree setup generates these settings for Docker development. For host-based development, use the reachable host User URL and the same token in both services. Never expose this token in browser configuration. A missing or mismatched token makes picture delivery fail closed.

Removing a picture stops future origin delivery; it cannot recall immutable copies already cached by browsers or a CDN. Replaced and removed originals remain private until their recorded expiry. Changing the configured retention duration does not rewrite existing asset deadlines.

Local evidence cleanup removes only published event rows and expired private picture candidates. It preserves current Profiles, active assets, Handle claims, and undelivered events. Delayed publication does not extend Handle reactivation eligibility. It does not erase downstream projections or retained NATS history; the temporary event-retention policy is tracked in [issue #162](https://github.com/rafaeltab/wallpaperdb/issues/162).

If telemetry is intentionally disabled, also disable the missing-signal alert. Otherwise operators will receive an alert for the absence they configured. See the [User workflow decision](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/user/docs/adr/0001-effect-profile-workflows.md).

## Enrichment workers

Deploy a Gateway that accepts CloudEvents color results before upgrading Color Extractor. Stop legacy worker replicas before relying on durable quarantine, because they retain their earlier termination behavior. Broker-exhausted legacy messages require operator replay; changing the consumer configuration does not recover them automatically.

Variant Generator and Color Extractor quarantine have a thirty-day repair horizon and one-GiB capacity with file-backed storage and discard-new overflow. Startup rejects incompatible policies. Explicitly migrate existing Color stream settings while preserving retained evidence.

Both workers use the [shared quarantine replay procedure](#quarantine-replay). Inputs that exceed the complete message budget or JetStream's 64 KiB header limit after quarantine metadata is added use bounded chunks and, when necessary, the versioned original-message frame. Every chunk and the completion manifest require durable acknowledgement before the source is acknowledged. Monitor pending inputs, quarantine capacity, and publication failures.

Existing variant object keys are immutable. Changing encoding settings affects new targets; replay does not regenerate an existing rendition with new settings. Deliberate regeneration needs a separately designed versioned target identity. See the [Variant Generator decision](https://github.com/rafaeltab/wallpaperdb/blob/main/apps/variant-generator/docs/adr/0001-replay-safe-variant-generation.md).

New variant announcements report their actual encoded dimensions. Existing variants retain the dimensions previously announced for their immutable targets, including historical nominal preset dimensions; replay does not rewrite those facts.
