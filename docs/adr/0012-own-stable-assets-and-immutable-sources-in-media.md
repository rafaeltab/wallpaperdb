# Own stable Assets and immutable Sources in Media

Status: accepted target direction in [#391's consolidated resolution](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6313111831), extended by [#256's generation and selection resolution](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525). Partially supersedes ADRs 0008 and 0009 and the Media/User/Ingestor local lifecycle clauses. Final specifications and production implementation remain #259 work.

The current context is the [Asset service](../../apps/asset/GLOSSARY.md). Historical Media decision names and links remain unchanged.

Media owns the complete lifecycle of a stable Asset containing immutable Source renditions. Applications retain their domain identities and references to Media-assigned Asset IDs. Changed bytes receive new Source IDs; accepted membership can change without changing the Asset ID. This replaces producer-owned immutable Asset identity and byte lifecycle, and keeps reusable technical acceptance and delivery policy inside Media. Configured Asset types select generic policies; no separate Publication identity or domain callback decides Source acceptance.

Applications authorize their domain operations through durable commands in Media's language. Author Source operations use the independent Owner authentication described in [ADR 0010](0010-authenticate-media-owners-through-configured-identity-providers.md). Media verifies mandatory admission rules before changing accepted membership. Supplementary inspection can continue afterward, preserving unchanged delivery and the conservative readiness/failure contract. Failed replacement retains prior membership. An Asset may start empty; after first acceptance, Source management cannot empty it. [ADR 0011](0011-unlink-profile-pictures-before-asynchronous-media-deletion.md) records terminal deletion and asynchronous Profile unlink.

Media retains the processed, cropped square Profile picture as its accepted immutable Source. Web selects the crop; Media processes temporary HDR input and validates the cropped output under the Profile picture type policy. The raw input remains private and temporary, and the accepted output no longer returns through Web for upload into User-owned storage. The existing SDR browser-editor path still produces a processed crop for admission into Media. User owns the Profile reference and its workflow. Ordinary picture replacement retains the Asset ID and switches the complete accepted Source set, preventing other format/range requests from selecting the previous picture.

Media checks the expected revision of that accepted Source set before replacing a picture. A competing picture mutation preserves the winning accepted set and requires explicit retry of the retained edit. User checks Profile concurrency for initial attachment/removal, but unrelated Biography changes no longer conflict with ordinary Source replacement. This replaces #243's broad Profile-version coupling for that operation while preserving its conflict/retry behavior. User's durable workflow fences stale confirmations and results against current attachment/removal intent.

This replaces ADR 0009's output-byte transfer, User storage/validation authority and exclusion of processed output from Media's catalog. Native processing remains in Media. Preserve the [#270 product requirements](https://github.com/rafaeltab/wallpaperdb/issues/270#issuecomment-5902621514), including crop, configured dimensions/bytes, HDR routing, motion, alpha, sanitation and canonical validation. The cropped output is a Source accepted through intake, not a Materialized rendition of the unedited input. No new HDR path is qualified by this ownership change.

ADR 0008's producer-issued byte identities, producer bucket layouts and producer-only deletion responsibilities no longer define new Media Assets. Media owns source storage mapping and cleanup. Preserve logical references without storage coordinates in integration contracts, immutable Source bytes, non-reuse of retired identities, and explicit treatment of future layout changes. This decision introduces no descriptor registry. The [clean rebuild](https://github.com/rafaeltab/wallpaperdb/issues/257#issuecomment-5940357833) requires no historical layout migration or compatibility implementation; #259 owns the new layout specification.

The Media-local ADR's immutable wallpaper targets, read-only source credentials and producer-owned deletion describe the existing implementation. In the target, immutable bytes belong to Sources while Asset membership and delivery state change under Media authority. Its durable acceptance, replay, outbox and recovery obligations remain. Media owns private-evidence retention and cleanup under per-Asset-type configuration, preserving the existing 30-day Profile picture default and recorded expiries as described in [ADR 0011](0011-unlink-profile-pictures-before-asynchronous-media-deletion.md). Temporary input expiry and terminal replay fences are separate obligations.

The [confirmed public announcement](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6251166579) is a change-driven complete snapshot of Asset ID, revision and compact jointly faithful output capabilities with sizing constraints and valid native coverage. It excludes Owner, Default Source, Source identities/membership, storage and diagnostics. Qualified outputs count before materialization; processing-support changes can revise the snapshot, deletion empties it, and temporary outages do not clear it. Native size/shape coverage remains required for browsing, while categorical filters describe faithful outputs.

Rendition delivery cannot enlarge an accepted Source. The [confirmed intake distinction](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312425664) retains #243/#270's small-crop authoring behavior, which may enlarge a crop to the configured processed picture size before acceptance. Explicit dimension preserve refers to the Default Source; if no eligible sufficiently large Source can satisfy the preserved size, the request fails rather than enlarging bytes or silently weakening preservation.

The [confirmed dimension rule](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312526402) makes omission equivalent to inherit. Both inherited axes use the selected Source's native displayed dimensions; one numeric axis derives the inherited axis proportionally. Two concrete constraints must match the Source's aspect ratio unless fit is explicit, under the no-enlargement rule. Inheritance refers to the Source, not a smaller Materialized input selected for reuse. #259 owns concrete sizing tables, schema and bounds under #256's selected generation and input-ranking policy.

The [#256 fit amendment](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525) replaces the earlier default `contain` and its no-padding meaning. Explicit `inside` scales proportionally within requested bounds without padding; explicit `contain` retains image proportions within an exact requested canvas with centered opaque-black padding by default. Explicit padding colors and transparent padding are available where the qualified output path supports them, without waiving Source-alpha preservation. `cover` crops proportionally and `fill` stretches when ratios differ, subject to current qualification and no delivery enlargement. Omitted fit rejects a request whose resolved dimensions require an aspect-ratio change, for both HTTP delivery and configured materialization. It does not silently select a fit mode. Allow only unavoidable integer-pixel rounding under a consistently defined proportional-resize rule; #259 specifies and tests the deterministic rule and exact boundaries. Neither the 3% Source-admission nor the 5% browse tolerance is a delivery-sizing tolerance.

The [confirmed #256 selection policy](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525) considers active accepted Sources and usable Materialized inputs with their Source provenance. It first filters for faithful satisfaction of the complete request under current processing qualification, lifecycle and preservation constraints. For explicit SDR, eligible authored SDR Sources and their qualifying descendants precede embedded authored SDR bases and their descendants, which precede qualified conversion. Within the eligible precedence class, select the smallest adequate actual displayed pixel area after accounting for fit, without enlarging any input. At equal adequate resolution, prefer a proven exact Source no-op, then an exact stored output, then the least processing, with a stable identity as the final tie-breaker. A Source no-op returns exact Source bytes. A smaller cropped, static, SDR or lower-depth output cannot recover information its processing discarded merely because its dimensions are adequate.

When both dimensions inherit, #256 selects the eligible Default Source within the required precedence class as the reference, otherwise the largest eligible Source in that class. Its native displayed dimensions establish the target, and all inherited characteristics refer to that same Source. Stored intermediates cannot reduce the target. If a stored output is missing or unsuitable, try another faithful stored output and then generate from the selected eligible Source under current limits, without persisting arbitrary on-request results. Established readiness, unsupported-rendition and temporary-failure responses apply when no valid path succeeds; missing stored inventory does not withdraw discovery eligibility.

The [confirmed ahead-of-time configuration](https://github.com/rafaeltab/wallpaperdb/issues/256#issuecomment-6320862525) preserves the supplying Source's aspect ratio and complete frame, without cropping, padding or stretching. Per-Asset-type configuration expresses desired outputs as `materialization.renditions: RenditionRequest[]`. Each entry uses the same request values, defaults and sizing semantics as HTTP delivery. The Asset service resolves each request against the Asset's accepted Source set using the confirmed Source-selection policy, rather than automatically generating it from every Source. The Asset service determines whether each target can be produced faithfully under current Source facts, qualification and limits; an entry is not evidence that its bytes exist or that its requested characteristics were actually encoded. A configured mismatched aspect ratio is ineligible even when an explicit `inside`, `contain`, `cover` or `fill` could deliver the request. An explicit fit that changes nothing for a matching Source/target ratio remains eligible. Mismatched requests can still be qualified for explicit on-request delivery. Later crop requests use the same qualified processing semantics as direct Source processing. #259 selects concrete initial per-type request arrays and measured work, preserving #263's full-resolution materialized SDR wallpaper requirement; earlier illustrative lists are not generation defaults.

Ahead-of-time generation starts directly from Sources. The user's quality requirement is to preserve the highest available quality for reusable intermediates and avoid cumulative degradation in later delivery. It does not require a mathematically lossless codec mode for every format. Generation and reuse still need qualified fidelity against direct Source processing; a maximum encoder-quality setting alone does not prove that a second encode is faithful. Exact encoder settings and measured acceptance belong to #259, without a new public quality selector or relaxing HDR qualification. The user deferred optional persistence of arbitrary requested results, retaining the existing caching exclusion.

Generated outputs have immutable identities tied to their Source provenance, resolved processing settings and encoding revision. Changed Sources or relevant encoding settings receive new output identities; retries reuse the committed result. Do not overwrite earlier bytes or replace their actual facts with requested settings. Reuse begins only after durable bytes and actual matching facts exist, using replay-safe local acceptance and external steps. Current membership, preservation requirements, policy and terminal deletion fence stale work and reuse independently of private byte retention. Exact normalization, identity encoding, storage layout and revision activation remain #259 specification details.

Individual accepted Source/default changes and newly usable inspection facts automatically trigger asynchronous consideration of configured targets. Configuration and processing-support changes update effective eligibility and desired targets but cannot automatically launch materialization across existing Assets. Applying additions, changed targets and retirement across the existing population requires an explicit manual, pausable operation with bounded processing load and durable progress. This prevents a configuration edit from starting an unexpectedly large generation batch and exhausting production capacity. Pause stops starting new files, lets bounded in-flight work finish and remembers where to resume. Safe existing outputs remain available while deliberate replacement work is pending; lifecycle or qualification changes exclude unsafe outputs immediately. Cleanup is asynchronous and cannot remove active Sources or current outputs. #259 specifies operator controls, resource budgets, durable pause/resume through restart and stale-work handling while preserving capacity for public delivery. This is ongoing management of the clean new system, not historical migration or backfill.

Public requests use one Asset URL with query selectors, including format, while exact Source access remains owner-protected. Returned filenames and extensions identify the actual encoding, including preserved/inherited formats and no-op bytes. An Asset URL can change representation under the same identity, so HTTP validation must distinguish its selected bytes from immutable Source identity. A representation-changing Source/default/processing update cannot receive an incorrect 304 based only on the stable Asset ID. No new caching mechanism or cache policy is selected; #259 must verify validators and actual browser save names.

The [selected wallpaper still-image defaults](https://github.com/rafaeltab/wallpaperdb/issues/391#issuecomment-6312814842) are inclusive 50 MiB encoded bytes, 100,000,000 pixels and 20,000 pixels per displayed axis. Media makes them operator-configurable by Asset type. Similar aspect ratio compares the candidate with all active Sources, including the replaced Source, using `largestRatio / smallestRatio - 1 <= 0.03` after orientation. Policy changes apply prospectively and acceptance rechecks the effective policy with current membership. These defaults do not broaden Source admission beyond selected qualified classes or settle animation/native resource budgets. Profile pictures retain their independently selected 512-square, 5 MiB processed and 50 MiB temporary-HDR defaults; #259 sizes resource and payload limits and specifies configuration activation.

Wallpaper color measurements use the first Default Source and retain that provenance for the Asset's lifetime. Later default changes, replacements or withdrawals do not automatically change the measurements. This avoids repeated color-information changes and anticipates future visual continuity, but the user explicitly accepts initial divergence while substantial replacements remain permitted. Neither similarity enforcement nor a permanent private-byte hold is selected. Preserve the first measurements durably; ordinary Source byte retention remains per type, and purging those bytes does not authorize silently re-extracting a different image. The color algorithm is unchanged. Visual-continuity research is deferred to [#414](https://github.com/rafaeltab/wallpaperdb/issues/414), without blocking the initial lifecycle.
