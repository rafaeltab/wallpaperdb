# Factory operations

Repository-owned operational infrastructure for continuously admitting and observing trusted ready issues through implementation, independent review, publication and CI observation. It is separate from the WallpaperDB product and runs on the host so it can use the existing authenticated GitHub and headless T3 installation.

## Capabilities

Validated semantic plans continuously refill capacity. A maintainer can also select a trusted ready issue and narrow its execution with context. Both paths share durable admission controls. The factory durably reserves the admission and expected implementation stage, requests a dedicated T3 thread/worktree using gpt-6.1-sol, and shows stage, elapsed time and issue/thread links. Launch uncertainty preserves the reservation and reconciles the exact job identity instead of launching twice. Only a structured outcome from the expected completed run (or a current babysitting watcher run carrying the exact active delivery identity), at the clean current commit and pinned base, advances a stage. Review-loop requires fresh independent Standards, Spec and Defects review; applicable tests, coverage and CRAP remain mandatory. Mutation and hosted review are advisory. The dashboard distinguishes current-commit PR readiness from verified default-branch landing.

The dashboard's **Generate plan preview** control automatically reads open ready issues, native and fallback blockers, parent requirements, trusted maintainer comments, configured prerequisite evidence and all active and parked jobs and current capacity. A separate gpt-6.1-sol planning thread returns a structured advisory proposal through `IPlanner`. Code rejects ineligible, cyclic, stale, duplicate and semantically constrained selections and presents their reasons. Preview never reserves an admission or dispatches implementation. The scheduler uses the same validated planning contract for automatic admission. Planner response failures are visible, and correctness tests use controlled external protocol endpoints rather than live model decisions. See the [planning port](src/capabilities/plan/index.ts), [GitHub discovery adapter](src/adapters/github/index.ts) and [T3 planner adapter](src/adapters/t3/index.ts).

Discovery fails safely if its 1,000-issue/context bound is reached or required context cannot be read. Planner responses are associated with the exact request and assistant run. The planner waits at most 120 observations; timeout or cancellation does not interrupt the external advisory thread. Within one service lifetime, the adapter retains responsibility for one outstanding advisory launch. Repeating preview observes the same known run and refuses another launch until its terminal state is verified. An uncertain launch blocks further planner starts and requires operator reconciliation. This in-memory bound does not survive service restart. Scheduler reservations and job associations survive restart independently of this advisory-planner limit. Durable recovery of the advisory planning thread remains unavailable.

## Operating constraints

Use the repository [Make targets](../../Makefile) and [pinned toolchain](../../mise.toml). Configure the pinned base, active T3 binary and private state directory in the [environment template](.env.example) before starting. The active installation must support headless thread start/list/show with worktree/model selection; the PATH launcher may be older. Startup checks the installed interface without upgrading or restarting T3. Bind only loopback or the host's tailnet address and restrict access to maintainers with tailnet ACLs. The HTTP interface deliberately has no public Internet deployment or product ingress.

State uses immutable, fsynced files and atomic hard links on a local Linux filesystem. Its parent directory must already exist and be durable; keep state outside the checkout/install directory. Do not remove a reservation to retry an uncertain launch. An interrupted launch can remain uncertain indefinitely when T3 cannot establish its identity. This favors avoiding duplicate workers over automatic retry. Stage sends have durable claims and use a stable delivery key when the installed CLI advertises support. The currently deployed CLI has no send idempotency key. A crash between claim and delivery remains visibly pending and requires operator investigation; it never automatically repeats a potentially successful send. Immutable stage records retain thread, run predecessor, comparison and commit associations across restart. Applicable failed CI dispatches babysitting to that same binding. Successful repair proceeds through independent review and publication before current-head CI readiness. Explicit expected-run GitHub-wait outcomes start a persisted one-hour watchdog; current CI run/job/step progress resets it. A single continuation is retained across restart and uncertain delivery. Active repair and human questions do not trigger this watchdog.

Open blockers require completed acceptance and independent review with passing CI at a pinned PR commit. Readiness comes from the owning completed factory job or explicit operator assertions for existing work. The adapter rechecks the live PR head, required CI, issue evidence and real Git ancestry before admission. Record the PR URL and validated commit in the blocker issue body or a trusted maintainer comment. Linear dependents and parallel forks start in dedicated worktrees at the deepest verified prerequisite tip, with that branch as their PR target. All prerequisites must already coexist in one linear ancestor chain or the configured base. Divergent joins remain visibly blocked pending join support. See the [prerequisite adapter](src/adapters/github/prerequisites.ts). Closed blockers need no assertion. Project status is reporting and does not trigger admission. The service does not claim or change issue lifecycle state.

The dashboard edits concurrency, distinct issue allowance and admission pause. Both limits initially permit one and accept -1 for unlimited. Concurrency includes implementation, review, publication and CI waits. Distinct reservations consume allowance once, including across restart; continuing an existing issue does not consume another admission. Lowering limits preserves existing jobs. Pausing admissions leaves existing work running. Controls use revision checks so stale submissions cannot overwrite newer settings. The scheduler reserves durably before launching and refills a completed slot while other jobs continue. Parked work does not satisfy dependents, and unrelated frontier work can continue. Stack maintenance, divergent joins, upgrades and resets remain unavailable. See the [scheduler contract](src/capabilities/plan/index.ts) and [durable store](src/adapters/store/index.ts). Questions and results stay in T3. Current owning-run structured user-input requests park the existing job visibly and report its active capacity as released. An observed answered request reacquires the existing stage and adopts the owning T3 continuation without sending another start. Otherwise refresh and explicitly resume that job. A cleared request alone never accepts or restarts the stage. Resumption retains the issue, worktree, thread, stage, pinned base and scope context, with a durable claim before delivery. Its distinct admission remains consumed. Cancellation is a separate explicit command that durably prevents subsequent factory deliveries and requests idempotent interruption of the owning T3 thread. Removing readiness labels does not cancel admitted work. The service reconciles jobs and admission opportunities periodically without a browser connection. Configure the intended PR target alongside the pinned comparison commit. Publication uses the existing issue thread and reusable publication skill; it must reconcile an existing PR and link it in T3. Required current-commit CI includes repository build/lint/tests and both E2E jobs; reported Codecov failures block readiness. It never merges or closes an issue.

Optional OTLP HTTP tracing uses a factory-owned provider and propagates inbound trace context. It does not register global product telemetry. Export sockets have bounded cleanup. Shutdown allows five seconds for HTTP requests, then closes their connections and cancels outstanding CLI subprocesses; external T3 workers and durable reservations remain intact.

Question observation and cancellation require the pinned binary's `acp-mcp-call` interface and an authenticated native MCP endpoint. Set `FACTORY_T3_MCP_ENDPOINT` and `FACTORY_T3_MCP_AUTHORIZATION_FILE` to a private file containing the complete `Bearer ...` authorization header. Use a dedicated MCP client session with orchestration read/operate authorization and the runtime ceiling required by the existing worker. Ordinary CLI-issued sessions are not MCP clients. The native local auth command supports an explicit `--subject mcp-client`; follow its `auth session issue --help` for scopes and expiry, keep credentials outside the checkout, and revoke them when retired. An unavailable or expired credential fails observation safely and preserves all records. No vendor database access or host upgrade is used. With MCP configured, stage sends use its stable `clientRequestId`; the CLI fallback remains safely pending after uncertain delivery. The service must have both MCP settings to handle questions and cancellation.
