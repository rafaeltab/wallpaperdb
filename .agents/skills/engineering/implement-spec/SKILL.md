---
name: implement-spec
description: "Implement a spec's tickets sequentially in T3 worktrees, stack their PRs, and verify the complete spec."
disable-model-invocation: true
---

Apply [task scope](../../../../docs/agents/task-scope.md) throughout coordination and complete-spec review. Include its scope and decision context in ticket-thread and reviewer briefs and the existing progress record.

1. Read the full spec, tickets, comments, and dependencies through the [issue tracker](../../../../docs/agents/issue-tracker.md). Order unfinished tickets by dependency. Verify already-landed requirements before excluding them.
2. Follow [setup](references/setup.md). For each ticket, launch one ordinary T3 thread with `t3_thread_launch` in a separate worktree. Base the first on fetched `main`, and each later ticket on the preceding PR's verified published head. The coordinator owns branch and worktree setup.
3. Give the thread the issue, full spec, predecessor PR, current workflow instructions, and [publication constraints](references/stack-recovery.md#publishing), including its expected remote tip or absence. Tell it to use $do-work through publication, keeping its PR draft. Wait for completion and verify the published PR, passing reviews, validation, and issue evidence before starting the next ticket.
4. Keep one PR per ticket: the first targets `main`, each later PR targets the preceding PR. Follow [stack publication and recovery](references/stack-recovery.md). Record ticket threads, worktrees, PRs, and passing commits outside the repository. Reuse existing threads for repairs and [continuation](references/continuation.md).
5. After every ticket is published, run separate $code-review and $review-agent subagents in parallel on the complete stack against current `main`. Give them the full spec and all tickets. Require the Spec review to account for every requirement with implementation and validation evidence, including cross-ticket behavior and requirements missing from tickets. Record comparisons and results. Assess existing evidence before repeating reviews after implementation or base branch changes; retain applicable evidence and review affected or unresolved work with its interactions.
6. Fix every confirmed in-scope gap in its owning ticket thread with new commits. For authorized required work without an owner, add a ticket and run it through steps 2–4 in dependency order. Apply task scope to proposed expansions before assigning implementation. Refresh affected layers, validation, and reviews, then repeat the complete-spec review until no required work or scope decisions remain pending. Report user-deferred proposals separately.
7. Validate the completed top branch with $testing, then verify published heads and PR targets match the validated work covered by direct or carried-forward review evidence. Check for merge conflicts. Mark PRs ready, recheck complete native membership, order, and readiness for multi-ticket stacks, verify tickets are `In Review`, and report PRs, thread links, validation, and the final spec verdict. Keep worktrees for repairs. Leave issues open until landing; merge only when explicitly requested, following [landing rules](references/landing.md).
