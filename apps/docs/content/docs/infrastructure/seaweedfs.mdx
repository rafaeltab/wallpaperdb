---
title: Migrate storage to SeaweedFS
description: Preserve existing MinIO objects and configuration when switching storage providers.
---

Local object storage uses SeaweedFS. For connection settings, use the generated `infra/.env` and app environment files. Host S3 clients use the worktree's `S3_API_HOST_PORT`; Docker clients use the Compose service endpoint.

Profile picture buckets must remain private. Follow the [picture storage requirements](/docs/guides/service-upgrades#private-pictures-and-evidence), including when creating a custom bucket.

## Existing MinIO data

SeaweedFS uses a new `seaweedfs-data` Docker volume. Its storage format differs from MinIO's, so do not mount the old `minio-data` volume into SeaweedFS. The migration does not copy or delete existing objects; an existing database may therefore reference wallpapers that still need copying.

Before starting the replacement service, stop the old MinIO containers so they release the S3 host port. In the old checkout, stop application writes and run `make infra-stop` before switching branches. This preserves the Docker volumes.

If you have already switched to the migrated checkout, stop application writes and remove the old containers with the following command from the repository root. Replace `wallpaperdb` with `COMPOSE_PROJECT_NAME` from your worktree's `.worktree` file:

```bash
docker compose -p wallpaperdb -f infra/docker-compose.yml down --remove-orphans
```

Do not add `--volumes` or `-v`; the old `minio-data` volume must remain intact. This also stops the other infrastructure containers for that project. Update configuration as described below before running `make infra-start` to start the new stack.

### Update existing configuration

Before regenerating environment files, copy any customized values from your existing `.env` files or override sources into the new settings:

| Previous setting | Current setting |
| --- | --- |
| `MINIO_ROOT_USER` | `S3_ACCESS_KEY_ID` |
| `MINIO_ROOT_PASSWORD` | `S3_SECRET_ACCESS_KEY` |
| `MINIO_API_HOST_PORT` | `S3_API_HOST_PORT` |
| `MINIO_CLEANUP_INTERVAL_MS` | `S3_CLEANUP_INTERVAL_MS` |

Update your shared secrets file (`$XDG_CONFIG_HOME/wallpaperdb/secrets.env`, or `~/.config/wallpaperdb/secrets.env` by default), CI settings, and exported shell variables as applicable. Remove old entries after copying their values. These old variable names have no runtime fallback. If you keep existing credentials, use the same values for the replacement server and all app clients; the new defaults are `storageadmin`.

Run `make install` to regenerate `infra/.env` and per-app `.env` files. This replaces generated files, so save any custom values in the override sources first. Remove or update an overridden `S3_ENDPOINT=http://minio:9000`: Compose clients now use `http://seaweedfs:9000`, and the old network alias is removed. Host clients use their assigned `S3_API_HOST_PORT`.

Update external health checks that read the old `minio` response field to read `s3`.

### Copy and verify objects

For data you want to retain:

1. While application writes are stopped, take backups of the database and old object storage. Keep the old MinIO volume and a usable source server or backup until migration is verified.
2. Stop/remove the old service containers as described above, then start SeaweedFS with its new volume. If a running source is needed, restore or run the old MinIO server under a separate Compose project with a different host port and network, so it cannot claim SeaweedFS's port. Preserve the source's original data.
3. Copy every required bucket and object through the S3 API. An S3 migration tool must support distinct source and destination endpoints and preserve content types, user metadata, and other headers your application relies on. An ordinary download/upload through a local directory does not preserve all object metadata automatically.
4. Compare bucket inventories, object counts, sizes, contents or checksums, and metadata. Exercise uploads and media retrieval against the destination while writes remain paused.
5. Resume applications against SeaweedFS after verification. Keep the source and backups until you explicitly decide to retire them.

For disposable development data, start with the new empty object store and reset the associated database only if you intend to discard its existing wallpaper records. Avoid `make infra-reset` while preserving data, as it deletes active infrastructure volumes.
